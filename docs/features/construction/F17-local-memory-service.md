## 背景

### 现状与痛点

多 Agent 接续要求 JiuwenSwarm、Codex、DeepSeek Harness（下称 DSH）等宿主读写同一份任务记录。现有两种接入都不满足：

| 接法 | 问题 |
|---|---|
| JiuwenSwarm 用 SDK | 内核在 JiuwenSwarm 进程里，关掉它记忆就停。接续 Registry 用单写者文件锁（`claim_single_writer`），别的进程打不开，任务接不上 |
| HTTP 服务 | 记忆独立了，但用户要自己启动服务、写配置、签发凭据，单机使用太重；MCP 桥还要求手工配置 `AGENT_MEMORY_URL` |

**记忆应该属于这台机器上的用户，而不是某一个 Agent。**

### 代码核对后的事实

以下事实决定了方案不能只是"把 Portal 的做法推广到内核"：

1. **Portal 子进程不含内核。** `portal/shared.py` 的共享 Portal 只把浏览器请求经 IPC 转回各 SDK 进程。能复用的是启动锁、私有目录、独立子进程和 IPC 工具；它的 10 秒启动超时也不适合加载模型的内核。
2. **凭据不持久。** API Key 只有内存 key store（`memory_key_store.py` 注明"进程重启后所有已签发的 key 失效"），每次请求做一次 Argon2id 校验（约 50～200 ms、128 MiB，默认并发 4）。
3. **JiuwenSwarm 默认配置会丢数据。** 内置默认装配的 KV 是 `memory`、审计是 `:memory:`；对话原文 `/messages/`、空间成员、dreaming 注册表都在进程内存里。
4. **SDK 与 HTTP 的 Scope 语义不同。** SDK 五维直映射；`_HttpClient._scope_payload` 会把 `space` 清空、`user` 换成认证身份、原 `user` 挪到 `session`，并丢弃 `org` 和 `session`。直接把 JiuwenSwarm 改走 HTTP，旧记忆会查不到。
5. **通用 MCP 桥不完整。** `continuity/client.py` 只允许 `continuity_task`、`continuity_relation`、`continuity_recover`、`batch_add`、`get`；MCP 只注册前三个，没有 `add` / `search`，且把 409 压成 `rejected`，丢失 `WriteIncompleteError` 的 `operation_id`。
6. **接续连接是静态配置。** `globals.continuity_connectors` 在装配时读取，新增一个 Agent 需要改配置、建空间成员、签发凭据。
7. **watchdog 不做启动对账。** `local_watchdog.py` 只处理启动后的文件事件，停机期间对 md 的手改不会进入影子索引。
8. **跨宿主接手受 owner 限制。** 除 create / get / find 外的任务操作只允许 owner；写入事件要求绑定连接就是调用者。
9. **打包缺口。** 根 wheel 排除了 `mcp_server` 和 `cli`，无 console script；`watchdog`、`sqlite-vec` 不在默认依赖。

## 目标与非目标

**目标**

1. 本机每个用户、每个数据目录只运行一个记忆服务，作为 Registry 和所有存储的唯一写者；关掉任一 Agent 不影响记忆。
2. 任何已连接的本机 Agent 首次用到记忆时自动拉起服务，多个 Agent 同时启动也只起一个。
3. Codex、DSH、Hermes、WorkBuddy 默认经 **MCP** 接入（模型通过工具读写）；每轮自动召回与自动写入作为可选的 **hook 增强**，Codex 默认开启，其余默认关闭、可按安装打开（D14）。JiuwenSwarm 沿用原生记忆插件，始终自动。
4. 每个宿主安装有独立身份，可追溯来源、可单独撤销。
5. 已有 JiuwenSwarm 用户切换后，原个人记忆、任务与绑定仍可见。
6. 一个宿主创建的任务，另一个从未参与的宿主可在用户确认后接手，原宿主不必在线。
7. 指定宿主目录后，可把 Codex、DSH、Hermes、WorkBuddy 自己保存的记忆**同步导入** agent memory，可反复执行、结果一致（D15）。
8. 装好 agent memory 后，经用户授权自动找出本机已安装的 Codex、DSH、Hermes、WorkBuddy 实例并批量接入，再逐个引导同步其已有记忆；之后新出现的实例自动接入（D16）。

**非目标**

- 不做跨主机、多写实例；团队部署仍是现有 HTTPS 服务，本特性只是同一协议的本机形态。
- 不把扫描宿主私有文件当作**默认**采集方式：D16 的本机扫描只看路径是否存在、不读文件内容；记忆同步只在用户对某个安装显式开启读取、并执行或开启同步后才读取，且只读，不修改宿主文件（D15）。
- 不提供同一系统账号下进程间的防冒充隔离：同账号程序能读到彼此的令牌文件，身份只用于来源归属。
- 不实现 Agent MCP 业务封装（服务端维护 active task / binding 状态的薄工具层），见 D11。

## 决策

### D1：服务按数据目录唯一，配置归服务所有

- 数据目录 `~/.jiuwen-memory/`（Windows `%LOCALAPPDATA%\jiuwen-memory\`），可由环境变量覆盖。服务身份 = 数据目录的规范路径，不按调用方的配置区分。
- 布局：

  ```
  service.yaml   服务独占配置：模型端点与密钥引用、文档目录、全部持久存储
  run/           start.lock、service.json（pid、端口、协议版本、启动时间），目录权限 0700
  installs/      每个宿主安装一份：令牌文件、安装记录（写了哪些宿主配置）
  data/          SQLite（KV、Registry、权限、审计、证据图）与影子索引
  ```

- `jiuwen-memory init` 首次生成 `service.yaml`：KV、审计、权限、Registry 一律 SQLite（`fixed_path: true`），不得使用 `memory` / `:memory:`；`continuity.default` 为 `mode: continuity`（需要关系时改 `role`）、`single_writer: true`。
- 模型密钥写在 `service.yaml` 引用的密钥来源中，**不从拉起方继承环境变量**，否则谁先拉起服务，模型和行为就由谁决定。

### D2：本机传输用 loopback HTTP + 发现文件

- 服务复用现有 `HttpServer`（`/v1/<方法名>`、Portal 路由、认证中间件、有界线程池），绑定 `127.0.0.1:0`，实际端口写入 `run/service.json`。
- 客户端读发现文件后用现有 `_HttpClient` / `ContinuityClient` 连接；团队部署只是把发现文件换成显式 HTTPS 地址。
- Unix 套接字和命名管道不作为首版传输。Portal 面向浏览器，本来就要开端口；命名管道需要两端都自写 HTTP 层。
- 启动锁、私有目录校验从 `portal/shared.py` 与 `_posix_ipc.py` / `_windows_ipc.py` 抽成公共模块，Portal 与本服务共用一份。

### D3：每个宿主安装一份凭据（本机令牌认证器）

- 新增认证器 `local_token`：`connect` 时生成 256 位随机令牌，服务端在 SQLite 中保存其 sha256、主体、角色与所属安装 ID，常时间比对，支持撤销；重启后仍有效。
- 令牌明文只写入 `installs/<安装 ID>/token`（POSIX 0600，Windows 仅当前用户 ACL），宿主配置里只写令牌文件路径。服务端只有摘要，**明文丢了无法复原**，因此签发顺序固定为：先在安装私有目录**原子写入令牌文件**，再登记其摘要（见 D5 第 1 步）。
- 不变量：**同一安装 ID 任何时刻至多一份有效令牌**。
- 选它而不选现有认证器：内存 `api_key` 重启即失效，且每次请求做 Argon2id；`trusted` 只有一个网关共享密钥，持有者可声明任意主体。高熵随机令牌不需要慢哈希。
- 这是安全能力变更，设计决策归档到安全能力 F04，接口契约更新 S10；本文只记录它在本特性中的作用。

### D4：主体粒度——每个安装一个主体，JiuwenSwarm 沿用原身份

- 新接入的宿主各发一个主体，例如 `{org: <本机组织>, agent: codex-<安装 ID>}`；`connect` 同时把它登记为 `continuity_connectors` 中的一条连接，并加为默认项目空间成员。
- JiuwenSwarm 例外：沿用它在 SDK 模式下的**完整认证主体**（五维 actor，不只 `org` / `user`）。任务 owner 取完整 actor 的指纹，连接匹配也比较完整 actor，少一维就会失去原任务的 owner 权限或匹配不到原连接。**只保留身份也不足以让旧记忆可见**：新服务还必须打开原来的 Markdown 目录、影子索引与 Registry 文件，保持记录的五维 Scope 不变，并恢复项目成员关系，切换流程见 D12。
- 共享的是**项目空间里的任务记录与记忆**；各主体的个人记忆不自动互通。
- **不新增"用户本人"主体。** 任务的兜底管理权交给已有的项目空间管理员角色（`MANAGE_SPACE`，见 D13）。管理员来源按空间区分：
  - **全新创建的空间**（`init` 建的默认空间等）：由第一个 `connect` 的安装担任；
  - **迁移来的已有空间**：只保留原权限存储或可信导出中的管理员（D12），**不因迁移把任何主体提升为管理员**。旧 JiuwenSwarm 主体原来只是写成员，迁移后仍只是写成员；
  - 已有空间缺少可用的管理员凭据时，走单独、显式的**管理权恢复流程**：由本机用户在命令行执行 `jiuwen-memory space recover-admin --space <空间> --as <安装>`：命令行在 `data_dir` 写一次性 0600 口令，服务用同一 `space` 组件对同一 KV 存储执行成员维护并失效空间事实缓存，二次确认与 `audit.log` 后完成；不提升任何安装令牌，不在迁移中自动完成。

  命令行与 Portal 使用已有安装的令牌执行管理操作（如 `jiuwen-memory task close --as <安装>`）。撤销令牌不删除主体，重新 `connect` 同一宿主可为原主体补发令牌，管理权随之恢复。
  - 理由：本机同一系统账号的进程能读到彼此的令牌文件（见非目标），另设一个"用户本人"主体也挡不住 Agent 读取它的令牌，安全收益接近零，只多一个实体。
- 拒绝"所有宿主共用一个用户主体"：区分不出来源，无法单独隔离出问题的 Agent；且按认证主体唯一解析连接的接续逻辑在多连接共用主体时会出现多匹配。

### D5：`connect` / `disconnect` 一次完成登记与回滚

- `jiuwen-memory connect <宿主> [--capture=off|task]` 是一个**按安装 ID 幂等的步骤序列**：
  0. **先生成并持久化稳定的安装 ID**，此后各步的副作用都以它为键（令牌、主体、连接名、空间成员、宿主配置条目），而不是依赖"做完了再记账"；
  1. 按安装 ID 补齐令牌与主体，**始终以令牌文件为准**：
     - 没有令牌文件：生成令牌并原子写入文件，再登记摘要；
     - 有令牌文件：确认服务端登记的正是该文件的摘要，没登记就补登记；
     - 服务端登记了该安装的其他摘要（例如文件未写成就退出、只留下摘要）：**先撤销旧摘要**，再按当前文件登记，保证同一安装只有一份有效凭据；
     - 主体按安装 ID 查询或补齐。
  2. 按安装 ID 查询或补齐 `service.yaml` 中的连接；
  3. 按安装 ID 查询或补齐项目空间成员；
  4. 让运行中的服务载入新连接（见下）；
  5. 经 `GET /local/status` 用该令牌确认：服务已识别该主体、连接已启用、空间授权已生效；
  6. 最后**合并写入**宿主配置（MCP 与 hook）。每个文件先写临时文件再原子替换，写完**回读核对**本安装 ID 的全部条目都在。
- 安装记录只是进度缓存，**不是真相来源**：重跑时每一步都以实际状态为准，即使某步的副作用已经发生、进度还没记上，也能识别并接着做。`disconnect` 同样按安装 ID 查找并清理所有副作用，不依赖安装记录是否完整。
- 只有第 6 步全部写入并回读成功，才报告"连接完成"。任一步失败都返回"未完成，可重试"；宿主配置放在最后写，保证 hook 装上时连接一定可用。
- 合并写入是硬要求：例如用户 `~/.codex/hooks.json` 已有其他工具注册的 8 个事件，不得覆盖。
- `disconnect` 先撤销令牌，再按安装记录回滚本工具写入的条目；用户后来修改过的条目保留并提示。
- 并发保护：安装记录的创建与 `service.yaml` 的读改写共用同一文件锁，两个宿主（或同一宿主重复）同时 `connect` 不会丢连接或产生两个安装。
- 出站复核与 `capture=task` 合并为**一次**确认，放在第 3 步**之前**（服务已拉起、令牌已准备，但空间尚未创建）：同一条提示里展示 D9 的数据去向清单和将要保存的内容；提示中的 capture/project 是**候选策略**，确认前不写安装记录或 connector。回答"否"时：新安装清理并标记 `disconnected`；已连接安装保持原连接、原令牌与原策略不变，不写任何宿主配置，也不创建空间或成员关系。确认前若读取 egress 或拉起服务失败，也不得把已连接安装改成 `installing`，否则下次取消会误走清理分支。
- 建空间需要组织 `ADMIN`：`connect` 用一个一次性 admin 令牌调用 `create_space`，调用后立即撤销并删除该凭据记录；安装令牌始终保持 `USER`，避免临时提权期间该令牌的其他并发请求获得管理权限。
- 安装主体由**完整安装 ID 的摘要**生成（相同 ID 幂等、不同安装必不相同），避免 `jiuwenswarm-*` 前缀导致重装继承旧成员关系与任务所有权。
- 宿主"连接完成"以宿主实际加载状态为准：DSH 通过 `dsh plugin --profile … add/list` 安装并核对每个 profile；记录本次实际新增的 profile，成功重连时与同一 install_id 的旧记录取并集，部分失败和断开时只撤销这些 profile，接入前已存在的插件保留；`list` 查询失败与"确认未安装"分开处理，无法判定时拒绝猜测归属。JiuwenSwarm 回滚只恢复本次安装写入且用户未再修改的字段（YAML/JSON 一致），保留其他修改并上报。
- 已有空间补成员时，`connect` 会借用本机**任一能通过 `list_space_members` 的已连接安装**的令牌执行 `add_space_member`。这依赖 D4「同一系统账号下不做隔离」的前提：能读 `installs/*/token` 的本机进程本就能代表这些安装。该调用经服务 PEP，并按本机模板的 SQLite 审计配置记录操作者与目标。
- `service stop` 先探活并比对发现文件的 PID 与 `instance_nonce`；过期发现文件只清理、不发送信号，避免 PID 复用误杀。
- **载入新连接 ≠ 空闲退出**，两个条件分开定义：
  - *可重载*：停止准入新请求、在途请求排空即可，**不要求没有租约**。其他客户端在重载期间收到"服务正在重载"，经发现文件重连，自行重试尚未发出的请求。
  - *可退出*：见 D7，要求无租约、无在途请求、无 Portal 会话。
  首版 `continuity_connectors` 仍是装配时读取的静态配置，因此"载入"用一次可重载的优雅重启实现，由 `connect` 主动触发，不等服务空闲；JiuwenSwarm 持续在线也不影响第二个宿主接入。运行时热更新连接、免去重启列为遗留。

### D6：自动拉起与进程脱离

- 所有客户端（JiuwenSwarm Provider、MCP 桥、Codex hook、DSH 插件、命令行）共用同一段拉起逻辑：读发现文件并探活 → 失败则取 `run/start.lock` → 再探活 → 仍失败则用固定解释器拉起服务子进程 → 等待就绪（超时按加载模型的耗时设，远长于 Portal 的 10 秒）。多个客户端并发只会起一个服务。
- 服务进程脱离父进程：POSIX 用新会话，Linux 有 systemd 时优先 `systemd-run --user`；Windows 加 `DETACHED_PROCESS` 与 `CREATE_BREAKAWAY_FROM_JOB`，宿主 Job 不允许脱离时告警。否则宿主被 systemd、容器或 Windows Job 统一回收时会连带杀掉服务，原问题重现。
- 解释器固定为安装时的环境（推荐 `uv tool install JiuwenMemory[local]`），不随拉起方的 `sys.executable` 变化。
- `service.json` 带协议版本：客户端版本不匹配时，服务空闲则重启为新版本，否则报错提示。

### D7：生命周期——开启 watchdog 时默认常驻

- 客户端经 `POST /local/lease` 登记租约并定期续约；JiuwenSwarm 退出只释放自己的租约，已被服务接受的写入继续完成。
- **文档记忆默认开启 watchdog，因此服务默认常驻**，不做空闲退出；关闭 watchdog 且无 dreaming 时，才在无租约、无在途请求、无 Portal 会话满 10 分钟后退出。
- 退出顺序：停止准入 → 排空在途请求与后台任务 → 释放 Registry 与 dreaming 锁 → 关闭存储 → 删除发现文件；排空期间到达的连接收到"服务正在退出"，由客户端重新拉起。
- 补 watchdog **启动对账**：服务启动时比对 md 文件与影子索引，补齐停机期间的手改；另提供 `service install` 注册 launchd / systemd user / Windows 计划任务实现开机自启，缩短空窗。
- 崩溃时文件锁随进程释放，下次使用重新拉起。dreaming 若使用 KV TTL 锁，崩溃后需等租约（默认 30 秒）过期才能恢复，拉起逻辑须把这类启动失败当作可重试。卡死不会释放锁，需要 `service stop --force`。

### D8：宿主 hook——服务做接续判断，宿主只做事件转换

```
Codex hook 命令 ────┐
DSH Cordis 插件 ────┼──▶ /local/hook/recall、/local/hook/capture ──▶ MemoryAPI
JiuwenSwarm 插件 ───┘     （解析连接、选择绑定、召回预算、写入过滤、幂等与恢复）
```

**职责边界**（三家一致，后续宿主复用同一套接续语义）：

| 宿主适配器负责 | 服务负责 |
|---|---|
| 读取宿主事件，取出宿主会话 ID、轮次 ID、用户文本、最终回答 | 按**认证主体**解析连接；请求里的 `connector` 只核对，不能指定 |
| 按宿主要求的格式交付召回结果 | 选择该会话已授权、仍有效的绑定；多个候选时要求显式选择 |
| 转发用户的任务选择（工具调用或 Rail 传入的 task_id / binding_id） | 校验选择属于本连接且仍有效 |
| 失败时不阻断对话 | 执行 D9 过滤、幂等写入、回执与恢复 |

JiuwenSwarm Provider 在本机模式下也调用这两个端点：Rail 传入的 task_id / binding_id 作为显式选择交给服务校验，Provider 不再自己维护一套找任务规则。

**recall**

- 入参：`{host_session_id, turn_id, prompt, project?, selection?, duty?, top_k?}`。
- **目标项目**按以下顺序确定，服务对结果做项目授权校验：
  1. 宿主显式传入 `project`（JiuwenSwarm 的 Rail 已传项目 Scope）；
  2. 未传时，若该安装在 `connect` 时**固定了唯一项目**，用它；
  3. 连接可用多个项目且未指定时，不猜测：返回"需要选择项目"，本轮不召回任务背景、不建待写记录。
  任务查找、待写记录与操作记录的键都包含项目：`{连接, 项目, 宿主会话, turn_id}`，同一会话 ID 在不同项目下互不影响。
- `duty`、`top_k` 原样转给 `search`，缺省取连接配置的默认值；保留 JiuwenSwarm 现有接续 `prefetch` 的参数与**结构化结果**（`items`、`paths`、`gaps`、`view_meta`）。宿主需要文本时由适配器渲染，服务不把结构压成文本。
- 服务按"本连接 + 项目 + 宿主会话 ID"精确 `continuity_task find`：
  - **恰好一个**有效绑定：`search(task_id=…)` 返回任务背景与相关记忆；
  - **多个**：返回候选清单、不召回任务背景，提示用户选择；选定前本会话不写入；
  - **没有**：只返回普通召回，附"本会话未绑定任务，本轮不会保存"，并附按描述查到的候选任务（须用户确认后绑定，见 D13）。
- 召回限定条数、字节数和耗时，注入内容标记为检索资料而非指令。
- **待写记录**：只有同时满足「本连接 `capture=task`」且「本轮已确定唯一有效绑定（自动唯一命中或用户已选定）」时，服务才把本轮持久化到自己的 SQLite（带过期时间）：`{连接, 项目, 宿主会话, turn_id, task_id, binding_id, 用户文本}`，服务重启后仍可用。`capture=off`、未绑定、多候选未选定、项目未定时**不保存用户文本**，也不建待写记录；召回用到的 prompt 只在内存中处理。
- **同一轮的待写记录只建一次**：用 `{连接, 项目, 宿主会话, turn_id}` 原子创建；同轮重复 recall 不覆盖已有记录中的绑定与用户文本，本轮已冻结后再改选择只对下一轮生效。

**capture**

- 入参：`{host_session_id, turn_id, project?, assistant_text, tool_notes?}`；项目按 recall 的同一规则确定。
- 服务取出本轮待写记录，与最终回答拼成一轮，按 D9 过滤后写入**该记录里的** task_id / binding_id，不重新查找。
- **冻结本轮内容**：发起写入前，用 `{连接, 项目, 宿主会话, turn_id}` **原子创建**操作记录，并保存冻结请求的**内容摘要**（覆盖正文、Scope 与 `continuity` 参数）。并发的两个 capture 只有一个能创建成功；之后同轮的 capture：
  - 摘要相同：复用已有操作（返回原结果或继续推进）；
  - 摘要不同（同一轮第二次 capture 带来不同回答）：返回**冲突**，不覆盖、不当作成功。这与 S11"同键异内容返回冲突"一致，避免本地层吞掉内核本该报告的冲突。
- **发起写入前**，先持久化本轮的**操作记录**，分两部分：
  - **操作关联**（不含正文）：`{连接, 项目, 宿主会话, turn_id} → {本地操作 ID, 原安装 ID, 原主体, task_id, binding_id, 事件 ID, 回答摘要, 状态, 内核回执（operation_id、refs）}`，保留到回执过期之后，用来按会话和轮次找回原操作。**本地操作 ID** 是稳定标识，供命令行查询这条本地记录；
  - **原写入请求**（完整 `add` 参数：正文、Scope、`continuity`）：保留到**终态**（已提交或已拒绝）为止，因为 S11 要求 partial 用原写入请求重试才能完成任务背景关联，只有 ID 不够。另设最长保留期（可配置），超期仍未到终态则删除正文。
- 状态：`已准备`（已落盘，`add` 可能还没调用）→ `已提交` / `partial` / `unknown` / `已拒绝`；超期未到终态记为 `已过期`；后台恢复时权限已失效记为 `已停止（权限失效）`。
- **服务自己推进非终态操作**，不依赖宿主重试：启动时和定期扫描 `已准备` / `partial` / `unknown`，用原写入请求按 S11 处理——`已准备` 直接以原事件 ID 重放（同键同内容幂等，即使上次其实已调用也不会多写）；`partial` 与 `unknown` 按回执的 `retry_action` 重试原请求或先 `continuity_recover` 再重试。
- **后台恢复以原安装的身份、按当前权限执行**：每次推进前重新校验——原安装的令牌未撤销、原主体仍存在、对该项目仍有 WRITE、原绑定仍有效。通过后用原主体构造安全上下文，走与普通请求相同的 PEP；**不沿用落盘时的授权结论**。服务只持有令牌摘要，因此这条内部路径按"安装 ID → 主体"查令牌登记并检查撤销状态，不经网络认证。校验不通过时：
  - `已准备`：本地没有回执，但**内核可能已执行**（例如内核已部分写入、服务在保存回执前退出）。因此不能只查"是否已提交"，而要按原操作的事件键**只读查询内核回执**，按结果处理：
    - 内核已提交：记为 `已提交`，补存回执；
    - 内核为 partial / unknown：按下一条处理（停止推进、保留回执）；
    - 内核确认**从未执行**该事件键：记为 `已拒绝（权限已撤销）`，删除原请求，不写入；
    - 无法核实（查询失败、内核不提供该查询）：保持 `未确认`，不推进、不删除原请求，直到最长保留期。
    这个只读查询不能用"重放写入"代替（撤权后重放本身就是越权写入），需要内核提供按事件键查询回执状态的维护接口，只供服务内部使用，不进 Agent 工具清单；该接口作为跨模块变更随 S11 一并修订。
  - `partial` / `unknown`（可能已有部分副作用）：权限仍有效时按回执的 `retry_action` 推进（原写重放或先 `continuity_recover` 再重试）；权限已失效时停止自动推进，记为 `已停止（权限失效）`，**保留内核回执**（`operation_id`、`refs`）供核对，原请求按最长保留期清理；对外**不得**报告为"未写入"或"已拒绝"。
  - **网络异常、409、5xx 是临时失败**：只做只读回执刷新并留待下轮，不得与 401/403 或缺失令牌走同一个终止分支。已过期的请求转 stopped 时必须保留原回执的 `operation_id`/`refs`，不能把它们清空。
- 是否写入只看**本轮绑定是否仍有效、本轮选择是否被更换**，不看任务修订号（其他宿主加入同一任务也会使修订号变化，原绑定仍有效）。收到 capture 时**先查操作记录，再看待写记录**：

  | 情况 | 结果 |
  |---|---|
  | 已有操作记录且已提交，回答摘要相同 | 返回"已提交"，不再写；回显字段按下方"三条路径分别鉴权" |
  | 已有操作记录，回答摘要不同 | 返回冲突，不写、不覆盖 |
  | 已有操作记录，状态 `已准备` / `partial` / `unknown`，原请求仍在 | 按上条重新校验权限后用原请求推进，返回推进后的结果 |
  | 已有操作记录，状态 `已过期`、`已停止（权限失效）` 或 `未确认` | 返回"**未确认，无法自动重放**"，附本地操作 ID 与可用的回执字段，下一步按实际字段给出（见下） |
  | 已有操作记录且已拒绝 | 返回原拒绝原因 |
  | 无操作记录、有待写记录，原绑定仍有效、选择未变（含 recall 后服务重启） | 照常写入；事件 ID 固定，重复触发只写一次 |
  | 无操作记录、有待写记录，但本轮绑定已解除、任务已关闭或会话中途换了任务 | 拒绝写入并说明原因，**不写到其他任务** |
  | 无操作记录、无待写记录 | 返回"未写入" |

  "未写入"只用于**确认从未尝试提交**的情况。原写入请求只在 `capture=task` 且已绑定时产生，内容与即将写入的事件相同，保留它不扩大落盘范围。

  **未确认时的下一步**（命令行 `jiuwen-memory op show <本地操作 ID>` 按回执的 `retry_action` 与实际字段给出，不只看"有没有回执"）：

  | 原请求 | 回执 | 下一步 |
  |---|---|---|
  | 仍在，权限有效 | `retry_action=retry_original_write` | 按原请求重试 |
  | 仍在，权限有效 | `retry_action=recover_then_retry` 且 `refs` 非空 | 先 `continuity_recover`，再按原请求重试 |
  | 任意 | `operation_id` 存在且 `refs` 非空 | 可经 `continuity_recover` 核对 |
  | 已过期 | 没有回执，或回执 `refs` 为空（如 unknown 尚无已确认引用） | **只能查询状态**，不能走事件恢复，也不能自动重放 |

  S11 的事件恢复要求 `operation_id` 与非空 `refs` 同时具备，缺一不提示 `continuity_recover`。

  **三条路径分别鉴权**：服务为判断"是否已写入"保留回执是内部需要；把回执里的内容**交给调用者**时，必须按调用者的**当前**权限裁剪。

  | 路径 | 调用身份 | 无当前项目读权限时 | 有当前读权限时 |
  |---|---|---|---|
  | 同轮 capture 重放 | 发起 capture 的安装 | 只返回状态（已提交 / 未确认 / 冲突），不回显正文、`refs` 或 `operation_id` | 另返回 `refs` 等引用 |
  | `op show` | 已认证服务端按安装令牌核验 | 只返回本地操作 ID、状态；无当前项目读取权时不回显事件/回执 ID、任务、绑定与引用 | 有读取权时另返回事件 ID、真实内核回执 ID、任务、绑定与引用 |
  | 人工恢复（`continuity_recover`） | 命令行使用的安装令牌 | 不提供 | 仅当调用者满足 S11 的恢复权限（相应来源身份及记录修改权）且 `operation_id`、非空 `refs` 齐全时才提供 |

  `continuity_recover` 会推进内核回执状态，属于写操作，不能用作撤权后的只读查询；只读核对使用前述服务内部的回执查询接口。

**各宿主适配**

  | 宿主 | 召回 | 写入 | 交付物 |
  |---|---|---|---|
  | JiuwenSwarm | `prefetch` | `sync_turn` | Provider 本机连接模式，经两个端点读写 |
  | Codex | `UserPromptSubmit` → `additionalContext` | `Stop`（async）；首版不注册 `PostToolUse`（工具操作记录留待后续） | `jiuwen-memory hook codex <事件>`，只依赖标准库以压低启动耗时 |
  | DSH | `system-prompt/assemble`，需实测是否每轮可拿到当前问题，备选 `agent/pre-step` | `turn/end` + `user/message`（只取人发的 `source`） | npm 插件，服务不在时调用 `jiuwen-memory service ensure`；锁定 DSH 版本，desktop 与 tui profile 都要安装 |

- hook 失败一律**不阻断对话**：召回超时返回空；写入失败记为"未确认"，不得显示为已保存。
- Codex 自带 `memories` 功能，`connect codex` 时提示可关闭，避免两套记忆同时注入。

### D9：自动写入的范围与开关

| 内容 | 处理 |
|---|---|
| 用户本轮文本 | 写入 |
| 最终回答 | 写入，超过 8 KB 截断并标注 |
| 召回时注入的记忆 | **必须剔除**，否则循环放大 |
| 系统提示、宿主自动注入（文件变更通知、AGENTS.md、skill 内容等） | 不写 |
| 思考过程 | 不写 |
| 工具调用 | 有工具事件时只写一行操作记录（工具名、命令或文件名、成功/失败），不写输出 |
| 疑似密钥 | 尽量过滤，不承诺过滤干净 |

- 写入形式：绑定任务时写成该任务的事件（`add` 带 `continuity`，`kind=statement`），保留原文；事件 ID = 连接 + 宿主会话 + 轮次，重复触发幂等。
- **未绑定任务不写。** 绑定流程与授权见 D13。
- 开关三档：`off`（只召回）/ `task`（只写已绑定任务）/ `all`（未绑定也写并抽取个人记忆，以后再做）。`connect` 默认 `task`，生效前按下表向用户说明数据去向并确认一次。

**数据去向**分三类，按实际配置提示，不笼统承诺"不离机"：

| 去向 | 何时发生 | 说明 |
|---|---|---|
| 本机持久化 | 写入时；以及 D8 的待写记录（仅 `capture=task` 且已确定绑定） | 原文与派生内容存在数据目录 |
| 记忆服务出站 | 任何**实际启用且会收到查询或正文**的远程组件：Embedder（向量化写入内容与查询）、LLM（派生抽取、分类、去重、查询改写、LLM Reranker）、远程 Reranker（`api`）、多模态 ASR / VLM 等 | JiuwenSwarm 默认配置的 Embedder 是远程服务，影子索引也引用它，因此**关闭派生抽取仍会把文本发给 Embedder** |
| 宿主模型出站 | 召回内容注入宿主后，随提示词发给宿主所用模型 | 由宿主配置决定，记忆服务控制不了 |

- 出站说明**由装配结果生成**：遍历所有已声明命名空间及已配置的插件类别（存储/控制命名空间除外，不是固定四类）；无声明的类别显示 `unknown`，实例级 `params` 覆盖全局端点，端点无法解析也显示 `unknown`。
- 每个组件的去向分三种：**已声明出站**（列出端点与内容）、**已声明不出站**、**未声明**。首版本机模板实际启用的内置组件随本版提供声明；第三方插件未声明数据去向时显示"去向未知"，不能当作不出站。
- 只有所有组件都是"已声明不出站"时，才可以对用户说"记忆服务不向外发送原文"；存在任何"去向未知"时不得作此承诺。`connect` 在第 5 步确认连接可用后、写宿主配置之前展示这份清单并等待确认；取不到清单时提示"清单不可用"，不能表述为"不向外发送"。
- 第三类单独提示：召回会把记忆内容带进宿主的模型请求。

### D10：MCP 桥补齐

- `continuity/mcp.py` 去掉对 `AGENT_MEMORY_URL` 的硬要求：未配置时走 D6 的发现与拉起，凭据读安装目录的令牌文件；配置了则保持远程模式。
- 补齐 `add` 与 `search` 工具，原样透传 409 回执（`operation_id`、`status`、`refs`、`retry_action`），不压成 `rejected`。工具清单按模式生成：只有本机模式（`connection="local"`）追加 `add`/`search`，显式远程模式的工具与行为保持不变。
- 不支持或未开启 hook 的宿主只经此桥显式调用；宿主接入的默认方式与 hook 开关见 D14。
- **只开放参与类操作**：MCP 工具与 hook 只提供查找、查看、为自己绑定 / 解绑、写入事件、检索与恢复。关闭任务、为其他连接建绑定或解绑、挂必需背景（`attach`）这类会影响其他参与者的操作不进入 Agent 工具清单，只在命令行与 Portal 提供，避免模型误判"已完成"或被注入内容诱导执行。
- 限制落在**实际调用路径**：现有桥按工具名分发、`continuity_task` 的 `operation` 是参数，因此在本机模式下桥与服务端都要按 `operation` 校验，拒绝管理类操作；不能只靠工具描述里不提。显式远程模式（配置了 `AGENT_MEMORY_URL`）保持既有工具与行为不变，避免影响已有部署。
- Portal 的关闭、解绑等管理操作走独立的管理入口，由服务端按 D13 的 owner / 管理员规则鉴权，不复用 Agent 的参与类入口。

### D11：与 Agent MCP 分支的关系

xwh 的 `codex/role-memory-mcp-dual-transport` 分支（`b9b2d1cd`、`4e39c533`，截至本文日期未合入 `mem2.0`）提供单进程承载 HTTP、Portal、Agent MCP 的统一服务，以及服务端维护 task / binding 状态的 5 个 `memory_*` 工具。

- 本特性**不依赖该分支**，只基于 `mem2.0` 已有代码。

### D12：已有 JiuwenSwarm 用户的切换流程

新数据目录默认是空的，所以已有用户必须走一次显式切换：`jiuwen-memory migrate jiuwenswarm --config <原配置>`。**首次启用本机模式时强制执行**，不能在后台静默完成。顺序是：**先识别、列出损失并取得确认，再提示退出旧进程**，最后接管。

1. **识别旧存储、身份与授权。** 从原配置和旧数据中逐项解析：

   | 核对项 | 内容 | 来源 |
   |---|---|---|
   | 认证主体 | 旧 `security_provider` 给出的完整五维 actor | 见下方"身份来源"，**不能只从 `--config` 取得** |
   | 记录 Scope | Provider 绑定的五维 Scope，以及各请求实际使用过的项目 Scope | 构造参数与配置给出基础 Scope；接续请求的项目 Scope 逐请求传入，需从 Registry 中的任务所在空间和旧宿主提供的清单补齐 |
   | 原连接 | Registry 中已有绑定引用的 `connector_id` 及其 actor | Registry 与原连接配置；连接名和 actor 都要原样登记，原绑定才能继续写入 |
   | 授权（空间成员、内容与治理权限） | 原主体在各空间的角色与授权 | **只来自原权限存储或可信导出**，见下 |
   | 存储 | Markdown 根目录、影子索引、各 KV / Registry / 权限 / 审计的后端类型与路径 | 原配置 |

   **身份来源分三种情况。** SDK 的主体由宿主在运行时经 `security_provider` 注入，配置文件里通常没有；任务 owner 只存完整 actor 的指纹，无法反推出五个维度。核对分两层：先凭可信来源**确认主体**，再**逐条**核对它声称拥有的旧任务。

   | 情况 | 取得方式 | 结论 |
   |---|---|---|
   | 可从配置直接取得 | 配置中显式写有 actor（例如可信连接配置里的 `actor`） | 主体视为已确认，可登记 |
   | 需旧宿主提供 | 由旧 JiuwenSwarm 在退出前调用 `security_provider()` 导出当前 actor，交给迁移命令（`--actor-from-host`，经宿主侧一次性导出） | 主体视为已确认，可登记 |
   | 无法核实 | 两者都拿不到 | **不登记该主体**；在第 2 步列出具体缺口：哪些个人记忆、任务与绑定无法延续 |

   主体确认后，对声称由它创建的旧任务逐条比对 owner 指纹：一致的任务延续 owner 管理权；对不上的**只影响该任务**，在第 2 步列为"owner 身份无法延续"，不影响主体登记与其他任务。

   主体登记以可信配置或旧宿主的认证上下文为依据。对声称由该主体创建的旧任务，逐条核对 owner 指纹后才确认管理权延续。只有个人记忆、尚未创建任务或仅参与他人任务的主体，也可凭可信来源登记；保留其原有授权。

   **授权不从任务与绑定推断。** Registry 只能证明某连接曾参与某任务，不能证明迁移时它仍有哪些内容或治理权限、授权是否已被撤销。因此：
   - 原权限存储是持久的（例如 SQLite 权限库），原位打开，授权照旧生效；
   - 原授权只在内存里、且没有可信导出时，**不重建**。列出受影响的空间（Registry 中出现过、但没有授权来源的空间），切换后由有授权能力的身份（项目管理员）显式重新授予；
   - 绑定记录照常保留，但没有对应授权时，该绑定不能用来读写。

2. **列出损失并确认。** 把第 1 步与下表汇总为"切换后将失去的数据与权限"展示给用户：无法核实的 actor 及其影响的任务与绑定、原 actor 无法登记为本机令牌主体（例如不符合主体登记的维度约束）、需要重新授予的空间、无法恢复的内存数据。用户确认后才进入下一步。

   | 数据 | 默认配置下的位置 | 切换后 |
   |---|---|---|
   | 文档记忆正文 | Markdown 目录 + 影子索引（持久） | 原位打开，不复制 |
   | 接续任务与绑定 | SDK 接续要求的 `fixed_path` SQLite Registry（持久） | 原位打开 |
   | 对话原文 `/messages/` | `kv_store.default: memory` | **不可恢复**；它只用于抽取时的上下文，不影响已有记忆 |
   | 空间成员与授权 | 内存 KV / 默认权限存储 | 持久则原位打开；只在内存时**不可恢复**，默认空间由 `init` 重建，其他空间需显式重新授予 |
   | dreaming 注册 | 内存 KV | **不可恢复**，需重新注册 |
   | 审计 | `:memory:` | **不可恢复** |
   | 已显式配成持久的其他存储 | 原配置路径 | 原位打开 |

   只在内存里的数据，旧进程一退出就无法恢复，只能在此时由旧进程导出。旧 Provider 目前没有导出接口，因此首版对默认配置用户只能如实列为丢失；导出接口列为遗留。
3. **退出旧进程并做共存检测。** 确认后提示用户退出 JiuwenSwarm，再检查原 Registry 写锁、文档实例锁（`claim_instance`）和数据目录锁；仍有进程内 Runtime 持有任一把锁时拒绝继续。
4. **服务接管。** `service.yaml` 原位引用第 1 步识别出的持久文件，不复制；路径无法原位使用（例如在其他用户目录）时才复制，并保留原文件。
5. **Scope 两条路径分别处理。** 本机模式下，普通读写和接续调用都按 **SDK 五维直映射**传 Scope，不使用 `_HttpClient._scope_payload` 的身份改写；接续调用本来就原样透传 payload，保持不变。远程 HTTP 模式的现有映射不改。
6. **核对。** 切换后用原主体、原 Scope 抽查：能读切换前的个人记忆与任务事件；能以原 owner 身份管理任务；能沿原绑定继续写入。原配置包含独立证据图、非默认职责策略或多个项目时，角色模式还要核对至少一条原关系和一次原职责查询，每个项目各抽查一次。结果写入切换报告。
7. **失败回退。** 核对未通过时，停止新服务并释放全部写锁（Registry、文档实例、数据目录），本机模式保持未启用；`service.yaml` 只原位引用原文件、不修改它们，原宿主可直接以原配置重新启动。切换报告写明失败项与当前写锁持有方（"无"或某个进程）。

- 迁移把旧存储**映射到实际装配项**：`document_root` → `markdown_store.default.params.root`，`registry_store` → `kv_store.registry.params.db_path`，`data_dir` 的 `kv.db`/`shadow.db`、权限库分别映射到对应 SQLite 装配项；旧路径另存 `local.legacy` 供追溯。
- 迁移目标 connector 必须与**已确认的宿主 actor** 唯一匹配，并优先限定在本次启用且 projects 覆盖目标项目的候选内；禁用条目或项目不相交的条目不参与选择。剩余候选仍不唯一/无匹配时在签发令牌前报错，绝不取旧配置里的第一个 connector。其他 connector 的 actor、projects、enabled 原样保留。
- 迁移令牌以已确认的完整 actor（含 space/session）登记，任务 owner 指纹与原绑定才能继续匹配；普通安装仍禁止 space/session。
- `space recover-admin` 不提升日常令牌：命令行写一次性口令，运行中的服务调用同一 `space` 组件的成员维护接口（同一 KV 存储）并失效空间事实缓存；双重确认、写 `data_dir/audit.log`。
- 核对在迁移前从旧 Registry 按任务所属主体采样 task / binding / unit ID：记录迁移前 owner，事件样本按关联 task 补齐 owner；迁移后比较同一任务的 owner 是否变化。其他 agent 合法持有的任务不可读时跳过；owner 未能解析的 403 只能算"未能验证"，必须由当前主体的读取后备探针补证。写入探针放在单独的 `migration verification task` 中（建任务、绑定、写入、读取当前 revision、关闭并检查结果），清理失败会使迁移失败，不留下"报告成功但活动任务仍在"的状态。没有当前主体可读样本时要求检索非空，空结果不再算成功。

### D13：跨宿主接手任务的授权与绑定

**现状的阻碍**：现有契约下，除 create / get / find 外的任务操作都要求调用者是任务 owner（`continuity_task` 的 owner 校验），写入事件还要求绑定的连接就是调用者自己。于是"JiuwenSwarm 创建任务后退出，Codex 用独立主体接手"这一核心场景走不通：Codex 不能给自己绑定，owner 已离线；owner 事先替它绑定也不行，因为 Codex 新会话的 ID 事先不知道。

**决策：连接自绑定授权策略默认开启（与现行接续端口一致），可显式关闭；本机服务模板写明 `self_bind: true`。**

- 配置 `continuity.default.params.self_bind`（名称以实现为准）：默认开启，与现行接续端口一致——参与者只能通过自己的连接自绑定/关闭，连接有效性在提交时重新校验（owner 绑定校验、连接启用与项目覆盖、绑定是否为本人）；显式设为 `false` 才退回「只有 owner 能改任务」的严格模式。**已有的 HTTP / SDK 部署默认行为不变**。
- 本机服务模板显式写入 `self_bind: true`（与默认值一致，便于审阅）。
- 开启后：调用者具备该项目 WRITE 权限，且 `bind` 请求中的 `connector_id` 正是调用者自己的连接时，可把**自己的宿主会话**绑定到该项目的开放任务。
- 不变的部分：
  - 为**其他连接**建绑定仍只有 owner 可以（另见下方管理员策略）；关闭任务只允许该任务的有效绑定持有者或 owner，绑定在提交时重新校验；
  - 解绑：owner 可解除任何绑定，连接只能解除自己的绑定；
  - 绑定仍只是"这个会话参与该任务"，不授予任何原记忆的读取权限（S11 不变量 2）。

**另一项策略：空间管理员可管理任务。** 现有规则只认 owner 指纹，项目管理员也绕不过；创建任务的 Agent 被卸载或撤销后，任务就无人能关闭、解绑或整理。

- 新增配置 `continuity.default.params.admin_manage_tasks`（名称以实现为准），默认关闭，关闭时与现行规则一致；本机服务模板开启。
- 开启后：对该项目具备 `MANAGE_SPACE` 的主体，可对空间内任务执行 owner 才能做的操作（关闭、为其他连接建绑定或解绑、`attach`）。这些管理操作只要求 `MANAGE_SPACE`，**不要求项目 WRITE**；反过来，只有治理权限的管理员不能借此写入事件，写入仍要求 WRITE 与有效绑定。
- 管理员是谁见 D4；这些操作按 D10 只经命令行与 Portal 提供，不进 Agent 工具清单。
- 绑定使用**接手方自己的凭据**：Codex 经 MCP 工具 `memory_continuity_task(bind)`，或用户运行 `jiuwen-memory task bind --host codex`（使用该安装的令牌）。
- 流程：recall 发现未绑定时，附上按描述查到的候选任务；用户确认后才绑定。不按标题自动合并（S11 不变量 3）。
- 同一会话命中多个任务时，要求用户显式选择；选择由服务按"连接 + 项目 + 宿主会话"保存，本轮及之后的 capture 都沿用选定的 task_id / binding_id（D8）。

**为什么不选其他做法**：
- *只支持 owner 预绑定*：核心场景直接不成立，且 owner 无法预知接手方的会话 ID。
- *全局放开自绑定*：会让所有既有部署的项目写成员都获得新权限，超出本机形态的范围。
- *委托授权*（owner 事先签发委托，接手方凭委托绑定）：要定义委托的签发、范围、过期与撤销，首版成本过高；可作为对项目成员权限更严格的部署的后续选项。

这是跨模块契约变更：实现时在 S11 的 `continuity_task` 授权说明中新增这两项策略及默认值，写明关闭时与现行规则一致；并在角色记忆 F11 中说明理由。

### D14：宿主接入分层——MCP 默认，hook 可选

**接入分两层，所有宿主共用同一个本机服务与同一套接续规则：**

| 层 | 作用 | 默认 |
|---|---|---|
| MCP（基础层） | 连接、自动拉起服务、任务查找与自绑定、检索与保存，由模型经工具调用 | 所有宿主开启 |
| hook（增强层） | 每轮自动召回、自动写入，不依赖模型调用工具；走 D8 的 `/local/hook/*` | 按宿主区分，见下表 |

**默认开关的规则**：宿主自带配置级 hook、只改配置文件、且已在本机核实事件的，默认开启；需要安装我们的代码插件，或事件尚未核实的，默认关闭，用户确认后才开启。

| 宿主 | MCP 写入位置 | hook 的实现 | hook 默认 | 原因 |
|---|---|---|---|---|
| Codex | `~/.codex/config.toml` 的 `[mcp_servers.jiuwen-memory]` | `hooks.json` 登记 `UserPromptSubmit` / `Stop` 命令（配置级） | **开** | 只改配置；0.166.0 已核实事件 |
| DSH | profile 配置中的 MCP client 条目（`dsh-mcp-client`，确切结构以 `dsh --dump-config-schema` 为准） | Cordis 插件（`jiuwen_memory_adapter/deepseek_harness/`） | 关 | 需安装代码插件；开发者预览版，插件接口随版本变，desktop 与 tui 两个 profile 分别安装 |
| Hermes | `~/.hermes/config.yaml` 的 MCP 段（每个 profile 一份） | `MemoryProvider` 插件 | 关 | 需安装代码插件；且 Hermes **同时只能启用一个外部记忆插件**，开启会替换用户现有的插件 |
| WorkBuddy | 按版本探测：社区版 `~/.workbuddy/mcp.json`，企业版 `~/.codebuddy/.mcp.json`；探测不到即报错，不猜 | 宿主自带 hook 配置（待实测） | 关 | 是否有"发言前""回答后"事件未证实；实测确认后可按配置级 hook 规则改为默认开 |
| JiuwenSwarm | —（原生记忆插件） | 原生插件 `prefetch` / `sync_turn` | 始终开 | 现状不变 |

- 用法：`connect <宿主>` 按上表默认；`--hooks` / `--no-hooks` 覆盖默认；已连接的安装用 `jiuwen-memory hooks enable|disable|status <宿主>` 切换。安装记录新增 `hooks` 字段，开关同样按安装 ID 幂等、可续做、可回滚（D5）。
- 需要安装插件的宿主，开启前展示"将安装插件"并确认；Hermes 检测到已有其他外部记忆插件时，额外提示"将替换 `<原插件>`"，用户确认后才切换，关闭时恢复原设置。
- **MCP 工具说明随 hook 状态变化**：hook 开启时说明"背景已自动注入，需要时再调用"，减少重复查询；只有 MCP 时说明"开始任务先查背景，得出结论后保存"，提高模型主动调用的概率。MCP 桥从安装记录读取 `hooks`。
- 两层同时开启不重复：hook 写入的是本轮问答原文（任务事件），MCP 工具写入的是模型整理的结论；查任务、权限、去重均由服务统一处理。
- 新增宿主只需新增 MCP 写入器（必选）与 hook 写入器（可选），按现有写入器注册表扩展，不在核心代码中按宿主名分支。

**安装实例：宿主名不足以标识要接入的对象**

同一宿主可能有多个实例：Hermes 的多个 profile、WorkBuddy 的社区版与企业版、企业版的用户作用域与项目作用域、DSH 的 desktop 与 tui profile。一个**安装**对应一个实例，各有自己的主体、令牌和配置条目。

- 安装记录新增 `instance`：`{kind, config_root, profile?, edition?, scope?, project_root?}`，其中 `config_root` 存**规范化后的真实路径**（解析符号链接）。同一宿主的两个实例是两个安装，不共用凭据。
- 选择规则（`hooks`、`sync`、`disconnect` 等所有按宿主操作的命令一致）：
  - 该宿主只有一个有效安装时，可以只写宿主名；
  - 有多个时，必须用 `--install <ID>`，或用 `--profile` / `--edition` / `--scope` 唯一确定；否则报错并列出候选，不默认选第一条。
- `connect` 按实例去重：同一实例重复 `connect` 续做原安装，不同实例新建安装。
- Hermes 的外部记忆插件绑定**初始化它的 profile**，因此 hook 也按 profile 开关；同一 profile 内只替换该 profile 的 `memory.provider`。DSH 的两个 profile 分别是两个实例，hook 插件分别安装。

**已有安装的升级**：旧安装记录没有 `instance`，升级时按"优先保留原身份与绑定"映射，不能唯一映射时让用户选择。

- Codex、JiuwenSwarm：只有默认实例，旧安装直接补上 `instance`（默认配置根），令牌、连接、任务绑定原样保留。
- DSH：旧安装一次管理 desktop 与 tui 两个 profile。按宿主配置中实际存在本安装条目的 profile 判断：
  - 只有一个 profile 有条目：旧安装映射为该 profile 的实例，令牌、连接、任务绑定与该 profile 的插件条目都归它；
  - 两个都有：提示用户选择哪个 profile 继承原身份（任务绑定只能跟一个连接走），另一个 profile 新建安装，其条目改记到新安装名下；非交互环境下不升级，`status` 报告"待选择"，原安装继续按旧方式工作；
  - 都没有：同样进入"待选择"——由用户指定哪个 profile 继承原身份；非交互环境下保留旧安装不升级，显式选择后再迁移。不按顺序自动分配，因为继承关系一旦生效，令牌与任务绑定的归属无法事后纠正。
- 升级只改安装记录与条目归属，不重签已有令牌、不改连接名，因此已有任务绑定继续有效。

**宿主配置的回滚按条目进行**：只删除本安装写入的条目；本工具新建的配置文件，只有在回滚时**仍只含本安装创建的内容**才删除整个文件，否则保留文件、只删条目，用户后来添加的其他 server 不受影响。

**宿主识别分三种状态**（以 WorkBuddy 为例，其他宿主同理）：

| 状态 | 判定 | `connect` 的行为 |
|---|---|---|
| 无法识别 | 找不到宿主的安装痕迹（应用目录、可执行文件、版本文件均不存在） | 报错"未检测到 WorkBuddy"，不创建任何文件 |
| 已识别，配置文件尚未创建 | 有安装痕迹，但 MCP 配置文件还不存在（干净安装） | 按该版本的格式**新建**配置文件并写入本工具条目；回滚规则同上，文件仍只含本安装内容时才删除整个文件 |
| 已识别，配置文件已存在 | — | 合并写入 |

WorkBuddy 企业版的 MCP 配置区分**用户作用域**（`~/.codebuddy/.mcp.json`）与**项目作用域**（`<项目根>/.mcp.json`），优先级为本地 > 项目 > 用户；`connect` 用 `--scope user|project`（项目作用域另需 `--project-root`）指定。

- server 名按安装唯一（`jiuwen-memory-<安装 ID 前缀>`），避免与用户已有条目或其他安装同名。
- 写入后校验**最终生效的条目**：按"本地 > 项目 > 用户"合并各作用域，确认生效的 `jiuwen-memory-*` 条目正是本安装写入的那条。若更高优先级作用域里有同名条目，报告"已写入但被 `<作用域>` 覆盖，未生效"，`connect` 不报告完成，由用户选择改写更高优先级作用域或移除冲突条目。

**能力声明**：每家宿主的写入器和读取器声明自己支持哪些能力，命令按声明返回明确结果，不静默忽略。

| 宿主 | MCP | 自动召回 | 自动采集 | 长期记忆导入 | 会话导入 |
|---|---|---|---|---|---|
| Codex | 支持 | 支持（hook） | 支持（hook） | 支持 | 支持 |
| DSH | 支持 | 支持（插件） | 支持（插件） | 不支持（无内置长期记忆） | 支持（v4 格式） |
| Hermes | 支持 | 支持（插件 `prefetch`） | 支持（插件 `sync_turn`） | 支持 | 待实测（`state.db` 结构） |
| WorkBuddy | 支持 | 待实测 | 待实测 | 支持（格式实测后） | 不支持（位置未知） |

- 对"待实测"或"不支持"的能力，`--hooks`、`--sessions` 等返回"该宿主当前不支持此能力"与原因，退出码区别于失败；MCP 接入与已核实格式的记忆导入不受影响，可单独交付。
- "待实测"改为"支持"的条件：选定一个可复核的宿主版本，留存脱敏的配置样例与事件或数据样例，并在真实宿主上通过验收——**宿主实际列出并调用了我们的工具**，或实际触发了 hook，而不只是配置文件写对了。
- Hermes 插件提供的不同回调分别对应不同能力：`prefetch` 对应自动召回，`sync_turn` 对应自动采集，`on_memory_write`（内置记忆写入的镜像）对应 D15 的镜像同步。

### D15：宿主记忆同步

指定宿主目录后，把宿主自己保存的记忆导入 agent memory；可反复执行，在崩溃和并发下结果一致。

**用法**

```
jiuwen-memory sync grant  <宿主> [--install ID] --dir <目录>... [--types profile,fact,daily_log] [--sessions] [--project <空间>]
jiuwen-memory sync        <宿主> [--install ID] [--dry-run] [--since 日期] [--limit N] [--mirror-deletes]
jiuwen-memory sync status <宿主> [--install ID]
jiuwen-memory sync recheck <宿主> [--install ID] [--op 操作ID]
jiuwen-memory sync resolve <宿主> [--install ID] --op 操作ID --action adopt|abandon|discard
jiuwen-memory sync revoke <宿主> [--install ID]
```

**1. 同步授权：把"读什么、写到哪里、谁能看"绑在一起**

同步授权是安装记录中的一份**授权单**，内容固定为：

| 字段 | 含义 |
|---|---|
| 来源根 | 一个或多个目录，存规范化后的真实路径（解析符号链接） |
| 数据类型 | `profile` / `fact` / `daily_log` / `session_turn` 中允许的子集；`session_turn` 需显式加入 |
| 目标空间 | 写入的项目空间，默认 `init` 创建的默认共享空间 |
| 可见人群 | 授权时目标空间的成员列表，**只是授权时的快照**，用于展示与审计，不限制后续访问 |
| 授权版本 | 每次变更加一 |

- 固定顺序：**展示来源范围、数据类型、目标空间及可见人群 → 用户授权读取 → 本地 dry-run → 用户确认写入**。dry-run 在授权之后，因为它本身就要读文件。
- **dry-run 只做本地工作**：读取、过滤、与账本比对，报告将新增、更新、替换、跳过、可判删的条数；**不调用 Embedder 或 LLM，不写入**。
- 授权展示特别标出 `profile` 类（如 `USER.md`）含个人信息，写入共享空间后，可见人群里的成员都能召回；用户可在 `--types` 中去掉 `profile`，或用 `--project` 改为只有本人安装可见的空间。
- **授权边界在打开文件之前落实**：读取器不能自己打开文件，只能通过服务交给它的**受限访问接口**枚举目录、打开文件。该接口在打开前解析真实路径，必须位于授权的来源根之内（符号链接跳出即拒绝），并按文件归属的数据类型核对授权；不满足就不打开，记入跳过清单。接口同时记录实际打开过的文件，供报告与验收核对。
- **扩大目录、加入会话、更换目标空间都要重新授权**（授权版本加一）；定期同步只在当前授权范围内执行，不能自行扩大。
- **在途操作与授权版本绑定**：
  - dry-run 产出的同步计划记录 `{安装, 授权版本, 目标空间}`，并**冻结用户看到的内容**：将新增、更新、替换的条目标识与源内容摘要，以及将删除（`--mirror-deletes`）的条目集合。确认写入时这三项必须与当前授权一致，否则要求重新 dry-run；
  - **执行前重算并比较**：执行时重新扫描，与冻结计划逐项比较条目标识、摘要和删除集合。有实质变化（要写入的条目内容变了、出现计划外的新条目，或删除集合不同）就停止执行，重新展示差异并确认；删除只针对用户确认过、且本次重算仍然成立的条目，新出现的删除候选必须再次确认；
  - 执行时在**开始读取前**和**每次提交前**核对授权版本；版本变化（撤销、扩大、换空间）后，尚未提交的批次全部停止，已提交的保留并如实报告；
  - 定期同步也在服务内部先做 dry-run 再提交计划，只是不向用户弹确认；提交前仍核对授权版本，撤权后不再提交。Hermes 镜像写入不经 dry-run，按授权单中已授权的策略独立执行，提交前同样核对授权版本。定期同步只有在授权时明确开启了镜像删除，才执行判删。
- `sync revoke`：撤销授权（授权版本加一）并停止定期同步；已导入的记忆默认保留。
  - 每份授权有一个**不变的授权标识**，授权版本在其下递增；账本每条记录都持久化导入时的 `{授权标识, 授权版本, 来源根, 目标空间}`。
  - 选择一并删除时，删除范围由用户在两者中明确选择：**当前范围**（只含当前授权版本的来源根与目标空间），或**全部历史**（这份授权历次版本导入过的全部来源根与空间）。确认界面按目录与空间分组列出实际涉及的记忆条数；非交互环境必须显式指定范围。
  - 例如先授权目录 A、再改为目录 B 后撤销：选"当前范围"只涉及 B 导入的记忆，选"全部历史"同时涉及 A 与 B。
  - 实际删除仍遵守第 4 节的统一删除条件，不满足的只解除账本关联。
- **空间后来新增的成员能读到已导入的内容**：空间授权按当前成员判定，授权单里的可见人群只是快照。`sync status` 展示当前成员与授权快照的差异，提示用户必要时撤销或迁移；成员变化不会自动触发重新授权。
- 读取授权与 `capture` 是两个独立开关。

**2. 读取器接口：给出稳定标识和扫描完整性**

```
宿主读取器（按宿主注册的插件）               本机服务（统一）
  scan(受限访问接口, 类型, 过滤) → 扫描结果 ──▶ 核对授权版本 → 过滤密钥 → 账本比对 → 写入 / 替换 / 判删 → 报告
  （打开文件前已由受限访问接口校验路径与类型）
```

- 读取器只实现一个入口 `scan`，入参是服务提供的受限访问接口（不是裸路径），返回**扫描结果**：
  - 导入条目：类型、正文、**稳定条目标识**、原始时间、声称作者、位置说明；
  - **完整性**：按"来源根 × 数据类型"逐个范围标明本次是否完整扫描成功；
  - **跳过清单**：哪些文件或范围被跳过及原因（读取失败、格式不支持、超出大小上限、被过滤条件排除）。
- **稳定条目标识**由三部分组成：`{数据类型, 逻辑集合, 集合内标识}`。
  - **逻辑集合**是条目所属的文件或宿主内的数据集合：如 Hermes 某 profile 的 `MEMORY`、`USER`，WorkBuddy 某天的日志文件（相对路径），Codex 的 `stage1_outputs`，某个会话。因此 `USER.md` 与某天日志里即使有相同文本，也是不同条目；两天日志各记一次同一事实，也是两条来源。
  - **集合内标识**：
    - 宿主自带稳定 ID 的，直接使用：Codex `stage1_outputs` 用 `thread_id`（该表每个会话一条记忆）；会话类来源用**会话 ID + 轮次或消息 ID**，单独的 `thread_id` 只够标识线程，不够标识轮次；Hermes `state.db` 用消息行 ID；DSH 用会话 ID + 轮次号；
    - 整个文件作为一个条目的（见下），集合内标识固定为文件本身，内容变化就是同一条目的更新；
    - Markdown 中逐条拆分、没有自带 ID 的条目，用**规范化正文的指纹**（去首尾空白、统一换行）。插入、重排不会改变已有条目的标识；**内容一改，就是一条新条目，旧条目按缺席处理**，不做"一消失一新增即替换"的推断。
  - **哪些按条目拆分**：`USER.md` 与 `MEMORY.md` 都按 Markdown 条目拆分，稳定标识为“类型 + 逻辑集合 + 规范化正文摘要”；这样镜像单条画像写入只更新该条，不会替换整份画像。升级前同步过的整份 `USER.md` 旧 `:file` 行在首次新扫描时按替换迁移。具体拆分方式随实测格式定稿。
  - 标识的作用范围包含来源根和 profile，所以相同正文出现在两个 profile 里，是两条合法的独立条目。
- 正文摘要只用于判断内容是否变化，不用于判断是不是同一条。
- 读取器只读，SQLite 的约束写成可验收的形式：**只读打开、有限等待（繁忙超时 2 秒）、在一个只读事务内读出一致快照；繁忙超时或格式不支持时，把该范围标为未完整扫描并报告跳过**，不阻塞宿主、不重试到超时为止。
- 读取器在服务进程中执行，CLI 经 `/local/sync`（需安装令牌）触发，定期同步和 Hermes 镜像复用同一入口。新增宿主只需新增读取器，核心不按宿主名分支。

**3. 导入什么**

| 类型 | 来源举例 | 默认授权 | 写入方式 |
|---|---|---|---|
| `profile` 用户画像 | Hermes / WorkBuddy 的 `USER.md` | 包含，授权时单独提示含个人信息 | 写为用户画像类记忆 |
| `fact` 长期事实与经验 | Hermes `MEMORY.md` 各条目、Codex `stage1_outputs.raw_memory`、`~/.codex/memories/` | 包含 | 已是整理过的事实，直接写入，不调用模型抽取 |
| `daily_log` 每日日志 | WorkBuddy `.workbuddy/memory/<日期>.md` | 包含 | 写为日志类记忆，保留日期 |
| 角色与行为设定 | WorkBuddy `SOUL.md` / `IDENTITY.md`、各宿主的 `AGENTS.md` | **不提供此类型** | 是给该宿主的指令，导入会影响其他 Agent |
| `session_turn` 会话历史 | Codex rollout、DSH 会话、Hermes `state.db` | 不包含，需显式加入 | 经抽取写入，一条来源可能产生多条记忆；只取用户与助手可见文本，过滤规则同 D9 |

- DSH 没有内置长期记忆，只能导入会话历史；会话为 zstd 压缩、带格式版本的事件流，读取器只支持已知版本（当前 v4），未知版本标为未完整扫描并报告。
- Hermes 条目的分隔方式、WorkBuddy 的目录结构须在选定版本上实测后定稿。
- 每条记忆带来源标记：`source_app`、来源根、稳定条目标识、源内容摘要、同步操作标识；原记录里的作者只作为"声称作者"保存，不当作已认证身份（与角色记忆 F11 第 8 节一致）。
- 本同步导入的是**个人记忆**，不绑定任务；把历史导入到某个任务仍走 F11 第 8 节的 `batch_add` + `continuity` 路径。

**4. 同步账本**

- 账本身份：`{安装, 来源根, 稳定条目标识, 目标空间}`，其中稳定条目标识已包含数据类型与逻辑集合。同一安装先后同步 A、B 两个目录的 `USER.md` 是两组记录；同一来源改导入另一个空间也是新记录，不会被旧摘要跳过。
- **来源与输出的关系**：两条来源即使正文相同，也各写各的输出、各自带来源标记，不主动合并。但内核去重可能让一次写入**复用既有单元**——它可能是另一条同步记录写的，也可能是早先由 MCP 或用户手工创建的记忆。因此每个输出要区分两种归属：
  - **本次同步创建**：单元由这次 `add` 新建。证据是单元创建时随单元原子写入、之后不再改动的系统元数据：`sync_created_by`（同步操作标识）与 `sync_initial_digest`（创建时的内容摘要）。合并到既有单元的写入不会改写这两个字段；
  - **复用既有单元**：`add` 返回的单元没有本批的 `sync_created_by`，说明是去重命中了已有单元。账本只记关联，**永远不因同步删除它**。
- **账本分两张表，归属记在输出上，来源只管引用**：
  - **输出记录**（每个单元一行）：单元 ID、**原始归属**（由同步创建 / 非同步创建）、创建它的同步操作标识（若由同步创建）、创建时的内容摘要、当前引用数。原始归属在第一次见到该单元时确定，**之后任何情况下都不改写**：单元自带本批 `sync_created_by` 即"由同步创建"，否则（去重命中了由 MCP、用户手工或其他途径创建的单元）为"非同步创建"。
    另设**删除保护标记**：一旦置上，以后任何同步路径都不得删除该单元。它与原始归属分开记录——原始归属回答"谁创建的"，用于审计与共享引用判定；保护标记回答"同步还能不能删它"。人工收尾放弃管理的产物（见下文 `abandon`、`discard`）置此标记，原始归属保持不变。
  - **来源记录**（每条来源一行）：源内容摘要、引用的输出单元 ID 列表、同步操作标识、授权标识与授权版本、状态、最后一次看到的时间。来源记录只增减引用，**不决定能否删除**。
- 例：来源 A 创建单元 U，来源 B 复用 U。U 的输出记录为"由 A 的同步操作创建"，引用数 2。无论先删 A 还是先删 B，都只是引用数减一；**最后一个引用解除时**才按输出记录判定，两种删除顺序结果相同。
- **统一删除条件**：替换清理、`--mirror-deletes` 判删、撤权清理、崩溃恢复，都在**单元的最后一个引用解除时**判定，必须**同时满足**：
  1. 输出记录的原始归属为"由同步创建"，且与单元自带的 `sync_created_by` 一致，并且**未置删除保护标记**；
  2. 引用数已为零；
  3. 单元自创建后未被修改，并且后端支持原子条件删除：比较预期摘要与删除在同一事务内完成。默认后端 `supports_conditional_delete()` 为 False，无法排除检查后到删除前的编辑，必须保留该单元并在待清理/报告中说明能力不足，不得退化为普通删除。
  内容已变、归属无法证明、后端缺少原子删除能力等确定性不满足：只解除关联，保留；能力不足不置永久删除保护，后端补齐能力后可再次清理。由 MCP 或用户创建的单元始终保留。
- 规则：
  - 新条目：写入；
  - 摘要不变：跳过；
  - 摘要变化（标识不变的条目：宿主自带 ID 的条目、整文件条目）：**替换**，步骤见第 5 节；
  - 逐条拆分的 Markdown 条目内容被改：新内容是新条目，照常写入；旧条目缺席，**严格按第 6 节判删**，默认保留。
- 旧输出在导入后被人工编辑过的，由统一删除条件第 3 条保留，报告中列为"已人工编辑，未改动"。

**5. 崩溃与并发下的一致性**

- **来源身份稳定，操作标识每次新生成**：
  - 来源身份就是账本身份（第 4 节），始终不变；源内容摘要只用于判断"未变化则跳过"。
  - **同步操作标识**标识的是"一次逻辑写入"，在进入 `writing` 前**新生成并持久化**（随机或单调序号，不由内容推导）。同一次写入的重试、崩溃后的恢复都沿用这个标识；这次写入完成后，哪怕内容又改回从前的值（如 `USER.md` 经历 A → B → A，或镜像删除后原文重新出现），也生成新的标识。
  - 原因：若标识由内容推导，A → B → A 的第三次写入会与第一次同标识，按旧回执恢复就可能登记一个已被替换清理掉的单元。
- **完成的依据是整批写入的返回结果**：一条来源对应一次 `add` 调用，`add` 正常返回的 `list[MemoryUnit]` 就是该批的输出清单；只有拿到这份清单并持久化，才算该条来源写入完成。**在目标空间里按同步操作标识查到了若干单元，不能证明整批已经写完**（例如一轮会话抽出三条，写完第一条就中断）。
- **账本状态机**：

  | 状态 | 含义 | 重启后怎么处理 |
  |---|---|---|
  | `writing` | 发出请求前已持久化同步操作标识、**写入意图**（新增或替换）与替换时待处理的旧引用；`add` 可能尚未发出、进行中、已部分写入或已完成 | 见下方"未完成写入的恢复"；不能证明未执行时按未知结果处理 |
  | `cleanup_pending` | 替换时新输出已写完并记下，**新旧两组引用都已持久化**，旧输出尚未清理完 | 对旧组逐个按统一删除条件处理（删除或只解除关联），处理完置 `ok`；可重复执行 |
  | `ok` | 完成 | — |
  | `retryable` | 仅用于明确可重发的来源（显式 `prepared` 或人工判定未执行）；缺回执本身不再产生该状态 | 下次同步重新写入；不阻塞空间清理 |
  | `unconfirmed` | 无法确认写入结果（回执探测不可用、失败或仍有已发现产物） | 不自动重写；按第 5 节"未确认操作的处理"由用户核对或收尾 |
  | `abandoned` | 用户已放弃该次写入（`resolve --action abandon / discard`） | 不再恢复；来源记录回到可重新写入的状态，下次同步按新的逻辑写入处理 |

- **写入步骤**：发出请求前先置 `writing`，同时持久化新生成的同步操作标识、写入意图（新增 / 替换）与替换时的旧引用 → 调用 `add`（带同步操作标识），新建单元的系统元数据随创建原子写入 `sync_created_by`；确定性直写同时写入 `sync_initial_digest`，会话抽取的每个输出由账本记录实际内容摘要 → 返回后按归属持久化输出清单，并**按写入意图转移状态**：新增置 `ok`；替换置 `cleanup_pending`，旧引用按统一删除条件清理完后置 `ok`。替换**不得原地改写旧单元**：新内容写入新单元，旧输出先解除引用、进入待清理；旧单元已被用户编辑或另有引用时保留，不覆盖也不会无条件删除。
- **恢复依赖的后端能力**（缺失时同步只做"只解除关联"与 `unconfirmed`，不做自动清理与重写）：
  1. **权威写入结果查询**：按系统元数据从**真源**精确查询，写成功后立即可查，不依赖异步索引——即 S06 的 `DomainStore.supports_exact_metadata_lookup` 能力。`MemoryAPI.list()` 的契约是"只返回已建索引的单元"，数据已写、索引未可见时会查空，**不能**作为恢复依据；
  2. **创建时写入归属字段**：`sync_created_by` 随单元创建原子写入，且内核去重合并到既有单元时不改写它；确定性直写同时写入 `sync_initial_digest`，会话抽取的派生单元不写源摘要，改由账本按每个输出记录实际内容摘要，避免摘要与单元内容不符导致永久保护；
  3. **删除语义**：只有后端提供原子比较删除时，摘要比较与删除才在同一事务内完成。默认后端 `supports_conditional_delete()` 为 False，无法消除检查后到删除前的编辑窗口，必须保留单元并报告能力不足；不得退化为本地比较后的普通删除。
  4. **按操作标识的写入回执**：`add` 接受调用方给出的同步操作标识，回执列出本次调用的**全部输出**（含去重复用的既有单元），可按操作标识查询；回执返回前重新做可信上下文与写权限校验。`batch_add` / `batch_add_async` 同样接受批级操作标识——整批是一次逻辑写入、对应一张回执，与单条回执同表、可由同一探测查询，重放按各项正文顺序判定一致。回执探测是 `MemoryAPI` 上声明的能力（`supports_operation_receipt()`），调用方先查能力再探测。当前回执为进程内实现，进程重启后的恢复只能依赖真源查询或落 `unconfirmed`，持久化仍列为遗留。
- **未完成写入的恢复**（遇到 `writing`），按以下顺序判断：
  - **有持久化的写入回执**：按回执恢复全部输出（含复用项）并登记引用，然后**与正常返回走同一状态转移**——按 `writing` 时持久化的写入意图，新增置 `ok`，替换置 `cleanup_pending` 并继续清理旧引用；不重写。否则 `USER.md` 从 A 改成 B、内核已提交 B 而账本未落盘时中断，恢复会留下 A、B 两版；
  - **没有回执**：缺回执不能证明写入未执行——内核可能已部分提交后抛异常，reload/重启也会清空进程内回执。只有显式 `prepared` 或人工确认未执行的来源才可重发；其余一律置 `unconfirmed`。回执因容量上限被淘汰同样按 `unconfirmed`，不能当作未提交；
  - 权威查询查到若干单元但无法证明整批完整时，是否允许自动重写取决于数据类型（统一语义，见下条）。
  - 后端缺少权威查询或创建时归属字段，或查询失败：置 `unconfirmed` 并报告，**不盲目重写**；只能经索引查询（如 `list()`）得到"查不到"时，同样不视为"没有产物"。
- **自动重发的统一语义**：
  - 内核明确拒绝且回执表明未执行：任何类型都可自动重发；仅有 `writing` 记录不能证明请求未发出。
  - **确定性直写**（`profile` / `fact` / `daily_log`，不调用模型抽取，同样的输入得到同样的输出）：部分写入后，若对每个已发现单元逐一检查统一删除条件全部满足（本批创建、无其他引用、未被修改），**证明产物已安全清理后**可整批重写；默认后端没有原子删除能力时不清理，置 `unconfirmed`，不删除、不重写。这里的"清理部分产物"属于破坏性清理，**只能在下方空间级恢复的第三步执行**，不能在逐条恢复时立即删除。
  - **会话抽取**（`session_turn`，经模型抽取）：两次抽取可能得到不同结果，即使清理成功也不能保证重写与第一次一致。只有第一次的**抽取结果已被持久化**（冻结的抽取输出）时才自动续写剩余部分；否则一律置 `unconfirmed`。本版普通 `add` 的抽取不产出冻结结果，因此会话来源的部分写入在本版一律进入 `unconfirmed`。
- **哪些失败可以自动重试**：只有能确认**没有产生任何写入**的失败，才在下次同步自动重试——例如授权校验拒绝、内核明确拒绝（校验错误、权限拒绝）且回执表明未执行。结果未知的失败（超时、连接中断、`add` 返回前崩溃）一律按上面的恢复规则处理，不能证明时进入 `unconfirmed`。
- 本版默认后端（本机模板的文档记忆）须在验收中覆盖以下断点：一批多条只写入部分后中断；替换时新输出已提交、旧输出未删完时中断；数据已写入真源、索引尚不可见时中断；删除前的检查通过之后、删除执行之前发生人工编辑；输出全部来自去重复用、`add` 已返回但账本落盘前中断。
- **并发约束**分两层：
  - 同一 `{安装, 来源根}` 上的手动同步、定期同步、Hermes 镜像写入全部串行执行；后到的请求排队等待，或返回"同步进行中"，不并发处理同一来源。
  - **同一目标空间内，"写入并登记输出引用"与"解除最后引用并删除输出"两段不能交错**。不同来源根可能复用同一个单元：B 的 `add` 已返回复用的单元 U、尚未登记引用时，A 若解除 U 的最后一个已登记引用并删除它，B 随后登记的就是一个已删除的单元；整个过程 U 的版本不变，原子条件删除也挡不住。本机首版直接**按目标空间串行**执行这两段：写入从调用 `add` 到引用登记完成、删除从解除最后引用到删除完成，各自在同一把目标空间锁内进行。
  - **锁随进程退出而释放，未登记的引用必须先恢复**：B 已复用 U、内核回执已提交、本地引用尚未登记时服务退出，重启后若 A 的删除先拿到锁，账本里仍只有 A 引用 U，U 会被删掉，B 随后从回执恢复出的就是失效引用。
- **空间级恢复：先登记整个空间能确认的引用，再做任何删除**。任何目标空间在执行破坏性清理（替换清理、判删、撤权清理、恢复中的部分产物清理）之前，在同一把空间锁内按三步进行：
  1. **只读核对**该空间全部待恢复操作（`writing`、`cleanup_pending`），逐条判定为：有回执可确认、部分产物可安全清理、`unconfirmed`。这一步不写账本、不删除任何单元。
  2. **幂等登记**所有已确认的引用：回执中的全部输出（含复用项）登记到对应来源；部分写入时已发现的本批产物，也先登记为该操作的"待定输出"（待定引用），让它们在账本里有引用、不会被别的操作当作无主单元删除。第三步清理某操作自己的部分产物时，先在同一事务中解除**该操作自己的**待定引用，再按统一删除条件判断引用数是否为零。
  3. **统一决定删除**：空间内只要还有 `unconfirmed` 操作，就无法知道它们引用了哪些单元，本空间的破坏性清理**全部推迟**；否则按统一删除条件执行所有待清理项，包括可安全清理的部分产物。
  这样结果与遍历顺序无关：先处理哪条操作，最终的引用登记与可读单元都相同。

**未确认操作的处理**

- **推迟的清理持久保存**：每个被推迟的删除写入"待清理项"表——单元 ID、所属来源记录、原本的清理原因（替换 / 判删 / 撤权 / 部分产物 / 丢弃）、阻塞它的操作 ID。"只解除关联、单元保留"的输出在输出记录上标为"已保留"并写明原因。两者都能随时查回，阻塞解除后据此继续，不依赖重新扫描。
- `sync status` 列出：每个 `unconfirmed` 操作（来源、空间、发生时间、已发现的本批产物）、被它阻塞的空间与待清理项数量，以及"已保留"的单元。
- `sync recheck`：重新执行空间级恢复的核对（例如后端恢复后，回执或权威查询变得可用）。能确认的操作按正常规则完成，阻塞随之解除。
- 仍无法确认时，用户用 `sync resolve` 对单个操作做安全的人工收尾，三种动作：

  | 动作 | 已发现的本批产物 | 来源记录 | 适用 |
  |---|---|---|---|
  | `adopt`（采纳） | 全部保留，登记为该操作的正式输出，原始归属不变 | 按 `writing` 时记录的写入意图处理：**新增**直接置 `ok`；**替换**须在确认时让用户选择旧版的去向——"保留旧版"（旧引用转为删除保护，置 `ok`）或"清理旧版"（进入 `cleanup_pending`，按统一删除条件清理）。来源标注"内容可能不完整"：没有回执时，本次复用了哪些既有单元无从得知，这些单元不会登记为本来源的引用，以后可能随其他来源清理，确认时须说明 | 用户认为已写入的部分可用 |
  | `abandon`（放弃，默认推荐） | 全部保留，原始归属不变，置删除保护标记（以后不会被同步删除）；解除该操作对它们的待定引用 | 置 `abandoned`，下次同步按新的逻辑写入重新导入；替换意图下的旧版引用原样保留，下次写入仍按替换处理这些旧引用 | 不确定时的最安全选择，不删任何东西 |
  | `discard`（丢弃） | 先持久化用户决定，把这些产物写入待清理项（原因为"丢弃"），并解除该操作自己的待定引用；**实际删除推迟到空间内不再有其他未确认操作时**，在空间锁内重新检查引用、归属、保护标记与版本后按统一删除条件执行。仅因仍被其他来源引用而不能删的，只解除本操作的关联、**不置保护标记**，留待最后一个引用解除时判定；因已被编辑、归属无法证明或后端缺少原子删除能力而不能删的，保留；确定内容已变或归属无法证明时置删除保护，能力不足不置永久保护 | 置 `abandoned`，下次同步重新导入；替换意图下的旧版引用原样保留，下次写入仍按替换处理这些旧引用 | 用户确认这些产物不需要 |

  - `discard` 前展示将删除的单元清单并确认；确认后若同空间仍有其他未确认操作，界面说明"已记录，待其他操作处理后再删除"。原因：另一条未确认操作 B 可能复用了 A 创建的单元 U、只是引用尚未登记，用户丢弃 A 并不能证明 U 对 B 无用，只能等 B 恢复或被处理后再判定。
  - `adopt` 替换时的确认界面同时展示新输出与旧版引用，旧版去向必须明确选择，非交互环境须显式指定。
  - 三种动作都只作用于该操作自己的产物与待定引用，不影响其他来源的已登记引用。
  - 置了删除保护标记的单元，之后同步不会删除，需要清除时由用户经普通删除完成；它们的原始归属仍可用于审计与共享引用判定。
- 空间内最后一个 `unconfirmed` 操作被处理后，该空间的待清理项在下一次同步（或 `sync recheck`）时按统一删除条件继续执行。
- **Hermes 镜像去重**：插件的 `on_memory_write` 收到内置记忆写入后，按 Hermes 读取器同样的规则计算来源根（所属 profile 的记忆目录）与稳定条目标识（数据类型 + 逻辑集合 `MEMORY` 或 `USER` + 集合内标识），经同一入口进入账本；之后文件扫描读到同一条，账本身份相同，直接跳过。镜像写入同样核对授权版本，撤权后不提交。

**6. 判删：只有完整扫描才能据此删除**

- 源端缺席的条目默认**不删除**，只在报告中列出；`--mirror-deletes` 时才删除本端对应记忆。
- 即使加了 `--mirror-deletes`，也只在以下条件**全部满足**时，才对某个"来源根 × 数据类型"范围做删除判断：
  - 该范围本次**完整扫描成功**（读取器标为完整、跳过清单中没有该范围）；
  - 本次没有过滤条件作用于该范围（`--since`、`--limit` 会让会话范围不完整；未授权 `session_turn` 时会话范围根本不在扫描内）；
  - 同步未中断。
- 不满足条件的范围本次**不推进任何删除判断**，账本中的"最后一次看到的时间"也不更新。
- 删除按第 4 节的统一删除条件执行；不满足的只解除账本关联并报告。
- 防误删：一次完整扫描后，某个范围缺席的条目超过该范围已知条目的一半时，暂停删除并要求用户确认（防止目录暂时被清空或换成了别的目录）。

**7. 触发**

- 手动执行；`connect` 完成后询问是否授权并立即同步一次（非交互默认否）；定期自动同步默认关闭，可按安装开启，且只在当前授权范围内执行。

### D16：授权后扫描本机 Agent 并自动接入

装好 agent memory 后，经用户授权，自动找出本机已安装的 Codex、DSH、Hermes、WorkBuddy 实例，批量接入并逐个引导同步其已有记忆；之后新出现的实例自动接入。用户不必逐个宿主执行 `connect` 与 `sync grant`。

**用法**

```
jiuwen-memory init                       # 初始化完成后询问是否授权扫描与接入（默认"是"）
jiuwen-memory scan [--add-dir <目录>...] [--remove-dir <目录>...] [--depth N] [--dry-run]
jiuwen-memory scan status
jiuwen-memory scan include <实例>        # 把"已忽略"的实例恢复为可自动接入
jiuwen-memory scan auto-connect on|off
jiuwen-memory scan revoke
```

命令命名为 `scan`，不用 `discover`：`discovery` 在本特性中已指服务发现文件（D2）。

**1. 两层授权**

| 层 | 允许做什么 | 不允许做什么 | 保存位置 |
|---|---|---|---|
| 扫描授权 | 在授权位置内查看文件、目录是否存在（只做 `stat` 与列目录），按宿主特征识别实例 | 打开文件读取内容；跟随跳出授权位置的符号链接；进入网络盘、外接盘或其他用户的目录 | `~/.jiuwen-memory/scan.json`（0600）：扫描位置、深度上限、`auto_connect`、已忽略的实例、授权版本 |
| 同步授权 | 按 D15 的授权单读取指定来源根、指定类型的内容 | 超出授权单范围（沿用 D15 的受限访问接口） | 安装记录的 `sync` 字段（D15） |

- 接入（修改宿主配置）位于两层之间：扫描授权允许发现之后才能接入，接入之后才有安装可挂同步授权。
- 扫描授权变更（增删目录、改深度、开关自动接入）时授权版本加一；扫描授权不隐含任何同步授权。

**2. 触发与默认行为**

- **安装后询问**：`init` 在交互终端完成后询问是否授权扫描与接入，展示将查看的位置、"只看路径、不读内容"、发现后会自动接入、以后新出现的实例也会自动接入，默认"是"。非交互环境不扫描，只输出提示命令：无人确认不能当作同意。
- **首次扫描**：结果一次性列出每个实例的宿主、实例（profile、版本、作用域）、命中的特征路径、接入将修改的配置文件、hook 默认值与可导入类型；用户可取消勾选个别实例，确认后批量接入。接入按 D14 的默认值：MCP 全部开启，hook 只有配置级且已核实的宿主默认开启，需要安装代码插件的 hook 不随扫描开启。
- **逐个同步授权**：每个实例接入后进入 D15 第 1 节的同步授权确认（来源根、数据类型、目标空间及可见人群、`profile` 个人信息提示、出站清单），可逐个跳过；确认后先 dry-run，再确认写入。会话类（`session_turn`）默认不勾选，与 D15 一致。
- **之后自动接入**：服务启动时和此后每 24 小时重新扫描一次，只看路径。`auto_connect` 默认开启，随首次扫描授权一起确认；新出现的实例按上面的默认值自动接入，并在 `status` 中报告。自动接入**不**自动开启同步授权：该安装记为"待授权同步"，在 `status`、下一次交互式 CLI 命令与 MCP 工具说明中提示用户确认。
- **用户意愿优先**：用户 `disconnect` 过、或在扫描结果中取消勾选的实例记入"已忽略"，此后重新扫描不再自动接入，只在 `scan status` 中列出；`scan include` 才恢复。
- `scan revoke`：停止定期扫描与自动接入；已有安装与同步授权不受影响，分别用 `disconnect`、`sync revoke` 处理。

**3. 扫描边界**

- 扫描框架统一执行边界，宿主的识别逻辑只能经框架提供的受限遍历接口查看路径（与 D15 受限访问接口同一思路，但只有 `stat` 与列目录，没有打开文件的能力）。
- 默认位置都是用户目录下的隐藏目录，不会触发 macOS 的文件夹访问授权；"文稿""桌面""下载"等受保护目录只在用户自己追加时扫描，系统拒绝访问时报告跳过，不重复请求。
- 用户追加的项目目录逐层下探，有深度（默认 4 层）与条目数上限，跳过 `.git`、`node_modules`、虚拟环境与构建产物；达到上限即停止，报告"未扫完"，不猜测剩余部分。
- 扫描结果只保存实例与特征路径，不保存文件内容。

**4. 四家宿主的识别**

| 宿主 | 查看的位置 | 实例划分 | 可导入类型（按 D14 能力表） | 可接管自带记忆（见第 7 节） |
|---|---|---|---|---|
| Codex | `JIUWEN_CODEX_HOME` 或 `~/.codex` | 单实例 | 长期记忆、会话 | 待实测（自带记忆默认关闭，开关位于 `config.toml`） |
| DSH | `JIUWEN_DSH_HOME` 或 `~/.dsh`，以及 `desktop`、`dsh-tui` 两个 profile | 每个 profile 一个实例 | 会话（无内置长期记忆） | 不涉及 |
| Hermes | `JIUWEN_HERMES_HOME` 或 `~/.hermes`，以及 `profiles/<名>/` | 每个 profile 一个实例 | `MEMORY.md`、`USER.md`；会话待实测，不可选 | 待实测（内置记忆配置项） |
| WorkBuddy | 社区版 `~/.workbuddy`、企业版 `~/.codebuddy`；用户追加目录下项目里的 `.workbuddy/memory/` | 按版本一个实例，企业版默认用户作用域 | `USER.md` 等长期记忆、项目每日日志；会话不支持 | 待实测（能否单独关闭未知） |

- 每家的特征文件声明在宿主注册表中，以选定版本的实测结果定稿。只有目录、不满足特征时标为"疑似"：列出供用户判断，不自动接入。
- 接入还依赖宿主自身工具时（如 DSH 的 `dsh` 命令），工具不可用则标为"已发现、无法接入"并说明原因。
- **WorkBuddy 项目日志并入用户级安装**：项目里的 `.workbuddy/memory/` 作为该用户已有 WorkBuddy 安装的额外来源根，进入其同步授权；不为每个项目新建项目作用域安装，也不往项目里写 `.mcp.json`，避免改动代码仓库或被提交进版本库。本机没有用户级 WorkBuddy 实例时，只列出提示，不自动接入。

**5. 插件化**

- 宿主注册表的 `HostSpec` 新增 `probe(view) -> list[ProbeResult]`：`view` 是受限遍历接口；`ProbeResult` 含宿主名、实例（与 D14 的 `instance` 同结构）、命中的特征路径、记忆来源根、可导入类型（必须是能力表中"支持"的类型）与状态（已发现 / 疑似 / 已发现但无法接入）。
- 接入复用 `connect` 的步骤与回滚（D5），同步复用 D15；扫描不另建接入或读取路径。
- 新增宿主只需在注册表中补 `probe`，扫描命令与服务不按宿主名分支。实现时在 S09 的宿主接入约定中补充 `probe` 的约束：不得读取内容、必须有边界、可导入类型不得超出能力声明。

**6. 失败与并发**

- 批量接入逐实例独立：一个失败不影响其他，最后统一报告；重跑时按实例去重（D14），续做未完成的接入。
- 后台扫描与 `connect`、`disconnect` 共用安装记录的文件锁，按实例去重，不会为同一实例建两个安装；用户正在断开的实例不会被同时接回。
- 后台自动接入失败（配置文件被占用、格式无法解析等）只记录原因，下一周期再试；连续失败三次转为"需手动处理"，不再自动重试。

**7. 与宿主自带记忆并存**

宿主自己的记忆功能（如 Codex memories、Hermes 内置记忆、WorkBuddy 的 `USER.md`）在接入后默认继续工作，agent memory 不修改、不关闭它；用户可对单个安装选择"由 agent memory 接管"（见本节末）。两套记忆同时存在会带来两类重复，分别处理：

- **同一件事两边各记一份**：hook 写入的是本轮问答原文（任务事件），宿主自带记忆再由同步导入一份整理后的条目。两者形态不同，不强行合并；导入条目带 `source_app` 与来源标识，召回时可区分来源。接入确认页说明"该宿主自带记忆已开启（或未开启），授权同步后会定期导入"，由用户决定是否授权同步，以及是否在宿主里自行关闭自带记忆。
- **回流：agent memory 注入的内容被宿主记下后又被导入**：自动召回把记忆注入宿主上下文，宿主自带记忆可能把这些内容记进自己的文件，下次同步再导入，形成"写入 → 召回 → 宿主记下 → 再导入"的循环，每转一圈多一份副本。处理分三层：
  1. **注入内容带标记**：召回注入的文本统一包在固定的标记块中（标记格式在实现时定稿并写入 S11 的召回视图约定）；同步过滤在入账前剥除标记块，宿主原样记下的注入内容不会被导入。capture 现有的"剔除本轮注入原文"规则不变。
  2. **正文相同即复用**：剥除后的条目，规范化正文与目标空间中已有单元相同、且该单元不是本来源创建的，不新写单元，只在账本登记对该单元的引用（`origin=external`），删除时按 D15 统一删除条件不会删除它。
  3. **改写后的回流不强判**：宿主把注入内容改写、摘要后记下的条目无法可靠识别，按普通新条目导入并保留来源标识；这部分列为已知遗留，不用相似度猜测去重，避免误吞用户真实的新记忆。
- 同一宿主的镜像写入与文件同步对同一条目使用同一稳定标识（D15），不会因两条路径各写一份。

**由 agent memory 接管（可选）**

用户可选择关闭某个安装的宿主自带记忆，改由 agent memory 承担，从源头消除重复与回流。

- **提供条件**（同时满足才在确认页出现该选项）：该安装的 hook 已开启；该宿主"关闭自带记忆"的配置项已在选定版本实测（第 4 节表中为"支持"）；用户在交互界面手动选择。后台自动接入的实例一律不接管。
  - 只有 MCP 时模型不一定调用工具，关闭自带记忆后可能什么都记不住，因此 hook 未开启不提供；
  - 配置项未实测时改错会破坏宿主配置，因此"待实测"不提供。
- **执行顺序**：先完成一次该安装的同步（需已有同步授权，dry-run 确认后写入），再修改宿主配置关闭自带记忆；同步未完成时不关闭，避免宿主已有记忆既未导入又不再更新。宿主的原始记忆文件不删除、不改写。
- **记录与恢复**：安装记录新增 `takeover`，保存被修改的配置项及原值。`disconnect`、关闭 hook、或执行 `jiuwen-memory takeover off <宿主>` 时恢复原值；恢复按 D5 规则只回滚本工具写入、且用户之后未改动的字段，用户改过的保留并报告。
- **接管后的同步**：宿主不再新增自带记忆，定期同步只需处理已有文件的变化；Hermes 的镜像写入（`on_memory_write`）随内置记忆关闭而不再触发，属预期行为。
- **状态可见**：`status` 显示每个安装是否处于接管状态；hook 因故失效（如宿主升级导致事件不再触发）时提示用户恢复自带记忆。
- 用法：`connect` 确认页勾选，或对已连接安装执行 `jiuwen-memory takeover on|off|status <宿主> [--install ID]`。

### D17：同步与 hook 的数据去向

- 读取授权与 `capture` 分开确认；两者开启前都展示 D9 的出站清单。同步授权另外展示目标空间的可见人群，并单独提示 `profile` 类含个人信息。
- 导入内容写入时会经 Embedder 向量化，包含 `session_turn` 时还会发给 LLM 抽取，清单中按实际装配列出；dry-run 不发生任何出站。
- 安装插件（DSH、Hermes 的 hook）时说明插件会在宿主进程内运行，并在关闭 hook 时卸载、恢复原配置。

## 本版交付与上线条件

本机服务、安装与发现、旧 SDK 数据接管、项目授权、JiuwenSwarm Provider、MCP 桥，以及 Codex 和 DSH 的原生召回与写入随同一版本交付。完整交付以「验证」中的端到端接续、三个宿主实际会话、安装与恢复、权限和平台用例通过为准。

D14 随本版交付；D15 先交付不含持久化回执的同步实现，逐次授权版本核对已落地；回执持久化完成并通过验收后再宣称完整交付。Hermes 与 WorkBuddy 以一条可判定的门槛验收，**分别**在选定版本上完成：
1. 宿主实际调用一次 `jiuwen-memory` 的 MCP 工具；
2. 从用户指定目录导入一条真实的长期记忆；
3. 由另一个获授权的 Agent 召回这条记忆；
4. 对原目录再次同步，结果不重复。

WorkBuddy 尚未核实的 hook 与会话格式按 D14 的能力表返回"不支持"，不影响上述两项核心功能在本版交付。

D16 已完成仓库内实现与自动化测试；四家宿主的特征文件、默认路径与接管配置项在选定版本真机实测后再宣称完整交付。

已有部署显式启用本机模式时先执行 D12，由服务在旧 Runtime 释放存储后接管；全新部署经 `init`、`connect` 完成装配。安装后须能从干净环境运行 CLI、发现或拉起服务，并使用本机模板中已装配组件的数据去向声明。

## 拒绝的方案

| 方案 | 不采用的原因 |
|---|---|
| JiuwenSwarm 继续进程内 SDK，其他 Agent 走 HTTP | 内核随 JiuwenSwarm 退出；Registry 单写锁使两者不能同时写 |
| 用户手工部署 HTTP 服务 | 单机使用要配服务、地址和凭据，太重；本特性保留它作为团队部署形态 |
| 直接推广共享 Portal 的转发模式 | Portal 子进程不含内核，只转发回宿主进程，宿主退出照样失效 |
| 每份配置一个服务 | 不同宿主配置不同，会起出第二个服务：同数据路径则抢锁失败，不同路径则记忆分裂 |
| Unix 套接字 / 命名管道作为首版传输 | Portal 仍需端口；现有 HTTP 栈可直接复用；命名管道需两端自写 HTTP 层 |
| 沿用内存 `api_key` 或 `trusted` 认证 | 前者重启失效且每次请求 Argon2id；后者共享密钥可声明任意主体 |
| 所有宿主共用一个用户主体 | 区分不出来源，无法单独隔离；接续连接解析会多匹配 |
| 只做 MCP，不做 hook | 模型可能不调用工具，做不到每轮自动召回与写入；改为 MCP 默认、hook 可选，见 D14 |
| 所有宿主默认开启 hook | DSH、Hermes 需安装代码插件，Hermes 还会替换用户现有的记忆插件；WorkBuddy 事件未核实。只对配置级且已核实的 Codex 默认开启，见 D14 |
| 所有宿主只用插件接入 | 每家插件接口不同且随版本变化，维护成本高；MCP 一套接法覆盖所有宿主，见 D14 |
| 扫描宿主私有会话日志作为默认采集 | 格式私有易变，权限、轮转、重复采集成本高（调研 3.5）；改为显式授权后的只读同步，会话历史默认不导入，见 D15 |
| 同步时导入宿主的角色与行为设定文件 | `SOUL.md`、`IDENTITY.md`、`AGENTS.md` 是给该宿主的指令，导入后会被其他 Agent 召回并当作事实或指令 |
| 源端删除即同步删除本端记忆 | 宿主可能因容量上限或整理而删除条目，自动删除会丢失仍有价值的记忆；默认只报告，`--mirror-deletes` 显式开启 |
| 按"本次没读到"判定源端已删除 | `--since`、`--limit`、读取失败、未知格式、中断、目录暂时不可访问都会让条目缺席，可能误删整个来源；只有完整扫描成功的范围才判删，见 D15 |
| 只按宿主名选择安装 | 同一宿主可能有多个 profile、版本或作用域，按名取第一条会选错凭据与配置；多实例时必须显式指定，见 D14 |
| 账本只按"安装 + 来源路径"标识 | 不同目录的同名文件互相覆盖，换目标空间会被旧摘要跳过；账本身份加入来源根与目标空间，见 D15 |
| Markdown 条目按位置定位 | 插入或重排后其后所有条目都变成新条目，导致大量重复；改用规范化正文指纹作稳定标识，见 D15 |
| 写入成功后再记账 | 写入与记账之间崩溃会在重跑时重复写入；改为两阶段记账并按同步操作标识核对，见 D15 |
| 先 dry-run 再授权读取 | dry-run 本身就要读文件；改为授权后再 dry-run，且 dry-run 不发生任何出站，见 D15 |
| 同一文件中"一条消失、一条新增"即视为替换 | 无法区分"编辑"与"删 A 加 B"，会绕过默认保留策略删掉 A；只按宿主稳定 ID 或整文件条目替换，见 D15 |
| 按同步操作标识查到输出即视为写入完成 | 一批多条可能只写了一部分；以 `add` 返回的输出清单或内核持久回执为完成依据；只查到部分产物时，确定性直写安全清理后可重写，会话抽取置为未确认，见 D15 |
| 读取器自行打开文件、读出后再校验授权 | 越界文件的内容已经被读取；改为服务提供受限访问接口，打开前校验，见 D15 |
| 两条来源正文相同时共用一个输出 | 删除其中一条来源时无法判断输出是否仍被引用；默认各写各的，内核合并造成的共享输出按引用计数处理，见 D15 |
| 同步账本引用数归零即删除单元 | 内核去重可能复用早先由 MCP 或用户手工创建的记忆，引用归零不代表有权删除；删除须同时有创建归属证据、无其他引用、版本未变，见 D15 |
| 部分写入后按标识查到单元即删除重写 | 没有写入时的摘要就无法判断是否被人工编辑，可能抹掉用户修改；改为依据随单元原子保存的初始摘要与带版本条件的删除，证据不足时置为未确认，见 D15 |
| 删除判定绑在来源记录上 | 共享输出的最终清理会依赖来源删除顺序，可能永久残留或被误删；归属记在输出记录上，最后一个引用解除时判定，见 D15 |
| 同步操作标识由来源与内容摘要推导 | 内容改回旧值时会复用已失效的回执，登记已被清理的单元；改为每次逻辑写入新生成并持久化，见 D15 |
| 凭回执恢复后直接置为完成 | 替换操作会跳过旧输出清理，留下新旧两版；恢复与正常返回走同一状态转移，见 D15 |
| 依靠空间锁防止重启后的删除抢先 | 锁随进程退出释放，未登记的引用会被删除抢先；破坏性清理前先恢复同空间的写入，无法恢复时推迟删除，见 D15 |
| 人工丢弃时立即删除该操作的产物 | 同空间其他未确认操作可能复用了这些单元且引用未登记；丢弃先记录待清理项，待空间内不再有未确认操作时再判定，见 D15 |
| 人工收尾时把保留的产物改记为"非同步创建" | 与"原始归属不变"冲突，丢失审计与共享引用依据；改为保留原始归属、另设删除保护标记，见 D15 |
| 逐条恢复时立即清理部分产物 | 同空间的其他回执尚未登记、或稍后才发现未确认操作时会过早删除；改为只读核对、登记引用、统一决定删除三步，见 D15 |
| 未确认操作只能"等用户处理" | 一条会话中断会无限期阻塞整个空间的清理，且被推迟的对象无处查回；新增待清理项持久表与 `recheck` / `resolve`，见 D15 |
| 会话抽取部分写入后清理并重新抽取 | 两次抽取结果可能不同，清理成功也无法还原第一次的输出；没有冻结抽取结果时置为未确认，见 D15 |
| 共享输出只按来源根加锁 | 不同来源根可复用同一单元，登记引用与删除可能交错，导致账本指向已删除单元；同一目标空间内两段串行，见 D15 |
| 真源查不到本批新建单元即重写 | 输出全部来自去重时真源同样零命中，调用却可能已成功，会话抽取重写还可能得到不同结果；以持久写入回执为准，无回执时置为未确认，见 D15 |
| 用 `list()` 查不到即视为没有产物 | `list()` 只返回已建索引的单元，数据已写、索引未可见时会重复写入；只用真源的权威查询，见 D15 |
| 确认时只核对授权版本与目标空间 | 预览后宿主可能改写文件或清空目录，执行的内容与用户确认的不同；冻结计划并在执行前重算比较，见 D15 |
| DSH 旧安装无证据时默认归第一个 profile | 继承关系决定令牌与任务绑定归属，生效后无法纠正；无证据时同样要求用户选择，见 D14 |

| 自动写入工具输出原文 | 量大，易带出密钥与文件内容；改为一行操作记录 |
| 等待 Agent MCP 分支合入后再做 | 合入时间不确定；两者职责可分离，见 D11 |
| 等服务空闲再重启以载入新连接 | JiuwenSwarm 持续续约时永远等不到空闲，用户已装好 hook 却用不了 |

## 验证

实现时按下列项验收；当前均未执行。

**首版交付门槛（端到端，必须整条通过）**

1. 从已有 SDK 数据启动：JiuwenSwarm 以进程内 SDK 写入任务 A 的事件，并已有若干个人记忆。旧主体带非空 `agent` 维度，任务 A 位于非默认项目空间。
2. 执行 D12 切换到本机服务；若原授权只在内存中，由项目管理员显式重新授予任务 A 所在空间。
3. 完全退出 JiuwenSwarm，确认服务仍在运行。
4. 一个此前从未绑定过任务 A 的 Agent（如 Codex），用自己的独立令牌找到任务 A，经用户确认后自绑定，并写入新事件。
5. 重启服务和 JiuwenSwarm。
6. 核对三类结果：
   - **数据搬到了**：双方按同一个任务 ID 都能读到第 4 步的新事件；第 1 步的个人记忆仍按原五维 Scope 可见。
   - **身份保住了**：JiuwenSwarm 仍以原 owner 身份管理任务 A，并能沿切换前的原绑定继续写入。
   - **权限仍正确**：新宿主只能管理自己的绑定，不能关闭任务 A、不能为其他连接建绑定或解绑。

这条用例同时检验生命周期、数据连续性和权限；只验证"服务进程还活着"覆盖不了后两项。

**服务与生命周期**

- 三个客户端并发拉起，只得到一个服务进程，其余连接成功。
- 关掉拉起它的 JiuwenSwarm，服务继续运行，Codex 读写正常。
- 服务重启后：令牌仍有效、对话原文和任务记录仍在、Portal 可再次打开。
- 停机期间修改 md，重启后影子索引已对账。
- kill -9 服务，下次使用自动拉起；未确认的接续写入按回执可核对恢复。
- 版本不匹配、数据目录权限过宽、端口被占用时给出明确错误。

**身份与权限**

- 每个安装的令牌只能以自己的主体访问；撤销后立即拒绝。
- 未加入项目空间的主体读不到该空间任务。
- JiuwenSwarm 切换本机模式后，按原 Scope 能查到切换前的个人记忆、任务与绑定；普通读写与接续调用两条路径分别验证。
- 旧进程内 Runtime 仍在运行时，切换与本机模式启用被拒绝。
- 连接只能为自己绑定、解绑；为其他连接建绑定或关闭任务仍要求 owner。
- 自绑定策略：本机服务模板下非 owner 的项目成员能自绑定成功；未开启该策略的既有部署（HTTP、SDK）拒绝非 owner 自绑定，行为与现行一致。
- 管理员策略：创建任务的 Agent 令牌被撤销后，空间管理员经命令行仍能关闭任务、解除其绑定；未开启该策略的既有部署中，非 owner 管理员仍被拒绝。
- 迁移不提权：旧 JiuwenSwarm 主体迁移前是普通写成员，迁移后仍能沿自己的绑定写入，但**不能**关闭他人的任务或解绑他人；管理权只能经显式的 `space recover-admin` 流程取得，并留有审计记录。
- Agent 工具清单（MCP 与 hook）中没有关闭任务、为他人绑定 / 解绑、`attach`；Agent 经工具发起这类请求被拒绝。
- 迁移时原 actor 无法登记或授权缺少来源，切换前列出将失去的数据与权限，用户不确认则不提示退出旧进程、不切换。
- 旧绑定仍在、但原主体在该空间的成员权限已被撤销：迁移后该权限**不能复活**，旧绑定不能用来读写。
- 同一会话命中多个任务时不召回任务背景、不写入，直到用户选定。

**宿主 hook（每家分别执行，记录宿主版本与实测事件载荷）**

- 新会话绑定任务后，下一轮自动召回到另一宿主写入的事件。
- 未绑定时只召回不写入，并能看到未保存提示。
- 召回注入的内容不会出现在下一次写入里。
- 同一轮写入事件重复触发只写一条。
- 服务不可达时对话不受影响，写入状态为未确认。
- `connect` 合并写入宿主配置、`disconnect` 只回滚自己写入的条目。
- JiuwenSwarm 持续在线时 `connect` 第二个宿主：重载后第二个宿主能完成首次绑定和读写，JiuwenSwarm 正在进行的请求不丢失。
- `connect` 中断覆盖**副作用已发生、进度尚未记账**的时刻（令牌已签发未记账、连接已写入未记账、宿主配置写了一半）：重跑不重复签发令牌、不重复写条目，`disconnect` 能找到并清理全部副作用；宿主配置未全部写入并回读成功前，不报告连接完成。
- 令牌：摘要已登记、令牌文件未写成时中断，重跑后旧摘要被撤销、新令牌能**实际通过认证**，该安装只有一份有效凭据；令牌文件已写、摘要未登记时中断，重跑后用原文件补登记。
- 待写记录：`capture=off`、未绑定、多候选未选定三种情况分别执行一轮，**直接检查待写表和事件表**，均无用户原文、无事件。
- recall 与 capture 之间仅重启服务、原绑定有效：写入一次，重复触发不重复写。
- recall 与 capture 之间解绑或切换任务：拒绝写入，事件表中其他任务没有新增。
- 另一个宿主在同一轮加入同一任务（任务修订号变化）：本轮仍正常写入。
- 写入结果未知后重试：沿原事件 ID 核对恢复，事件表只有一条。
- 提交成功 → 响应丢失 → 待写正文过期 → 同轮重试：返回原结果，事件表只有一条，不返回"未写入"。
- partial → 待写正文过期 → 同轮重试：用保留的原写入请求完成重试，事件表只有一条，**任务背景关联已建立**。
- 操作记录已落盘、`add` 尚未调用时 kill 服务：重启后服务自动以原事件 ID 重放，事件只有一条、背景关联完整；宿主是否重试不影响结果。
- 非终态操作超过最长保留期：原请求被删除，同轮重试返回"未确认，无法自动重放"并附本地操作 ID；已有内核回执时另附 `operation_id` 与 `refs`，没有回执时提示只能查询状态。
- `unknown` 回执 + `refs=[]` + 原请求已过期：`op show` 只提供状态查询，不提示 `continuity_recover`，也不重放。
- 操作记录 `已准备` → 撤销该安装令牌（或把主体移出项目）→ 重启服务：服务确认未提交后记为已拒绝，事件表无新增，不再自动重放。
- 内核已部分写入 → 本地回执未落盘（本地仍是 `已准备`）→ 撤权 → 重启服务：服务经只读回执查询识别出 partial，停止推进并补存回执；**不得**记为已拒绝。查询失败时保持未确认。
- 操作记录 `partial` → 撤销该安装令牌（或把主体移出项目）→ 重启服务：停止自动推进，保留 `operation_id` 与 `refs`；同轮查询返回"未确认"，不是"未写入"。
- 项目：同一连接、两个项目、相同宿主会话 ID：两边的任务查找、待写记录与写入互不串；未指定项目且连接有多个项目时返回"需要选择项目"，不召回任务背景、不写入。
- JiuwenSwarm 本机模式使用非默认 `duty` 与自定义 `top_k`：结果与切换前进程内接续 `prefetch` 一致，结构化字段（`items`、`paths`、`gaps`、`view_meta`）完整保留。
- 同轮冻结：顺序重复 capture（同内容）只写一次；两个 capture 并发只有一个创建操作记录；同轮第二次 capture 内容不同返回冲突，事件表不变；同轮重复 recall 不覆盖已冻结的绑定与用户文本。
- 回显鉴权：已提交 → 把主体移出项目 → 重试同轮 capture 与 `op show`：只返回状态，不回显正文、`refs` 或 `operation_id`，也不提供 `continuity_recover`。

**迁移身份与回退**

- 原配置不含 actor、actor 由旧宿主运行时注入、任务位于非默认项目：经 `--actor-from-host` 取得并登记，核对 owner 指纹一致后才确认原任务管理权；无法取得可信身份或无法核实某项权利时，切换前列出具体缺口。另测只有个人记忆、没有自建任务的主体能沿原 Scope 读回旧数据，以及同一宿主会话 ID 在两个项目保存不同任务选择时互不覆盖。
- 角色模式且原配置含独立证据图与非默认职责策略：切换后至少一条原关系可查、一次原职责查询结果与切换前一致。
- 切换后核对失败：新服务停止并释放全部写锁，原宿主以原配置重新启动可正常读写；切换报告写明写锁持有方。

**安装、生命周期与宿主事件**

- 并发 `connect` 两个宿主：两份连接与 hook 条目都保留（宿主配置的读改写需加锁，不能只靠单文件原子替换）；同一新空间只产生一个首任管理员。
- 撤销后重新 `connect`：签发新令牌，旧令牌继续失效。迁移时复用的成员关系与原连接记录来源，`disconnect` 只清理本安装创建的资源。
- 启动超时后旧进程才就绪、重载时仍有后台 capture、旧服务退出时新服务已发布发现文件：始终只有一个写者，新发现文件有效，已接收的写入可核对。
- 用真实宿主退出验证进程脱离；Windows Job 不允许脱离时，`service status` 明确显示降级状态。
- 三家分别实测 recall 与 capture 能否拿到同一个稳定轮次标识（JiuwenSwarm 写入侧要求 `event_id`，读取侧目前没有对应必填项，需宿主补齐或由适配器生成）；覆盖同会话两轮交错、重复 Stop、缺少轮次 ID（不写入并提示），以及服务冷启动超出宿主召回预算时对话照常继续。有工具事件的宿主验证仅写操作摘要；JiuwenSwarm 的工具记录需由 Rail 提供事件。
- MCP：本机模式下经工具传入管理类 `operation` 被桥与服务端拒绝；显式远程模式既有工具行为不变。
- D13 三类身份分别覆盖：普通成员（只能自绑定）、owner、仅有 `MANAGE_SPACE` 的管理员（无需项目 WRITE 即可执行管理操作，但不能写入事件）。

**宿主接入分层（D14）**

- 四家 `connect` 默认都写入 MCP 配置，并能经工具完成任务查找、自绑定、检索与保存；Codex 默认另写 hook，DSH、Hermes、WorkBuddy 默认不写 hook。
- `--hooks` / `--no-hooks` 覆盖默认；`hooks enable|disable` 切换后宿主配置与安装记录一致，关闭后不残留 hook 条目或插件。
- 对"待实测"或"不支持"的能力（如 WorkBuddy `--hooks`、DSH 长期记忆导入）返回明确的能力结果与原因，退出码区别于失败，且不改动任何文件。
- 安装实例：Hermes 两个 profile 分别 `connect` 得到两个安装与两份令牌；只写 `hermes` 时报错并列出候选；`--profile` 或 `--install` 能唯一选中；`hooks disable` 只影响选中的 profile。
- Hermes 某 profile 已启用其他外部记忆插件时开启 hook：先提示将替换并要求确认；拒绝则不改动；关闭后恢复原插件设置。
- WorkBuddy 三种识别状态：无法识别时报错且不创建文件；已识别但无配置文件时新建；已有配置时合并写入。企业版用户作用域与项目作用域分别写入正确文件；项目作用域有同名高优先级条目时，用户作用域写入后报告"未生效"，`connect` 不报告完成。
- 回滚：本工具新建的配置文件被用户追加了其他 server 后执行 `disconnect`，只删本安装条目、保留文件与其他 server；文件仍只含本安装内容时整文件删除。
- 旧安装升级：无 `instance` 的 Codex 旧安装升级后令牌、连接名与任务绑定不变；DSH 旧安装只有一个 profile 有条目时映射到该 profile；两个都有或两个都没有时要求选择，非交互下不升级且原安装照常工作；未继承身份的 profile 新建安装后，其条目归属新安装。
- 真实宿主验收：在选定版本上确认宿主实际列出并调用了 `jiuwen-memory` 的工具（开启 hook 的确认实际触发了召回与写入），留存版本号与脱敏样例；只验证配置文件内容不算通过。
- MCP 工具说明随 hook 开关变化；hook 与 MCP 同时开启时，同一轮不会产生重复的任务事件。

**宿主记忆同步（D15）**

- 授权：未授权时 `sync` 拒绝执行且不打开任何宿主文件；授权展示来源根、数据类型、目标空间与可见人群，`profile` 类单独提示；授权后才执行 dry-run。
- dry-run 不调用 Embedder 或 LLM（出站清单为空调用）、不写入。
- 范围校验：读取器只能经受限访问接口打开文件；来源根内指向根外的符号链接**不被打开**并记入跳过清单（按接口记录的已打开文件核对）；扩大目录、加入 `session_turn`、更换目标空间时要求重新授权；定期同步不越出授权范围。
- 授权版本：dry-run 后撤权或更换目标空间，再确认写入被拒绝并要求重新 dry-run；同步进行中撤权，扫描开始、恢复每条操作、每个缺席项、每批待清理、每条写入前后都重新核对当前授权；写入检查与 `_add_sync()` 在同一 `installs/<id>/grant.lock` 临界区，撤权写入使用同一把锁，未提交的批次停止、已提交的如实报告；撤权后已排队的定期同步与 Hermes 镜像不再提交。清理项的最终授权检查与删除在同一 `installs/<id>/grant.lock` 临界区内完成，授权写入也使用同一把锁，避免检查通过后、删除执行前插入撤权。
- 可见人群：授权后向目标空间新增成员，`sync status` 显示与授权快照的差异；新成员能召回已导入内容这一点在授权提示中已说明。
- 撤销：`sync revoke` 后定期同步停止；先授权目录 A、再改为 B 后撤销并选择删除："当前范围"只删 B 导入的记忆，"全部历史"同时删 A 与 B，确认界面按目录与空间列出条数；非交互环境未指定范围时拒绝执行。
- 账本身份：同一安装先后同步 A、B 两个目录的同名 `USER.md` 得到两组记录、互不覆盖；同一来源改导入另一个空间得到新记录，不被旧摘要跳过；相同正文出现在两个 profile 各保留一份；同一根下 `USER.md` 与某天日志含相同文本、两天日志各记同一事实，都是独立记录。
- 共享输出：内核去重把两条来源合并到同一单元后，删除其中一条来源对应的记录不会删掉该单元；两条都删除后才删除。
- 稳定标识：在 `MEMORY.md` 中间插入一条、重排条目后再同步，已有条目全部跳过，只新增插入的一条。
- 不推断替换：从 `MEMORY.md` 删除事实 A 同时新增无关事实 B，未加 `--mirror-deletes` 时同步后 A、B 都在，A 列入"源端缺席"；修改 `USER.md` 某一条目后同步，只有该条目被替换，其他画像条目保留。
- 多输出：一条会话来源抽取出多条记忆时，账本记下全部输出；该来源内容变化后，旧输出全部被替换。
- 崩溃（本版默认后端）：一条会话来源写出部分产物后 kill 服务，重启后已有产物保留、该来源状态为 `unconfirmed`、模型抽取调用次数不增加；一条会产生多个单元的确定性直写来源（如 `USER.md` 的多个条目）部分写入后 kill，产物满足统一删除条件时清理后整批重写，结果与一次写入相同；替换时新输出已提交、旧输出未删完即 kill，重启后继续删除旧输出，不重写新输出；部分写入的单元被人工编辑过时置为未确认、不删除；存储不支持精确元数据查询时置为未确认且不重写。
- 并发：手动同步、定期同步与 Hermes 镜像同时处理同一来源，最终每条来源只有一组输出。
- Hermes 镜像：同一条 `MEMORY.md` / `USER.md` 条目先经 `on_memory_write` 镜像、再经文件扫描读到，账本只有一条记录、只写入一次。
- USER 旧账本迁移：升级前只同步过整份 `USER.md`（`:file` 来源行）的安装，首次全量扫描出现按条目的新项时，旧 `:file` 行按替换处理，旧引用进入待清理并按统一删除条件清理，不依赖 `--mirror-deletes`；旧行不会阻塞判删或与新条目长期并存。
- 判删：`--mirror-deletes` 下，`--since` / `--limit`、文件读取失败、未知格式、中断、来源根暂时不可访问，均不删除任何记忆；完整扫描后缺席超过一半时要求确认；导入后被人工编辑过的输出不被删除也不被替换。
- SQLite 读取：宿主持有写事务时，读取器在 2 秒内返回一致快照或报告该范围跳过，不阻塞宿主。
- 每家读取器用实测样例覆盖：Hermes `MEMORY.md` / `USER.md` 与 profile 目录；WorkBuddy `USER.md` 与每日日志，且 `SOUL.md`、`IDENTITY.md` 不被导入；Codex `memories_1.sqlite` 与 rollout；DSH v4 会话可读、未知版本跳过并报告。
- 导入的记忆带 `source_app`、来源根与稳定条目标识，其他已连接 Agent 可在目标空间召回；原作者只作为声称作者保存。
- 单条写入失败不影响其他条目；只有确认未产生写入的失败在下次同步自动重试，结果未知的失败进入恢复规则或 `unconfirmed`，不自动重写。
- 复用既有单元：先经 MCP 手工写入一条记忆，再导入相同内容（内核去重复用了该单元），之后撤销导入并选择删除，原记忆仍可读；`--mirror-deletes` 判删、替换清理与崩溃恢复对它同样只解除关联。
- 共享输出的并发：B 停在"已复用单元 U、尚未登记引用"，同时让 A 解除 U 的最后一个已登记引用并清理；B 登记完成后，U 仍可读，引用数为 1。
- 替换回执恢复：`USER.md` 从 A 改成 B，在拿到内核回执、尚未写本地账本处中断；重启后按回执登记 B 并进入 `cleanup_pending`，A 按统一删除条件清理，最终只剩 B。
- 内容回到旧值：`USER.md` 经历 A → B → A，第三次写入使用新的同步操作标识，不复用第一次的回执；第一次的 A 已被清理时，第三次重新写入 A，账本不指向已删除单元。镜像删除后原文重新出现同理。
- 进程退出后的清理顺序：B 已复用 U、回执已提交、引用未登记时服务退出；重启后 A 的删除请求先到，服务先恢复 B 的 `writing` 操作再清理，U 仍可读；B 的操作无法恢复（`unconfirmed`）时，该空间的删除被推迟并在报告中列出。
- 空间级恢复与顺序无关：同一空间内一条操作有回执未登记、另一条为部分写入的确定性直写，交换两者的遍历顺序执行恢复，最终引用登记与可读单元一致；若再有一条 `unconfirmed`，部分产物的清理也被推迟。
- 双未确认下的丢弃：同空间 A、B 都未确认，B 复用了 A 创建的单元 U 但引用未登记；用户先 `discard` A，U 不被删除，待清理项中记录 U；随后 B 恢复出对 U 的引用，U 仍可读、未置保护标记；之后 B 的来源也被清理且 U 未被编辑时，U 正常删除。
- 人工收尾保留事实：`abandon` 保留的单元，以及 `discard` 因已被编辑或无法证明归属而保留的单元，原始归属不变并带删除保护标记，之后任何同步路径都不删除它；`discard` 仅因其他来源引用而保留的单元不带保护标记；`adopt` 一次替换的部分结果时，选择"保留旧版"后旧版受保护且仍可读，选择"清理旧版"后进入 `cleanup_pending` 并按统一删除条件清理。
- 未确认的处理闭环：一条会话抽取进入 `unconfirmed` → 重启 → `sync status` 列出该操作与被阻塞的待清理项 → 用户 `sync resolve --action abandon` → 其他来源被推迟的替换清理与判删按统一删除条件恢复执行；被放弃操作的产物仍可读。`adopt` 与 `discard` 各覆盖一次，`discard` 只删除满足统一删除条件的产物。
- 部分写入的统一语义：确定性直写的来源在已发现产物全部满足删除条件时清理后重写，结果与一次写入相同；会话来源部分写入后一律置为 `unconfirmed`，不使用冻结抽取结果（本版没有），也不重新抽取。
- 全部复用后中断：一条来源的输出全部来自去重复用，`add` 返回后、账本落盘前中断；重启后有回执时恢复原清单（含复用项）且不重写，无回执时置为 `unconfirmed`，不重发。
- 共享输出的删除顺序：来源 A 创建单元 U、来源 B 复用 U；先删 A 再删 B、先删 B 再删 A 两种顺序，最终都在最后一个引用解除时删除 U（U 未被编辑时），结果相同。
- 部分写入恢复的证据：部分写入后被人工编辑过的单元，重启后不被删除，该来源置为 `unconfirmed`；后端不提供权威查询或创建时归属字段时，同样置为 `unconfirmed`。
- 索引不可见：数据已写入真源、索引尚不可见时中断，重启后经权威查询识别已有产物，不重复写入；改用只查索引的路径时置为 `unconfirmed`，不重写。
- 检查后编辑：删除前检查通过、删除执行前用户编辑了该单元，条件删除失败，单元保留。
- dry-run 绑定内容：预览后宿主改写 `USER.md`、新增会话或清空目录，确认执行时检测到差异并重新展示；`--mirror-deletes` 下只删除用户确认过且重算仍成立的条目。
- 入口与授权单：从 `/local/sync` 进入、使用真实安装对象执行；请求体中的目录、项目、会话参数超出授权单时被服务端拒绝或忽略，以授权单为准（CLI 确认不能替代这层检查）。
- 缺席保留：未加 `--mirror-deletes` 时，源端缺席条目的记忆与账本关联都保留，下次源端恢复该条目时仍能识别为同一条。

**本机 Agent 扫描与自动接入（D16）**

- 安装后询问：交互终端执行 `init`，完成后出现扫描授权询问，默认"是"；非交互环境执行 `init` 不扫描，只输出提示命令。
- 只看路径：用伪造的用户目录覆盖四家宿主，扫描过程中被打开读取的文件数为 0；扫描结果文件中不含任何宿主文件内容。
- 识别与实例：Hermes 两个 profile、DSH 两个 profile、WorkBuddy 社区版与企业版分别识别为独立实例；只有目录、缺少特征的标为"疑似"且不自动接入；`dsh` 命令不可用时标为"已发现、无法接入"。
- 批量接入：首次确认后四家全部接入，其中一个实例的配置文件不可写时，其余实例照常接入并在报告中列出失败项；重跑后续做失败项，不重复建安装。
- hook 默认值：扫描接入后只有 Codex 的 hook 开启，DSH、Hermes 不安装代码插件。

- 新实例自动接入：新建一个 Hermes profile，下一次周期扫描后自动接入并在 `status` 中报告；`auto-connect off` 后不再自动接入，只列出。

- 扫描边界：用户追加的目录中有跳出该目录的符号链接、`node_modules`、超过深度上限的层级，均不被进入，报告"未扫完"；macOS 上追加"文稿"目录且系统拒绝访问时报告跳过。
- 回流不导入：hook 召回注入的标记块被宿主原样写进其自带记忆文件后，再次同步不新增单元；去掉标记、正文与空间中他人创建的单元完全相同的条目只登记引用，不新写，撤销同步并选择删除时该单元保留。
- 自带记忆提示：接入确认页按实际探测结果显示宿主自带记忆是否开启；未选择接管时，agent memory 不修改宿主的自带记忆设置。
- 接管条件：hook 未开启、配置项待实测或后台自动接入时，确认页不出现接管选项。
- 接管顺序与恢复：选择接管后先完成同步再关闭自带记忆，宿主原记忆文件不变；同步失败时不关闭。`disconnect` 后自带记忆配置恢复原值；用户在接管期间手动改过该配置项时保留用户的值并报告。
- WorkBuddy 项目日志：追加一个含 `.workbuddy/memory/` 的项目目录后，该目录成为用户级 WorkBuddy 安装同步授权中的候选来源根，项目里不新增任何文件。

- hook 路径的 `continuity_receipt_status`（D8）仍是"不在 `MemoryAPI` 上、服务按 `getattr` 探测"的可信进程内端口，与 D15 本次收口前的 `operation_receipt` 同形；是否同样声明为显式能力另行决定（D8、D15）。
- 创建归属键 `sync_created_by` / `sync_initial_digest` 自 D15 收口后对任何 `add` / `batch_add` 调用方（含 MCP）开放：伪造只能往自己的新单元上盖一个对不上任何操作标识的标记，影响不了判删；原先"普通 `add` 直接拒绝"的那层纵深防御不再保留（D15）。
- 写入调用中途抛异常（部分项已提交、后续项因后端故障等非逐项错误中止）时**不记回执**：调用方按同一 `operation_id` 重发会重复写入已提交的项。单条 `add` 同样如此（回执只在调用成功返回后登记），不是批量回执新引入的；同步引擎自己对缺回执的写入只置 `unconfirmed`、不自动重发，但通用调用方（如 MCP Agent 重试）没有这层保护。回执持久化与"提交即登记"一并列为遗留（D15）。
- 批量回执的重放判据只比较各项正文：同一 ID、同样正文但换了逐项 scope / metadata 时照样重放首次结果、不报冲突（首次结果里各项的落点会被逐项复核写权限，所以不是越权，但调用方不能靠重放改落点）。注意单条 `add` 比这严——它把请求 scope 的各维与回执 scope 逐一比对，换 scope 会被拒；批量只比对批级 scope，逐项 scope 的变化检测不到（D15）。
- 没有批级 `scope` 的批量写入，回执记在空 `Scope()` 下：重放时的 scope 比对全部放行，只靠逐项授权兜底；`operation_receipt` 是精确匹配，这类回执必须用 `Scope()` 来查，按某个真实空间去查会落空（D15）。
