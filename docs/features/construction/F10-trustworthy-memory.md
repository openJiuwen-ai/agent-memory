## 背景

可信记忆要解决的是：对于当前提问者、问题时间和使用场景，一条已召回记忆是否适用、依据是什么、应以什么确定程度表达。主要面向知识更新、历史查询、多源冲突、推断偏好以及源证据纠错；不新增记忆 tier，不另建平行记忆系统。

采用“受控来源与证据 → 时间适用性 → 认知评估 → 可信披露 → 纠错闭环”的方案。来源可信、内容完整、事实正确是不同判断：用户明确说过不代表客观正确；系统签发的 MAC 不证明原始作者身份；未经校准的评分不能宣称为正确概率。

## 决策

### 1. 最小闭环与明确范围

第一版必须同时具备来源标签、认知状态、世界时间提示、依据回指、保守冲突处理及披露标签，否则只有时间重排仍会把推断当事实。先提供可解释的规则评分，再以标注数据校准。签名、跨 Scope 证据依赖和完整系统历史回放分阶段交付。

全部记忆类型可携带可信描述，但只有已接入并通过契约测试的写入、演进、检索路径才声明支持可信模式。未覆盖的 Schema、层级摘要、文档编辑、经验或技能路径不能仅因字段可序列化便宣称完整支持。启用 profile 时按实际路径校验能力；不支持则启动失败或明确拒绝该操作。

可信模式默认关闭，旧 profile 的行为不变。可信模式下，旧记录标为 unknown，禁止自动提升为 stated、高可信或已验证。停用后不删除已保存的可信描述，但调用方必须知道本次结果没有经过可信复核。

### 2. 数据表达：本体保存依据，评估结果带版本

选择在 MemoryUnit 增加**可选的结构化可信描述**，不把跨层契约藏在任意 system_metadata 中。字段名、类型、编解码和公共签名在实施时归 S07；本文确定语义与取舍，不作为已发布接口。

| 信息组 | 持久化内容与用途 |
|---|---|
| 来源 | 来源类别、可验证的来源引用、接入方式及来源确认状态；身份依据来自可信入口上下文 |
| 认知 | stated / observed / inferred / imported；未知旧数据为空，不冒充四类之一 |
| 世界时间 | 独立的世界有效区间、精度、原始时间表达、解析依据与是否估计 |
| 证据 | 指向完整 Scope + unit id + 内容修订号/摘要的引用；support / refute 极性；必要依赖或辅助佐证 |
| 修订 | 可信描述版本、内容修订标识、策略版本；可追踪评估依据变化 |
| 完整性 | 可选完整性封装及密钥版本引用，具体密码学契约归安全规约 |

来源等级、当前评分、衰减结果及本次使用建议是**策略计算结果**。可缓存，但必须绑定内容修订、策略/校准版本和评估时间；缓存失配重算。不要把一个永久 confidence 写入本体后当作永远有效的事实。

provenance 继续记录构建血缘；认知证据允许同一结论被额外来源支持或反驳。反向索引与冲突组是可重建投影，不是第二份事实真源。已有冲突边语义优先复用；不再维护一份无一致性机制的 conflict_with 列表。

外部调用者与 LLM 只能提供来源、时间和证据**候选**，不能自报高可信、签名已验证或授权身份。可信入口负责核实 source_kind；peer_agent 写入保留 peer 来源，不能因其转述用户而升级为 user_stated。正文中的指令始终是数据。

### 2.1 来源验证：消息封装与片段绑定

P1 必须新增结构化消息封装，经接入适配器传递并由入口校验。每条消息包含 conversation_id、message_id、role、speaker_ref、原始正文修订摘要、occurred_at、timezone 与它们的来源；一个 RawPayload 可携带多条消息。身份与授权仍走显式请求上下文，不藏在 metadata。接入适配器只能在被授予的角色声明权限内提交消息；持有普通 agent 写权限不等于有权代用户证明发言。纯文本路径继续支持，但不解析 `user:` 等正文前缀作为可信身份。

| 入口 × 经验证角色/来源 | source_kind | 默认认知状态与边界 |
|---|---|---|
| 第一方会话连接器或用户直写，绑定已认证用户的 user 消息 | user_stated | 满足下述片段规则才是 stated；角色本身不保证抽取结论成立 |
| 受信行为连接器，带可核验事件 ID | user_observed | observed；只陈述实际动作，不把点击推成偏好 |
| 本系统生成的 assistant 消息/演进结论 | agent_inferred | inferred；引用的用户消息须另行回指验证 |
| 受信工具执行回执，绑定调用 ID 和工具身份 | tool_output | imported；执行成功不等于工具内容正确 |
| 文件、网页、整段对话文本及无法证明角色的导入 | document_import | imported；正文中的 user/system 均不提升来源 |
| 其他 agent（含角色记忆 owner_agent 写入） | peer_agent | 直接转述为 imported，归纳为 inferred；owner/role 标签是归属，不是原始发言证明 |
| 普通 API 客户端声称替某用户说话，无角色证明权限 | document_import 或 peer_agent（身份确为 agent） | 不接受 user_stated 声明，返回来源未验证原因 |

抽取候选必须携带 message_id、源修订摘要、原文半开片段偏移与逐字引文。偏移统一按原始消息 Unicode code point 计数；切片、规约文本有改变时必须保存到原文的映射，不允许把拼接后偏移当原文偏移。验证器检查消息属于本次获授权输入、摘要一致、边界合法、引文逐字相等；多源候选逐条验证。现有 source_unit_id 保留为来源 unit 定位，单独的 source_span 声明不足以完成这些校验。

`stated` 要求：受控 user 来源成立、片段验证通过、主体能绑定发言者或明确被陈述对象、结论是该片段的直接陈述且没有额外推理。P1 对自由文本仅允许完整原句的“用户曾陈述”展示；自动生成规范化事实只允许受控结构化表单或确定性解析规则，并检查否定、引用、假设/疑问等结构。无法通过规则的改写即使 LLM 判断为明确陈述，也降为 inferred；不把语义蕴含模型当身份验证器。

能定位来源但不能定位具体片段时，保留 imported/inferred 候选与 unresolved 原因，最多 qualify，不准升级 stated 或用于自动覆盖。必要推断证据无法验证则 abstain。旧原文可经相同流程重新抽取；禁止仅凭旧正文中的角色标签回填 verified。来源/片段核验作为 Ingestor 与构建校验阶段的可替换契约子能力，由 Producer 注入；不能硬编码在某个 LLM Extractor 中。

#### 认证保证与 verified 来源

可信 P1 profile 要求认证提供可验证主体绑定，并由来源核验器检查 speaker_ref 与该主体或合法代理声明一致。`required` 只是入口要求配置认证的模式，不是用户身份已验证的证明。当前实现对应关系如下；核心通过新增的认证保证声明与请求级验证结果判断，不按 target 名写分支。

| 当前认证实现 | 可信来源资格 |
|---|---|
| dev（固定或 identities 映射） | 无主体证明能力；可信 P1 profile 装配拒绝。默认 local/developer 及测试选择器都不能产出 verified user |
| api_key | 验证有效凭据绑定的主体；只有 user 主体且消息属于本人，或具备显式代理发言证明权限，才可进入 user 来源核验；agent/admin 身份不自动证明任意用户发言 |
| trusted | 必须有受保护网关通道、网关注入并覆盖身份头、已注册主体及可验证消息声明。仅有可由客户端伪造的头不够；可信参考部署要求 gateway_key 与隔离直连的部署保证 |
| 第三方认证 | 显式声明主体证明/代理声明能力，提供请求级核验结果，通过同一契约测试后接入 |

缺少保证声明的旧认证插件不能靠配置声称 verified。认证插件负责证明 actor，连接器仍须证明消息角色和归属，两道检查缺一不可。dev 可继续运行普通非可信 profile 用于本地功能测试，其数据迁入可信 profile 后仍为未验证，不能因重新读取而升级。入口的默认认证策略不在本特性中改写；认证保证扩展同步进入既有安全 spec/F04。

### 2.2 现有 confidence/evidence 的迁移

现有 confidence 是模型对抽取支持程度的自评分，evidence 是模型生成的文本，并非可定位证据。当前实际存于 system_metadata，不能误称为 user_metadata；它们仍缺少可信协议类型与验证语义。

- 可信 profile 将旧字段只读映射为 legacy extraction diagnostics，保留原值和生成器版本，不映射为可信概率、stated 或 verified evidence。新输出使用结构化诊断区，与可信评估区隔离；旧键只为兼容读保留，不双写为两套权威状态。
- 默认非可信 profile 保留现有 min_confidence 行为。可信 profile 同步修改抽取/摘要 prompt，取消“只输出 0.5～1.0”的约束，允许低支持候选并要求单独输出认知候选与来源引用；旧 confidence 仅作可选诊断。可信 profile 禁用**按 LLM confidence 阈值提前丢弃**：通过结构和片段校验的低分候选进入有界待评估区；准入由 TrustEvaluator 决定。配置同时要求旧阈值过滤与可信证据完整性时装配失败，不能悄悄两者并用。
- 不把“保留低分候选”等同于立即发布记忆。每条来源消息最多接受 16 个候选；超额返回 extraction_partial 并保留原文回放游标。无效结构/越界引用明确拒绝并记录原因。原始证据保留期由治理策略控制，过期后不能承诺可重放。
- Abstractor 同样执行该规则；摘要必须绑定验证后的证据，而不是把模型 evidence 字符串直接当引用。迁移验收覆盖 0.4 候选保留待评估、旧键不提升可信、原文重新抽取及证据缺失。

### 3. 插件边界：复用主链路，新增少量独立能力

不新增一套万能“可信引擎”。Control 仍协调跨层业务；现有 Evolver、Retriever、IndexBuilder 和 DomainStore 承担各自完整责任。以下名称是拟议契约角色，不是当前可用 target。

| 角色 | 所属层与责任 | 依赖及替换方式 |
|---|---|---|
| TrustEvaluator | common 的纯评估子能力：合并来源、认知、证据状态，输出评分、使用建议与原因 | 注入来源策略与可选校准器；不自行读取存储或调用鉴权 |
| TemporalInterpreter | common 的时间解释子能力，供构建与 QueryParser 共享时间规则 | 输入原始表达、真实消息时间、时区；输出区间、精度、歧义；规则与模型实现可替换 |
| ConflictResolver | 复用 construction 现有契约，只提出更新/冲突处理决策 | 输入由上游核验的证据；LLM 候选不能自行决定覆盖 |
| EvidenceReader | storage 领域门面的拟议 capability：有界证据展开与反向依赖查询 | 从同一 StoreManager/DomainStore 获得标准端口，不另配私有数据库 |
| MemoryIntegrity | common/security 的可选子能力：保护和验证记忆修订 | 显式注入具名 KeyProvider；安全设计只维护到既有 F04 |
| 可信检索组合 | 现有 Retriever 的组合实现，完成物化、复核、评估、排序和披露的完整责任 | 注入上述能力及现有 Parser/Fuser/Reranker/Discloser；子能力不能直接充当 Retriever |

来源权重、拒答阈值、证据上限属于策略参数，不为每个阈值创建插件。级联纠错是 Control 调度的工作流，复用证据端口与构建提交能力，不创建第二套调度器。证据算法若有不同后端，只替换门面背后的实现。

#### S09 装配要求

- 各新增能力采用契约与 Producer、实现目录分离的模式；实现加载后注册，配置选择 target，再解析依赖、构建、health。调用方不 import 具体实现、不按 target 分支。
- profile 显式引用具名 evaluator、temporal interpreter、领域存储及可选 integrity。默认实现也走同一装配路径；示意依赖是 `Retriever/Evolver → evaluator + temporal + 同一领域存储`，不是可直接运行的新 YAML。
- 组合顶层必须校验所需能力集合；纯评分器不能替代完整检索阶段。启用 strict integrity 却无验证端口、启用 cascade 却无可靠反向依赖能力，都在装配时失败。
- 同一装配内共享存储、客户端、KeyProvider 和校准器状态；具名缓存归装配上下文，跨装配隔离。插件不能匿名构造有状态依赖。
- 能力声明在实例生命期内稳定。暂时故障由 health/错误报告，不能动态撤销能力或换成默认实现掩盖故障。
- 运行时可刷新策略值，但依赖拓扑变化必须重建。缓存按策略版本失效。
- 装配根持有生命周期所有权，按对象身份去重，先关使用者再关依赖；借用资源不关闭，启动失败仅清理本次新建资源。

### 4. 写入与演进：先核验依据，再提交

流程：入口身份与 Scope 校验 → Ingestor 规约来源 → Extractor 提出认知/时间/证据候选 → 构建层验证引用与条件 → ConflictResolver 提案 → 计算可信描述 → IndexBuilder/领域存储提交 → 更新派生索引。

Ingestor 不落盘；Evaluator 和 Resolver 不落盘；API 不负责演进编排。直接 add、update、批量导入、文档编辑与后台演进也必须通过相同的可信提交校验，不能只改 Extractor 而留旁路。

| 情况 | 处理 |
|---|---|
| 同一主体、属性、条件，可信同源明确更正且时间可比较 | 复用 SUPERSEDE，保存前驱与更正原因 |
| 不同条件、不同时间段或非互斥属性 | 并存；补充信息不自动判为冲突 |
| 相互矛盾但无确定裁决依据 | 保留双方，形成未决冲突；不按“最新”“来源分高”强行覆盖 |
| inferred 获得新支持或反驳 | 生成新的评估修订，保留证据变化；不重复累计同源转述 |
| 用户明确否认自己的偏好推断 | 经身份和指代核实后撤销该推断；否认第三方客观事实只增加反证 |
| 低于可用阈值 | 标记需复核/不建议使用；不凭负证据自动生成反向事实 |

主体、属性和条件无法可靠识别时，保守并存。第一版只对可结构化匹配的事实执行自动取代；自由文本语义冲突识别可以输出待复核候选。

### 4.1 P1 匹配键与覆盖范围

P1 的**自动取代、结构化冲突判定与属性时间线仅覆盖扩展后的 Schema entity/property 路径**，且实体绑定、属性值和更正意图必须分别通过验证。现有 LLM Schema 路径不直接具备该资格；得到 canonical entity id 不等于实体身份已确认。普通记忆仍获得来源验证、认知标签、证据评估与显式时间参考，但不因文本相似就参加自动取代或伪装成完整属性历史。

拟议 ClaimKey = 完整 Scope + canonical entity id + schema/property 定义版本 + property name + 条件规范化摘要。条件来自受控 schema（例如地点、适用角色）；枚举、单位、大小写及空值按该 schema 规范化，排序后摘要。未知条件不同于已确认的空条件；未知时不能建立可自动裁决的键。property 定义须声明 single/multi-valued；只有 single-valued、同键、世界区间重叠且值不相容才成为冲突候选。value 不进入键，世界区间单独比较。

P1 必须交付下列 Schema 扩展，而非假设现有配置已经提供：每个属性的 cardinality（single/multi）、value 类型与确定性规范化规则、允许的条件键/类型/枚举、空条件与未知条件语义，以及可自动取代的来源/更正规则。可信 profile 缺这些声明时装配拒绝对应自动裁决路径；旧 schema 继续用于非可信抽取。复用现有 catalog 内容哈希 schema_version，将新增声明纳入规范化哈希并随 ClaimKey/修订保存；不另造无关版本号。版本变化不自动跨版本合并，只有显式、可审计迁移才能重建键。

#### 实体确认与取代资格的两道检查

第一道是实体绑定：仅接受经过授权的稳定外部主键映射、认证用户到其本人实体的绑定，或用户/管理员确认的实体链接。现有 `_exact` 名称匹配也不能替代这道检查，同名不同人必须保持独立。语义召回和 LLM 合并只生成 link proposal；未确认时分配临时实体，不修改 canonical registry、不改既有 Property 的归属、不参与自动冲突或取代。确认须记录来源、操作者、目标实体及修订并检查权限；已有 LLM 合并产物在迁移时标未确认，不能沿用其 canonical id 自动升级。

第二道是属性与更正验证：LLM 可以提出 property/value/时间/更正候选，但只有受控表单、已登记的确定性文本解析规则或用户确认结果，才形成可执行的更正指令。指令绑定明确目标修订、已确认实体、属性、条件、新值及世界时间依据。规范化后的值必须能按规则回放到验证片段；仅有逐字引文并不能证明改写值正确。

| 输入/验证结果 | P1 行为 |
|---|---|
| 已认证本人通过结构化属性编辑提交，实体由本人绑定，明确更正目标版本 | 校验 schema、Scope、并发修订后自动 SUPERSEDE；保留直接陈述及操作依据 |
| 对话命中已登记的确定性更正规则（含否定/引用检查），实体和目标均确定 | 同上；不依赖 LLM 判断才能生效 |
| 对话经 LLM 改写为 Schema 值，未通过规则 | inferred 候选；并存，不自动取代。返回 proposal 供用户确认规范化值、实体及目标 |
| 用户确认 proposal | 新增确认事件作为直接依据；重新检查身份、schema 与目标修订后执行，不把原始模型推断追溯性改成 stated |
| 实体只是名称相同或被 LLM 判为同一对象 | 仅建议链接；不形成自动裁决 ClaimKey，不能误合并后再交 Resolver“兜底” |

因此 P1 **不承诺任意自然对话的全自动知识更新**。可落地路径是结构化编辑、有限确定性对话规则及“模型提案→用户确认”；通用语义自动更新另需经验证的判断机制。确认交互由 entry/adapter 暴露，API 接收结构化确认意图，Control 执行；插件负责提出和验证候选，不自行修改本体。Entity binding/claim validation 必须作为显式契约子能力注入 Schema 组合实现，不能只关闭 LLM merge 开关而继续信任名称匹配。

来源去重另用 OriginKey = 来源命名域 + conversation/event id + message id + revision + 片段范围；有经验证的原始来源链才合并跨 agent 转述。不能凭相同内容去重不同独立证词，也不能把 ClaimKey 当作来源独立性依据。无法证明独立来源的重复证据进入同一 unknown-origin 组，不能累加支持。

普通记忆无键：并存、独立展示，不做属性时间线；仅对明确指向同 Scope 目标 ID/修订的受权更正执行定点修订。语义相似只用于提示“可能相关”，不建立自动取代/冲突边。跨 Space 即使 entity 同名也不合并键。后续通用 ClaimNormalizer 需独立契约与验证数据，列为 P2 之后扩展，不在 P1 中隐式实现。

### 5. 时间：不破坏已有 as_of 语义

已有 t_valid/t_invalid 与 as_of 保持现有兼容语义。新增世界有效区间专门回答“现实中何时成立”，避免将存量系统记录时间直接当作搬家、入职发生时间。系统获知时间保留 t_ingest；**仅凭 t_ingest 与 supersedes 无法恢复被原位改写前的认知状态**。

第一版仅对通过历史能力门禁的 Schema 属性路径支持世界时间 latest / snapshot / history / range 的显式意图，复用 Schema 分支已有的时间解析经验，但不把 Schema 专用过滤原样套到普通记忆。完整“在某天系统当时知道什么”需要修订历史及系统历史查询契约；P1 虽保存证据修订，第二阶段之前仍明确不支持该查询，不能用当前修订伪造历史回放。

- 世界区间采用半开区间；精确点生效的属性可确定闭合前驱区间。
- “上个月”以实际来源消息时间和时区解析成月区间，保存月精度；不伪造月初某一天发生变化。查询落入变化的不确定区间时，返回不确定或冲突提示。
- 时间未知时保留未知；允许用于当前参考，但不能当作确定的历史答案。若展示以摄入时间估计的区间，必须标为估计。
- 问“去年在哪工作”默认是范围问题，可能返回多段任职；不能任取去年某个时间点。问“搬家之前”且无可定位事件时标记时间歧义。
- 查现实历史须能取到 SUPERSEDED 前驱，不能先套当前 ACTIVE 过滤删掉旧版本。该模式必须显式采用历史候选与复核策略，不隐式附加“系统当前有效”的过滤；仅用户显式给出系统 as_of 时才与世界区间联合收窄。这个调整同时覆盖下推和真源复核，不能只修改 Parser。遗忘、撤销、权限限制仍生效；历史查询不恢复已撤销的可信资格。
- 世界时间过滤、系统 as_of、事件窗口独立组合，用户条件只做 AND 收窄。索引下推与本体复核使用同一语义。

例：10 月收到“9 月搬到深圳”，查询 8 月应支持北京，查询 10 月应支持深圳；查询 9 月某日因缺少确切搬家日期不能断言。查询“9 月系统是否已经知道深圳”则属于系统历史，第一版明确不支持。

### 5.1 时区来源与相对时间

当前 RawPayload 仅有 occurred_at，公共 as_utc 将 naive 时间解释为 UTC；这是兼容事实，不能据此推断用户使用 UTC。可信消息封装新增 IANA timezone（优先）或显式 offset、time_origin 与 timezone_origin。优先级：受控消息原始时区 → 会话显式设置 → 已授权用户配置；组织默认只能标为 assumed，不能覆盖消息明确时区。时区设置由本人或获授权管理员维护，不能从正文中的“timezone=...”读取。

先在来源本地日历解释“上个月/昨天”，再把区间端点转 UTC 用于比较和索引，同时保存原时区与精度。aware occurred_at 的 offset 可用于该时刻的日历计算；跨夏令时边界需 IANA 规则，缺失则标歧义。naive 时间只有在具有经验证时区时才本地化；不存在/重叠的夏令时时刻需明确 offset，否则 unknown。无时区、只有假定默认值或无消息时间时，不给相对时间生成确定世界区间，也不用机器当前时间替代。

验收：`2026-10-01 00:30 Asia/Shanghai` 的“上个月”是本地 9 月区间，即 UTC `[2026-08-31T16:00Z, 2026-09-30T16:00Z)`；不得先转换为 UTC 后按 9 月 30 日计算成 8 月。另覆盖无时区与 DST 歧义。

### 5.2 前驱保留矩阵与装配门槛

以下是代码静态核对，不是后端集成测试结论。保留本体、索引可发现与灾后可恢复是三种不同能力。

| 后端/写入组合 | 当前前驱本体 | 历史发现与恢复限制 | 可信历史模式门槛 |
|---|---|---|---|
| InMemory KV + forward/hybrid | SUPERSEDE 保留旧对象；forward 的 SOFT 不删本体 | 向量/全文 SOFT 可删投影；进程退出无持久历史 | 仅测试 profile，需同 Scope 历史枚举/点读适配；不能承诺持久恢复 |
| SQLite KV + forward/hybrid | 同一 KV 写入语义保留前驱，直到显式清除 | 当前检索索引不能代表全部历史，尚无可信修订/快照协议 | **P1 唯一持久参考后端**；交付下述领域事务及历史端口，通过重启/重建测试后开启 |
| Postgres KV + forward/hybrid | 由领域/IndexBuilder 生命周期决定保留，不因数据库名称自动具备历史 | 需验证隔离、分页与一致性读取，未做实后端验证 | 同上，未验证拒绝历史 profile |
| Redis KV + forward/hybrid | 正常更新路径保留前驱键 | 还受过期、淘汰及持久化配置影响 | 禁止历史键自动过期/淘汰，并通过恢复测试；否则拒绝 |
| encrypted KV 包装 | 继承底层保留语义 | 历史密钥可用性是额外条件 | 底层历史能力与密钥保留均满足，不因包装自动增加能力 |
| 文档 md + SQLite shadow（document/unified） | SUPERSEDE 删除 md 旧块；shadow.update_units 可暂存旧 unit_json | 文档 SOFT 通常为空操作；shadow 暂存不等于可由 md 重建的历史真源 | **P1 拒绝可信历史模式**；须先增加独立、可恢复的版本存储与历史读取端口 |
| 第三方 DomainStore | 未知 | 不推断实现能力 | 显式声明并通过同一契约测试，否则拒绝 |

因此“SOFT 删除使前驱必然不存在”不成立；但“前驱可稳定历史查询”也没有现成保证。`cloud_engine.py` 中跨 pipeline OVERWRITE 的 SOFT 与 SUPERSEDE 要分别检查，不能混为同一条路径。

装配开启历史模式时必须同时检查 predecessor_retention、scope_history_enumeration、revision_read、rebuild_preserves_history 及所需 consistent_read 能力，校验所有绑定 pipeline；这些是待定义的 capability 语义，不是当前已存在的标志。声明与契约测试证据相配套，不能启动时用破坏性探测测试生产数据。运行期缺失前驱返回 history_incomplete；禁止伪造连续时间线。生命周期清理后若超出保留窗口，查询明确报告窗口外不可用。

### 5.3 世界区间与索引投影草案

本体采用 world_start/world_end 两个可选边界，每个边界存 earliest/latest（精确时相等）、precision、basis、timezone；空边界另标 open 或 unknown，不能混为一个 None。“9 月搬家”的起始边界是 9 月内的不确定点，不是“只在 9 月有效”。前驱终止边界引用同一次变化边界。支持确定区间与可能区间，避免把月精度压成月初。

索引投影为 world_start_min/max、world_end_min/max（UTC epoch 毫秒）、world_time_state、world_precision 和 claim_key；开放边界使用显式 open 状态及统一极值，未知状态保留单独分支。snapshot(t) 的可能命中为 start_min <= t 且 end_max > t；确定命中为 start_max <= t 且 end_min > t。range[a,b) 以 start_min < b 且 end_max > a 下推可能相交，真源再核验精度与半开端点。未知分支仅作为 qualify 候选，不能计作确定历史答案。

历史候选从领域历史端口读取，不能依赖已移除的普通检索索引；必要时对授权且有 ClaimKey 的历史集合做有界枚举。投影缺失/版本落后不得假装精确过滤：按预算回查本体，不能完成则 partial。所有派生字段由统一 IndexBuilder 投影函数生成，下推和真源复核共享区间规则；新字段的后端适配是 P1 门禁之一。

### 6. 有度：评分可解释，概率须校准

先分别给出来源等级、证据充分性、时间适用性、完整性状态和未决冲突，再输出 `use / qualify / abstain` 使用建议。完整性失败、已撤销等是准入条件，不能乘一个小权重后仍进入答案。来源权重与置信度也不重复相乘。

初始规则实现将证据按原始来源/事件聚类，同源副本只计一次；支持与反驳分别计入有界分数，并保留贡献说明。必要证据缺失优先导致不可使用；辅助证据减少导致重新评估。长时间无新证据的衰减只适用于易变推断，不让历史事件因时间久而变假。当前分支没有经验 Curator/Wilson 实现，本方案不将其作为已有能力或复用依赖。

未有标注数据时仅返回等级与 `uncalibrated` 标志，不给“80% 正确”的承诺。校准器按来源/认知类型等适用域训练与留出验证，输出概率时携带版本与适用域；域外数据回退到未校准等级。阈值由任务风险与 coverage–risk 曲线选择，不凭空固定为 0.8。

### 6.1 评估数据与准入规则草案

拟议 TrustAssessment 包含 subject_ref（完整 Scope/id/revision）、source_grade、epistemic、temporal_applicability、integrity_state、evidence_summary、conflict_state、decision、reason_codes、policy_version、evaluated_at、calibration_status 及可空 probability。evidence_summary 包含支持/反驳独立组数、必要依赖完整性、闭包检查状态与截断原因。访问上下文不放在这个对象中；对外只投影已获授权的解释字段。

默认来源等级为序数 high/medium/low/unknown，不是概率：经验证的用户直接陈述 high（只证明其说过）、受信行为事件 medium、工具回执 medium、文档导入 low、peer_agent low、无法确认来源 unknown。agent_inferred 不设来源高分，从证据聚合得到评价。来源类别不代替主题权威性，high 不能单独触发自动覆盖。

P1 聚合形态是按 OriginKey 分组的 `(support_groups, refute_groups, required_complete)`，不做无依据的概率计算。同组最多计一次；同组同时支持和反驳标矛盾。规则默认“足够支持”为至少一个经验证直接证据组，或至少两个独立 medium 以上观察组；不满足者只能 qualify。此处是可调整的启动策略，不是统计校准结果。

以下按优先级首次命中决定，`use` 意为可按认知标签使用，不代表绝对真实；inferred 即使 use 仍必须说成推断。

| 优先级 | 条件 | 结果 |
|---|---|---|
| 1 | 无权限、Scope 不符 | 不返回该条及其存在性；操作级权限错误按 API 契约处理 |
| 2 | 已撤销、完整性 invalid、确定不在所问世界区间 | abstain，条目不进入回答上下文 |
| 3 | strict 要求验证但 missing/key_unavailable；必要插件失败 | 不准入并返回结构化错误，不能报告正常空结果 |
| 4 | 必要证据缺失/撤销，闭包循环、预算耗尽或一致性未知 | abstain + review_required/partial |
| 5 | 未决冲突或有效反驳组存在 | qualify，显示获授权冲突；要求单值确定答案时整体 abstain |
| 6 | 世界时间未知/仅可能适用、来源未知/low、兼容模式缺签、片段未定位 | qualify，不得当确定事实或自动裁决依据 |
| 7 | 必要证据完整、时间满足问题、无反驳/冲突、来源至少 medium 的直接记录，或 inferred 达到上述支持规则 | use，保留 stated/observed/imported/inferred 标签与未校准标记 |
| 8 | 其余支持不足 | qualify；问题要求确定答案且无 use 条目时给 abstain 建议 |

P1 未配置完整性能力时状态为 not_enabled，只能显示未验证；它不等于 missing，更不等于 valid。未校准本身不阻止带标签的 use，但禁止展示概率。

### 7. 检索与呈现：硬约束先于排序

流程：授权及 Scope 过滤 → 解析时间意图 → 领域召回并物化本体 → 有效期/撤销/完整性复核 → 有界证据读取 → 可信评估 → 相关性与可信偏好重排 → 一对一披露 → 结果分组呈现。

可信评分只在满足相关性与准入条件的候选中起作用；不让“不相关但高可信”的条目占据答案。过滤后不足 top-k 时，按固定预算补召回，达到预算仍不足则返回不足与原因，不谎称没有记忆。冲突对端和必要证据由领域端口定向取数，不要求碰巧同时进入向量 top-k。

每条结果至少说明认知类别、来源类别、世界适用时间、评估等级/校准状态、冲突与完整性状态，以及使用建议。L0/L1/L2 都不能因预算紧而丢掉影响解释的标签；必要时减少条目数量。证据正文只有另经授权且预算允许才展开，拒绝/不存在不能泄漏对端内容、ID 或数量。

Discloser 保持单条塑形约定；结果编排按主体属性及条件分组，组织时间线和冲突集合。提供给回答模型的约定包括：“用户曾陈述”“系统推断”“记录存在矛盾”，不能把 inferred 改写成“你说过”。检索层能给出拒答建议，但不能保证下游模型遵守；评测须分别量化标签正确性与回答执行率。

### 8. 纠错闭环与一致性

区分“旧事实过时”“原事实错误”“证据被撤销”“硬删除”。SUPERSEDE 不代表旧记录有毒，不能让历史摘要因正常搬家全部失效。撤销或证伪才触发可信资格检查；必要依赖失效阻止使用，辅助佐证失效重算，新建且已验证的证据关系若缺依赖类型，按必要依赖处理；存量 provenance 不自动转成认知必要边，迁移规则见下文。

纠错通过已有 update/delete/evolve 语义的受控扩展进入 Control。拟议的“解释依据”和“撤销并纠错”需要在 S02 明确权限与返回结果后才能发布；不直接把新操作名当作现有 API。

提交与恢复采用以下设计要求，具体公开存储 capability 在实施时进入 S06：

1. 按完整 Scope、对象修订及操作 ID 提交，乐观并发校验防止新证据与撤销互相覆盖。一次提交原子记录真源变更、撤销屏障和可恢复任务意图；依赖外部消息队列不是默认要求。
2. 同步阻止被撤销对象及受影响后代继续以有效状态使用，再异步遍历反向依赖。Scope 级证据 generation 可使旧评估缓存整体失效；复核读开始/结束 generation，不一致则重试或返回暂不可用。
3. 反向索引只是加速器；未完成水位或损坏时使用可验证的真源扫描。若预算内无法确认依赖完整性，返回待复核，不能认为“没有依赖”。第一版可以 Scope 级保守阻断，后续再优化到受影响子图。
4. 遍历使用完整身份去重，限制深度、节点数和每批预算，支持环检测、断点与幂等重试。超过预算返回任务 pending，不报告完成；后代评估不可使用状态持续到复核成功。
5. 本体提交后索引更新失败，保留任务重建；报告“真源已提交、投影待修复”。严格可信检索须按本体复核，不凭陈旧索引放行。
6. 后台每轮重新鉴权；授权失效暂停任务。第一版证据依赖限定同一真实 Scope，跨 Scope 只允许受权展示独立记录，不建立可级联依赖。后续开放需同时解决目标 Scope 授权与撤销广播，不能借后台任务扩大权限。

P1 在尚无异步级联和评估缓存协议时，对派生记忆每次读取同步检查完整必要依赖闭包，并使用一致性快照或覆盖整个依赖闭包的读取前后 generation 检查（见 8.1）；循环、超预算或无法确认一致性时返回待复核。不能用缓存结果跳过源撤销检查，也不能宣称已完成后代持久化纠错。P2 才引入上述屏障、缓存与异步工作流优化。

存储不提供原子提交/并发检查或等价恢复保证时，不得启用上述严格纠错模式。不能假设现有各后端已支持事务。软撤销保留最小审计依据，硬删除先处理依赖失效再清正文；清除后只保留合规允许的无正文墓碑，不留“为了溯源”的隐性内容副本。

### 8.1 P1 读取预算与存量血缘

下列是可配置的初始硬上限，P0 基准可调，部署配置必须显式保留上限：请求 k≤50；初次召回最多 2k，最多补召回两轮，每轮最多 2k，总候选≤min(6k,200)。证据检查全请求共享预算：最多 128 个不同修订节点、深度 4、每批点读 32、最多 8 次存储调用、可信附加读取总时限 200ms；整体请求 deadline 更短时服从整体限制。重试也消耗同一预算，不能按每个候选重新计费；P1 不在线调用 LLM 展开证据闭包。

证据检查与来源正文披露分开：优先读取状态/修订，原文另受 token 预算；请求内同一 Scope/id/revision 只读一次。超限返回 partial、具体内部原因和通用外部提示，未完成检查的派生条目 abstain，可继续返回已完成检查的独立条目。真源慢、补召回耗尽与确无候选不能混为一类。

旧 provenance 只保留构建血缘，标 legacy_unverified，不展开成全量必要依赖，也不因其中一条旧源撤销就永久废掉整棵树。旧摘要在兼容模式至多 qualify；需要严格派生证据模式则在迁移前 abstain。后台重抽取生成“结论/句段 → 必要证据”的映射并验证后才进入可信模式。P1 新摘要若无法把一个可披露单元的必要证据控制在预算内，就不发布为 use；可以保留普通摘要并提供已验证叶记录。未知依赖绝不能通过任意截掉来源来变成完整。

P1 的一致性读也属于装配门禁：后端须提供快照或能覆盖整个依赖闭包写入的单调修订/generation 校验。仅逐条点读前后自身版本不够，因为先读的源仍可能随后撤销。P2 增加撤销屏障与异步物化优化，不承担弥补 P1 读一致性缺口的责任。

### 8.2 多 agent、策略覆盖与解释/纠错操作

策略默认 → 组织 → Space → agent 依次细化，权限边界及 strict 下限只能收紧；信任提升须有组织授权的 trust_policy_admin 权限，普通记忆写入权不包含策略管理权。组织管理员可在其组织内委派 Space 管理员；agent 只能选择已批准 profile 或收紧阈值，不能自行提升自己的来源等级。策略修改审计、版本化并使评估缓存失效。具体权限标识是拟议语义，实施时复用现有 Authorizer 资源/动作模型，安全规则进入既有 F04。

peer_agent 历史可信度延后到 P2：以经核实的纠错/验收反馈、按 agent 与任务域统计；不使用 agent 自报成功或记忆数量加分。样本不足保持 low，样本充分后也只能在组织设定上限内调节，不能跨域沿用声誉。P1 所有 peer 来源按默认 low，角色记忆写入遵循 2.1 的入口证明规则。

跨 Space 召回在各真实 Scope 分别授权与复核，再按同一请求侧策略版本评估排序；来源侧声明不能给自己加权。来源侧治理限制与请求侧限制取更严格者。不同 Scope 的分数未经同域校准时按相关性和序数等级排序，不直接比较概率；不跨 Scope 合并 ClaimKey、证据组或执行自动取代。允许展示已授权独立条目，不代表允许建立跨 Scope 级联依赖。

| 操作意图（拟议，非已发布 API） | 权限与目标确定 | 返回内容草案 |
|---|---|---|
| 为什么这么认为 | 目标读取权限；每条证据独立读取授权。客户端提交 Scope/id/revision 最可靠；自然语言指代只能在本次可见结果中解析，多个目标则返回待选择，不猜测 | target_ref、认知标签、可披露理由、已授权证据引用/片段、assessment、complete/partial、截断原因；不可见证据仅通用“依据不可完整展示”，不泄漏 ID/数量 |
| 这条是错的 | 读取目标不代表可撤销。需目标真实 Scope 的更正/撤销权，校验 expected_revision 与 operation_id；用户可否认自己的偏好推断，不能因此撤销第三方共享事实 | applied/pending/needs_selection/conflict/rejected、获授权 target_ref、新修订（若有）、可见任务引用及是否完成；不得暴露无权后代数目 |

无更正权限时可作为受权反馈入口提交“异议”供维护者处理，不能改变目标可信状态；没有反馈权限则拒绝。指代不唯一时零写入，返回授权范围内的候选供选择；版本竞争返回 conflict，不能把更正应用到新修订。P1 支持目标明确的解释及同步撤销资格；不存在后台任务时只能返回已应用的资格变化或不支持，不能返回 pending。P2 才提供可恢复级联任务及 pending/完成状态。新增 API 发布前必须将这些数据与错误语义归入 S02。

### 9. 完整性能力与安全设计归属

记忆完整性是可选强化阶段，不能替代来源核验和反投毒评测。本 F10 仅描述业务依赖；密码学、密钥轮转、签名格式和审计协议的新增设计统一更新 [F04 安全总纲](../common/F04-security-interfaces-and-encryption.md) 与既有安全 spec，不恢复原安全 F10～F14。

拟保护范围包括正文/披露层内容、真实 Scope、来源、认知状态、时间、证据引用和修订身份。向量与可重建排名缓存不作为内容真源。规范化格式必须带版本；内容或受保护元数据变化后重新保护，索引重建不应破坏有效封装。审计 MAC 与记忆 MAC 使用不同用途域，具体密钥派生由安全能力定义，不复用审计链私有方法。

结果区分 valid、invalid、missing、key_unavailable：篡改失败拒绝使用；旧数据缺签按明确兼容策略标记；密钥服务故障作为错误，不伪装无结果。strict 模式下必要验证失败就阻止使用，兼容模式的缺签也不能显示已验证。HMAC 仅证明受信系统保护后的内容未被改动，不提供第三方不可否认性；需要原始作者证明时另议数字签名与身份绑定。

## 拒绝的方案

| 方案 | 不采用原因 |
|---|---|
| 新建可信记忆库、信念 tier 或全能 TrustEngine | 复制现有生命周期与权限路径，插件替换成本过高 |
| 将全部可信信息放入自由 metadata | 缺少稳定类型与兼容机制，易被用户字段冒充系统状态 |
| 直接重解释存量 t_valid 为世界时间 | 已有代码与数据语义不同，历史查询会静默改变 |
| 来源等级 × 置信度 × 签名 × 时效统一相乘 | 相关因素重复计权，并把不可使用的硬失败变成软排序 |
| 让 LLM 自报概率、自动裁定事实胜者 | 无可验证校准依据，且不符合现有保守冲突裁决边界 |
| 只有签名就宣称防投毒 | 恶意内容也可能合法写入并被系统签名 |
| 仅后台更新后代，不在读时设屏障 | 级联完成前仍会使用错误派生记忆 |
| 首版引入跨 Scope 全局证据图和分布式事务 | 权限及撤销传播成本高，当前同 Scope 闭环可先验证收益 |

### S09 插件验收

统一契约套件覆盖默认实现与测试替身；只改配置替换单个 evaluator、时间解释器、证据端口或完整性实现，上层不改代码。验证发现/注册失败、未知 target、缺具名依赖、能力组合不全均 fail fast；验证同装配对象身份共享、跨装配隔离、health 聚合、关闭顺序和启动失败清理。覆盖必需能力失败、可选部分失败、授权拒绝、底层端口隔离及默认配置回归。真实后端测试跳过不等于通过。

### 效果与成本基线

先固定数据版本、模型、提示、judge 与预算，记录 LongMemEval/LoCoMo 分项成绩及自建更新、冲突、撤销样例。做同一数据上的消融：基线、时间、可信标签、证据评估、完整性/级联。

衡量更新/时间问题准确率、错误自信回答率、冲突识别准确率与召回率、证据追溯率、撤销后错误使用率、投毒成功率及正常记忆误拒率，同时记录 coverage、tokens/query、P50/P95 延迟与写入放大。只对已校准输出统计 ECE 与 Brier，并报告样本量及适用分组；不能通过大量拒答制造准确率提升。

确定性安全与一致性样例必须全部通过；端到端收益门槛和成本预算在取得基线后确定并冻结，再评估方案。当前不填写未实测的收益数字。

| control / retrieval | P1 同步撤销与有界读侧复核、历史候选与世界区间投影、准入与 partial 返回；先前驱可读再显示时间线 |
| 验证 | 一套从受认证消息/确认到取代、重启、历史查询、证据撤销的端到端测试；并发写/读、崩溃恢复及预算耗尽均通过 |

SQLite 参考设计在**同一数据库事务**中写入当前 MemoryUnit、不可变的内容/可信修订、证据关系和 Scope generation；并发检查失败整次回滚。SUPERSEDE 同事务提交新版本与旧版状态，撤销同事务提交资格变化与 generation。领域端口持有事务所有权，向统一门面公开操作；不允许插件访问 SQLite 私有连接或拼接多次 KV.update 冒充原子操作。修订表是该领域真源的版本组成部分，当前行是同事务维护的读模型，不是平行记忆库。

所有改变可信正文、来源、依赖、生命周期或撤销资格的写入（含后台和管理入口）必须走该端口；固定数据库路径、禁用可信记录 TTL 自动清除及绕过端口的写入。硬删除按治理规则事务性清理修订正文并更新撤销墓碑/generation；保留期外查询明确不完整。上述端口通过 StoreManager 的公开 capability 注入，共享同一后端所有权；现有 persistent_atomic_records 仅保证单记录替换，不能当作新事务 capability。

P1 读侧在有界 SQLite 读事务中完成依赖闭包状态读取，返回该快照的 generation，结果出站前检查 generation；变化则在同一总预算内重试，失败为 partial/abstain。保证针对读快照及最终检查时刻成立，不承诺结果交付后再发生的撤销能追溯阻止已完成回答。向量/全文为异步可重建投影，历史通过领域历史端口查询，不依赖普通索引保留旧条目。

P1 保存不可变修订是证据定位与一致性读的基础，但不发布完整“系统当时知道什么”的公共查询；该查询的语义和保留窗口仍在 P2 设计。P2 新增的是异步级联任务/撤销屏障优化、恢复任务意图及校准器，**基础原子修订和一致性读取不能延期到 P2**。P1 无异步级联时不返回虚构的 pending 任务：撤销资格已提交则返回 applied，并明确 descendants_materialized=false；后代每次读时核验，无法提供的持久化级联操作返回不支持。

本文是方案，未更改已发布契约；因此本次不把拟议接口写成 specs 的现状，也不把计划插件写进模块 AGENTS.md 实现清单。实施前按阶段同步：S07（可信描述与评估类型）、S05（构建提交与证据验证）、S04（时间意图与可信返回语义）、S06（证据端口、修订及恢复）、S03（纠错编排）、S02（公开参数/结果与授权）、S01（来源接入）、S08（装配配置）；安全扩展更新既有 S10-security 与 F04。S09 本身不需新增例外。实现落地时补受影响模块 AGENTS.md，并以当天日期更新修订的 specs。
