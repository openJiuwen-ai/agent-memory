## 1. 项目背景

agent-memory 面向框架无关的记忆摄入、构建、检索和生命周期管理，支持多个 Agent 在隔离与授权边界内复用记忆。用户的任务可能始于 WorkBuddy，随后由 Hermes 接手，再交给 JiuwenSwarm 组织执行或验证。三方产品各有会话、工具环境和上下文，用户需要的是：**工作能够沿着已有目标、进度和证据继续，并且谁能读取、贡献、修改和共享记忆是可控的。**

这包含两个相关但不同的问题：

1. **跨 Agent 接续底座**：不同产品能够关联同一任务，写回新结果，并让有权限的接任者取得必要上下文。同一职责换 Agent、未声明角色的任务也必须支持。
2. **职责角色记忆**：规划、诊断、执行、测试等角色在共享事实基础上形成与职责相关的判断，并积累可跨任务继承的经验。新 Agent 接任的是职责，不只是接上一段对话。

角色记忆聚焦的问题是：**同一段经历对不同职责意味着什么？哪些理解和经验应被保留，才能让接任者继续工作？** 共享证据是基础，角色视图是读侧呈现，职责经验的积累与修正是写侧闭环。

本文的核心机制是“定位记忆起点 → 按职责选择关系 → 有界展开 → 回读记忆与依据”。职责不是另建索引或只改查询措辞。跨产品接续从已经保存的任务记录恢复背景，不依赖前任在线、主动整理交接单或后任确认接受。本文保留需求与行为要求，并在第 13 节给出收敛的设计方案。接入适配、共享治理和交接可见性是端到端交付的必要组成，不将其全部留作外部假设；环境迁移、任务调度和最终决策仍由相应系统负责。

## 2. 为什么需要角色记忆

### 2.1 不同职责需要不同的历史理解

多个 Agent 协作时，规划、诊断、执行、测试等角色经常面对同一批历史数据，但需要回答不同的问题。

例如，一段历史记录包含：

- 某次接口请求失败，日志记录了错误。
- 一名 Agent 提出了原因假设。
- 另一名 Agent 修改了配置。
- 重试成功，但只验证了其中一个场景。
- 后续变更可能使这次解决方法不再适用。

这些内容对不同角色的价值不同：

| 角色 | 真正需要回答的问题 | 所需记忆形态 |
| --- | --- | --- |
| 规划 Agent | 哪些前置条件必须满足？哪些步骤还被阻塞？ | 依赖、约束、已完成事项与未决事项 |
| 诊断 Agent | 哪些原因有证据支持？哪些已被排除？ | 假设与证据链、反例、尚未验证的推断 |
| 执行 Agent | 当前环境下可以复用什么操作？ | 带适用条件、参数与验证方法的操作经验 |
| 测试 Agent | 已经验证了什么？还遗漏哪些场景？ | 覆盖范围、失败条件、测试缺口与预期行为 |

统一摘要容易丢失关系；统一向量检索可能找到主题相关的记录，却没有找全解决问题所需的证据。给每个角色复制一套记忆，则会带来冗余、更新成本和事实不一致。

因此，需要解决的核心问题是：**共享事实如何转化为与职责和当前任务相关、具有证据依据的可用上下文。**

### 2.2 减少对历史信息的重复理解

一段历史通常混合了目标、约束、尝试、结果和未决问题。每个角色重新阅读全部历史并独立整理，容易重复分析，也可能遗漏影响当前判断的条件。

角色记忆让各角色延续与自身职责有关的历史理解，回答：此前哪些事情影响当前判断，哪些结论仍然成立，还有什么没有解决。

### 2.3 保持职责连续性

任务中断、恢复或由其他 Agent 接任时，角色此前承担的事项、判断依据和未完成责任需要得到延续。其价值不仅在于恢复对话内容，还在于帮助接任者理解该角色当前处于什么状态、下一步需要关注什么。

产品身份、Agent 实例和会话可以变化；稳定的任务关联和职责定义不能随之丢失。

### 2.4 减少协作断层

一个角色完成工作后，下一个角色需要理解结果的含义和边界。例如，执行角色报告操作成功，测试角色仍需知道成功发生在哪些条件下、哪些场景尚未验证，规划角色则需要知道任务是否具备继续推进的条件。

角色记忆应帮助各角色理解前序工作的依据、限制和未决事项，减少交接时信息丢失或含义变化。

### 2.5 让共享历史支持不同职责

同一份历史证据可以支持规划、诊断、执行和验证。角色记忆应使各角色在共享事实的基础上形成与职责相关的理解，减少重复积累历史信息的必要。

### 2.6 积累可继承的职责经验

测试角色在多次任务中积累的回归清单、诊断角色反复验证的排查顺序、执行角色遇到的失败条件，不应只留在某个 Agent 的会话中。它们需要以经验的形式被明确保存、修正和复用。

这类记忆按职责组织，但仍归属于受治理的空间，有具体来源和适用范围。“测试角色可以参考”不等于“所有测试 Agent 均可读取”；“多次使用”也不等于“在所有环境中已验证”。

## 3. 核心定义

角色记忆是让不同职责的参与者在共享历史基础上，持续保留与职责相关的事实、判断、未决事项和经验，从而支持任务延续、角色交接与协作决策的能力。

角色体现持续的职责、关注点和判断要求，任务决定此次具体要解决的问题。同一角色切换任务或进入不同任务阶段时，需要关注的历史信息也应随之变化。

角色记忆应帮助角色理解：

1. 当前判断需要依据哪些历史事实，这些事实有什么适用条件。
2. 此前作出过哪些判断，依据是什么，是否仍然成立。
3. 哪些事项已经完成，哪些问题仍待解决或验证。
4. 前序角色交付了什么结果，结果存在哪些限制。
5. 新证据、职责变化或环境变化是否要求重新审视过去的结论。
6. 哪些职责经验可用于当前任务，哪些条件尚需重新验证。

### 3.1 职责角色、身份与任务

| 概念 | 定义与约束 |
| --- | --- |
| 参与者身份 | 经接入认证识别的人或 Agent，决定以谁的身份请求访问；不能从文本中的自称推断 |
| Agent 实例 | 某产品内的执行主体；产品名、实例标识和会话标识分别保留，不以 WorkBuddy 等产品名代替实例身份 |
| 职责角色 | 稳定职责的标识及描述；在项目或业务范围内定义，不保证不同团队同名角色含义一致 |
| 职责承担关系 | 参与者在某任务、阶段或时间段承担哪些职责，由负责人或编排方提供；多对多，允许人类参与 |
| 任务 | 可跨产品、会话持续的工作；有稳定任务标识，产品本地标识由 agent-memory 的 TaskRegistry 持久化绑定，用户或受托脚本显式建立，不能靠标题相似自动合并 |

一个 Agent 可同时担任多个职责角色，也可与其他 Agent 共担同一职责；业务职责可多选保存；首版每次查询只选择一个内置遍历策略 duty，业务职责由部署配置或调用方显式映射为该策略，未指定时使用 general。职责描述变更需可识别版本，历史判断保留当时的职责背景。首版不定义角色层级与继承：“安全测试”不会因为名称自动继承“测试”的经验，更不会继承权限；两者可显式映射到 testing；首版不自动合并多个遍历策略。作者职责、经验适用职责与查询策略分别记录，不混为同一字段。

全文的“角色”均指**职责角色**。它与现有 `SpaceContentRole`（包括 viewer、contributor、editor）和 `SpaceGovernanceRole` 不同，后两者属于权限治理。未来接口使用明确的职责语义命名，避免无上下文的 `role`，不引入人格意义的 persona。

### 3.2 任务判断、职责经验与角色视图

- **任务判断**：针对某次任务作出的解释、建议或决策，关联证据和适用条件；不自动成为跨任务经验。
- **职责经验**：从经历中明确归集的可复用策略、操作步骤或失败条件，可关联一个或多个职责。它独立于单次任务存续，但保留来源任务、证据和验证范围。
- **角色视图**：在当前授权、任务、可选职责和上下文预算下，组织共同背景、任务判断及职责经验得到的输出；默认不另存一份事实真源。

不同角色可以基于同一份证据提出不同判断或建议，但不能改写事实。作者的职责、经验适用的职责和查询时选择的职责是三个不同概念；角色既参与写入归集，也参与查询，不能只作为检索提示词。

## 4. 具体示例

以下为说明需求而构造的示例，真实集成和收益验证见第 10、11 节。

### 4.1 共享证据的不同职责理解

共享历史记录：

- E1：配置版本 v1 下，批量请求出现超时。
- E2：将批量大小从 100 降为 20 后，同一测试场景通过。
- E3：尚未验证批量大小为 50 的情况。
- E4：系统随后升级为 v2，尚未复测上述参数。

期望得到的视图：

| 角色 | 期望输出 |
| --- | --- |
| 规划 | v2 下正式执行前需要重新验证批量参数；历史成功配置可作为试验起点 |
| 诊断 | 批量大小与超时存在观察到的关联，但现有证据不足以证明唯一原因，也不足以证明 v2 中仍成立 |
| 执行 | 可提出从批量大小 20 开始的小范围验证步骤，并附带来源 E2、适用版本限制和失败后的停止条件 |
| 测试 | 需要覆盖 v2 下的批量大小 20、50、100，以及相关边界场景；历史 v1 测试不能直接算作 v2 覆盖 |

执行角色在 v2 下完成一次批量大小为 20 的验证后，测试角色需要了解这次验证的条件和覆盖范围；规划角色需要据此判断是否具备继续推进的条件。如果更换执行 Agent，接任者应能了解已完成的验证和未解决的问题，减少重复探索。该示例主要验证证据和版本推理，不能单独证明角色信息的额外收益。

### 4.2 WorkBuddy → Hermes → JiuwenSwarm 接续

用户在 WorkBuddy 完成一部分工作后关闭产品，随后在 Hermes 选择同一任务继续；WorkBuddy 不需要再运行或提交交接。JiuwenSwarm 或 OpenClaw 后续也可在授权后读取同一任务背景。

| 环节 | 记忆系统提供的能力 | 限制 |
| --- | --- | --- |
| WorkBuddy 工作期间 | 经工具或可用钩子保存目标、观察、结果与来源 | 没提交的历史不能凭空恢复 |
| Hermes 恢复任务 | 显式绑定同一任务，读取已登记背景，定位相关记忆并展开关系 | 缺失记录、未验证状态和环境差异必须可见 |
| JiuwenSwarm 测试 Agent 查询 | 从有明确验证连接的问题记忆沿验证方法、验证结果关系展开；无边则报告缺口 | 不能把诊断假设变成已验证事实 |
| 新结果形成 | 保存新记忆及有依据的关系，下次查询可读取 | 不依赖前任接受，不保证外部执行互斥 |

人工整理的交接记录可作为额外背景，但不是接续前提。多个产品的并发观察分别保留；任务完成状态不能仅由最后一条消息或最新摘要裁定。

### 4.3 职责经验的跨任务继承

另一个任务要求“验证支付服务的新重试实现”。历史任务中，测试职责曾发现：**响应超时但服务端已记账时，重复请求可能重复扣费；必须在提交后、响应前注入故障，并校验业务幂等键。** 这条经验记录了具体失败轨迹、修复后的验证结果及适用协议版本。它并非从“测试”这个名称就能推导出的通用建议。

新的测试 Agent 没参与旧任务，仍应在有权限且条件匹配时获得该经验及证据。执行职责可参考部署和回滚经验，但不能因此漏掉共享的重复扣费风险。新测试发现幂等协议已变化时，记录新结果并修订经验，而非无条件照搬。

评测同时比较“仅任务检索”和“任务＋职责经验”，两组可访问相同历史；另设把完整职责背景写入任务文本的对照，区分信息增量与角色组织方式的贡献。不能人为让基线看不到那段历史来制造收益。

## 5. 目标与范围

### 5.1 目标

- 提高多 Agent 完成任务的成功率，减少上下文缺失造成的重复探索、证据遗漏和错误复用。
- 使不同角色共享事实，同时获得适合自身任务的证据结构。
- 支持跨产品任务恢复和角色交接，保留职责状态、判断依据与未决事项。
- 支持角色经验跨任务积累，并由新的合适参与者在授权内继承。
- 减少反复阅读历史和重新整理上下文的成本。
- 让输出可解释且可被程序消费：能够追溯来源、关系和适用条件。
- 用可复现实验区分角色信息的收益与一般检索增强的收益。

### 5.2 更适合的场景

- 任务持续时间较长，需要中断、恢复或在多个产品间切换。
- 角色之间存在稳定职责差异，对同一历史信息有不同关注点。
- 同一批历史证据会被多个角色反复使用，职责经验可跨任务复用。
- 协作中频繁发生交接、复核和判断更新。

### 5.3 收益可能有限的场景

- 任务较短，当前上下文已经包含完成任务所需的信息。
- 各角色职责高度相似，对历史信息的需求差异很小。
- 几乎没有可用历史，或历史缺少可靠的结果与反馈。
- 单次任务描述已经充分表达职责和信息需求，角色信息没有额外贡献。

### 5.4 能力边界与非目标

角色记忆改善协作中的信息条件，不单独保证分工合理、目标一致或决策正确。历史记录缺少证据时，不能保证得到可靠结论；角色身份本身也不能作为其判断可信的依据。

首版明确不做：通用任务编排、自动职责分配、工具及运行环境迁移、跨组织授权互信、角色继承体系、自动判定外部事实真伪、无限深度判断图维护、通用消息推送平台。它们不构成绕过共享授权和交接核验的理由。

首版**包含**任务登记、无交接恢复、职责驱动关系展开，以及经验的显式积累、继承与修正；自动从全量历史挖掘经验、大范围后台巩固和主动推送是后续增强。先完成一个真实任务链路和一组职责经验的闭环，不追求覆盖所有协作模式。

## 6. 输入数据需求

### 6.1 数据来源

可接入用户授权提供的对话、Agent 执行轨迹、工具调用及结果、环境状态、人工纠正和测试反馈。不同来源的可信度与验证能力不同。

聊天记录能够提供需求、决策和陈述；缺少执行反馈时，不能把“建议这样做”视为“这样做已成功”。结构化工具结果也只证明指定环境中的一次观察，不自动证明结论可跨环境复用。

### 6.2 最小公共信息

| 信息 | 用途 |
| --- | --- |
| 来源产品、参与者、事件标识及原文定位 | 追溯作者和依据；重试或转述不能变成多个独立证据 |
| 内容类型、分类依据与置信状态 | 区分观察、陈述、建议、假设、行动、结果、决策；允许未分类 |
| 时间、任务和会话标识 | 关联同一任务，保留发生、消息与摄入时间，不按三方时钟推断全局因果 |
| 职责及承担关系版本 | 保存作出判断时的职责背景，区分作者职责与经验适用职责 |
| 涉及的实体与对象 | 连接同一系统、文件、参数或事件 |
| 环境、版本及适用范围 | 防止过期经验被直接复用 |
| 验证状态及结果引用 | 区分未验证、原环境已验证和新环境复验；与数据迁移分开 |
| 真实归属 Scope 与可信访问上下文 | 控制原始记录、派生内容和视图的可见范围；身份不从业务 metadata 获取 |
| 交接所需资产引用及未满足条件 | 明确工作区、版本和工具条件，不在记忆中传递凭据 |

内容字段允许缺失并显式保留未知状态；认证身份、合法归属和写入权限不能以“未知”绕过校验。不同 Agent 格式由适配层处理，统一结构不等于保证语义质量。

## 7. 功能需求与优先级

P0 是首版闭环必须满足的行为；P1 是可独立增强的能力。P0 按“接续底座→最小职责记忆”两步实施，见第 11 节。权限、证据状态和新结果写回不能为减少 P0 数量而后移。

| 编号 | 优先级 | 需求 | 首版边界与验收重点 |
| --- | --- | --- | --- |
| R1 | P0 | 共享记忆底座 | 同一事实可被多个角色引用，无需按角色复制 |
| R2 | P0 | 职责驱动关系扩展 | 相同查询或起点＋不同职责，按关系类型和方向展开；不要求自动推断职责 |
| R3 | P0 | 有类型的关系检索 | 首版支持有依据的关系写入、图投影和有界遍历；全库自动关系发现为 P1 |
| R4 | P0 | 证据可追溯 | 关键事实定位到来源，推断明确标记 |
| R5 | P0 | 时间与冲突处理 | 不静默覆盖冲突，不把过期事实当当前事实 |
| R6 | P0 | 存储增长受控 | 不按角色复制历史；任务记录与经验有归档、保留及清理边界 |
| R7 | P0 | 共享管控与权限一致性 | 明确读、写、改、共享和撤销；派生内容与读取路径不能绕过权限 |
| R8 | P1 | 可替换的基线与评测接口 | 建立通用策略切换；P0 仍需固定场景下的任务检索对照 |
| R9 | P0 | 证据变化后的复核闭环 | 有界检查依赖、展示待复核项、写回复核结果；超界标明未完成检查 |
| R10 | P0 | 保留新观察与验证结果 | 新结果写入成功后才纳入交接；临时计划不自动成为事实 |
| R11 | P0 | 职责连续与跨 Agent 接续 | 前任离线且无交接单时，新 Agent 仍可恢复已保存背景；明确未采集信息和证据缺口 |
| R12 | P0 | 必要的全局背景 | 已知的共同约束、风险和覆盖缺口不因职责筛选而遗漏 |
| R13 | P1 | 自动分歧分类 | 区分事实冲突和建议差异；P0 无法分类时保留双方与待核实状态 |
| R14 | P0 | 角色信息按需使用 | 角色缺失或不提供增量时仍围绕任务提供记忆 |
| R15 | P0 | 证据状态与抽取鲁棒性 | 缺失条件、分类不确定性可见，重复引用不构成新增验证 |
| R16 | P1 | 职责变化的自动相关性复核 | P0 保留职责版本与未交接责任；自动重判历史相关性后续增强 |
| R17 | P0 | 职责经验的积累与继承 | 显式保存经验、条件和来源；新 Agent 可在授权内复用并回写修正 |
| R18 | P0 | 三方接入与存量连续性 | 接入能力通过 G0 门槛；任务绑定持久化，旧记忆可显式关联到共同背景并被交接引用 |
| R19 | P0 | 写后可读与交接一致性 | 不依赖索引立即更新；绑定变更修订校验、事件幂等和冲突保留，具体保证见 13.4 |
| R20 | P0 | 写入来源治理 | 认证来源与内容可信度分开；指定异常来源可停止共享使用，派生内容不能继续绕过 |

## 8. 针对已识别问题的设计要求

本节规定行为要求，第 13 节说明实现取舍。所有要求针对已提供、可访问的信息；外部事实核实和执行依赖见第 12 节。

### 8.1 按需使用角色信息，避免强行区分

角色应作为补充职责背景使用，不能成为获得任务相关记忆的必要条件。

- 没有角色信息时，仍应基于任务和已有历史提供上下文。
- 角色描述只重复任务要求时，不强制产生不同视图，也不为体现角色差异而排除必要信息。
- 多个角色需要相同证据时，允许获得相同内容。
- 职责描述缺失、含糊或相互冲突时，说明不确定范围，不凭角色名称补出职责或决策权限。

### 8.2 保留必要的共同背景，防止角色信息盲区

各角色的上下文均应保留与当前任务相关且有权访问的共同约束、关键风险、跨角色依赖，以及会改变当前判断的反例或未决冲突，再补充职责相关内容。

- 信息不能仅因来自其他角色或不属于本角色通常关注的范围而被排除。
- 与操作相关的未排除风险、适用条件和验证限制，应与操作结果一并呈现。
- 受上下文预算限制时，优先保留影响决策的条件和风险；无法完整提供时，明确覆盖不足。
- 共同背景同样受访问权限约束，角色需要某项信息不意味着自动获得访问权；不可借“缺口说明”泄露受限内容。

具体领域中哪些条件构成关键风险，需要场景提供判断依据；已明确的风险不得被角色筛选遗漏。

### 8.3 保留判断依据，支持条件变化后的重新审视

历史判断应与依据、适用条件和验证状态关联，不能脱离条件作为当前结论使用。

- 区分“历史上成立”“当前仍有证据支持”和“当前适用性未知”。
- 收到反例、证据纠正、环境变化或职责变化后，标记受影响的旧判断及依赖它的派生结论，说明需要复核的原因。
- 缺少重新验证时，不将旧判断呈现为已验证的当前结论；历史仍保留供追溯。
- 同一来源被多次引用或转述，不视为新增独立证据，也不提高验证状态。
- 依赖检查须有节点、深度和耗时上限；未检查完的结论不能因未被标记而默认为有效。

待复核项要进入任务推进前的视图和交接结果，由用户或现有编排方交给责任人。收到确认已读只能关闭提醒，不能恢复验证状态；恢复必须关联新的验证或有依据的裁决。具体闭环见 13.5。

### 8.4 区分事实冲突与职责导致的建议差异

对同一对象、时间和条件下相互不兼容的事实陈述，保留各自来源并标记待核实；不能按角色身份高低选择其中一项作为事实。

对共享事实之上的不同建议，分别保留目标、约束、依据和适用条件。例如，“可以继续小范围试验”和“尚不足以支持全面执行”可以同时成立，不能简单视为事实冲突。

- 条件不同导致的表面冲突，应明确条件差异。
- 无法确定分歧类型时，保留双方表述及待澄清问题，不强行归类或合并。
- 已提供核实结果或最终决策时，记录来源和适用范围，保留此前分歧供追溯。
- 事实核实、目标权衡和最终裁决由相应责任方承担，角色记忆提供决策所需的分歧及证据。

### 8.5 显式表达证据质量与信息缺口

观察、来源陈述、推断、建议、行动和验证结果应分别表达。缺少执行反馈时，建议不能记为已成功；局部验证不能扩大为全面验证。

- 缺少来源、环境、适用条件或验证结果时，保留未知状态并说明缺口。
- 派生摘要和角色判断保留来源及原有的不确定性，不能通过转述变成事实。
- 自动分类保留分类依据、原文定位和可用的置信信息；低置信或结构矛盾时降为未分类/待核实。模型自报分数不等同于可信概率，没有校准数据时不伪造置信度。
- 依据不足时，说明目前能支持什么、不能支持什么，以及还需要哪些证据。
- 收到纠正或补充证据后，更新相关判断的状态并保留变更依据。

### 8.6 保障职责延续，明确交接中的未知事项

任务恢复或角色交接时，保留目标与约束、已完成事项及依据、当前判断及适用条件、未决问题、未完成责任和已知风险，并带上需要继承的职责经验引用。

- 已完成操作与已验证结果分别交接，不能相互替代。
- 更换承担同一职责的 Agent 时，必要历史理解应延续，不要求接任者从全部历史重新推导。
- 收到职责变化后，保留原职责下未完成的责任，直至收到明确交接或取消结果；自动相关性复核按 R16 分阶段完成。
- 责任归属不清时，标记待分配，不能默认由接任角色承担或视为已完成。
- 接任者直接核验已有任务背景及必要记录，不要求前任提交或后任确认交接；读取不完整或环境不满足时呈现缺口。

职责定义和任务执行分配由用户、协作模块或责任方提供；显式交接是可选补充。角色记忆负责保存和呈现，不自行分配职责。

## 9. 待验证的设计假设与风险

本节集中记录预期收益的不确定性；前述行为要求不依赖收益结论即可验收。

| 假设 | 应观察到的结果 |
| --- | --- |
| 按任务组织证据关系比只检索相似文本更有用 | 相同预算下，任务成功率或证据完整性提升 |
| 职责及其经验在任务文本之外仍提供价值 | 去掉职责条件或经验选择后，性能出现可重复下降 |
| 角色记忆有助于职责延续与交接 | 任务恢复或接任后，重复探索和交接信息丢失减少 |
| 证据、时间和版本约束能减少错误复用 | 过期经验误用、无依据结论或重复失败减少 |
| 可解释视图有助于调试协作流程 | 能定位选错证据、漏检关系或错误推断的来源 |

主要风险是抽取误分类、来源投毒、职责定义不清、候选召回遗漏、复核噪声以及适配器没有完整提供事件。不能靠角色名称或结构化输出证明原始内容可靠。测试注入这些故障，并分别记录系统可发现与无法发现的部分。

如果任务描述已经包含角色所需的全部信息，应记录角色条件没有额外收益的情况，并据此调整角色配置与查询机制。不得为展示差异而删去共同背景或限制基线的历史访问。

## 10. 评测需求

### 10.1 视图质量、接续正确性与协作效果分开评测

- 视图质量：同一历史下各角色是否获得所需信息、关系与适用条件；同一角色切换任务后是否调整。
- 接续正确性：三方身份和任务正确关联、读写符合授权、交接引用可读、新结果可见、错误和缺口可消费。
- 协作效果：固定分工与执行流程后，是否提高任务成功率、减少重复探索和错误复用。

视图内容不同不能证明任务能力提升；协议替身通过不能证明三方产品集成已完成。

### 10.2 必须包含的对照组

1. 无长期记忆。
2. 共享摘要或普通混合检索。
3. 任务驱动检索，不使用职责条件。
4. 任务与职责共同驱动的记忆，包含职责经验。

比较职责条件时保持历史和经验集合一致；另做移除职责经验、把职责背景完整写入任务的消融实验，拆分“多了信息”和“组织方式更好”的贡献。整体成本计入经验形成、更新和复核。

### 10.3 公平性要求

- 固定模型、工具权限、多 Agent 分工和执行流程；跨产品无法统一的因素如实记录，不把产品差异归因为记忆收益。
- 同时报告成功率及团队总 token、工具调用量、延迟和成本。
- 用相近预算比较，避免靠增加调用次数取得优势。
- 测试问题的答案、证据标注、隐藏测试和标准补丁不能进入记忆构建过程。
- 跨任务经验只能来自允许的历史或训练划分；测试任务间是否共享记忆必须明确。
- 固定历史记忆与任务执行后允许回写的实验分开报告。
- 记录运行次数、随机种子（可控时）、失败类型及不确定性。

### 10.4 核心指标

- 最终任务成功率、关键证据召回与无依据结论比例。
- 重复失败次数、错误经验复用次数及角色筛选造成的关键背景遗漏。
- 交接后的信息完整性、重复探索量、必需记录可见延迟及不完整交接识别率。
- 经验继承后的适用性判断、反例出现后的复核正确性。
- 总推理成本、检索延迟、依赖检查量、待复核项数量和存储增长。
- 共享授权、来源隔离、撤权和失败恢复用例的通过情况。

收益幅度及性能阈值由基线决定；越权泄露、未确认持久化却报告交接成功、已知失效结论仍标为已验证等属于功能失败，不等待统计提升后再处理。

### 10.5 设计要求的验收场景

| 对应要求 | 验收场景 | 预期行为 |
| --- | --- | --- |
| R14、8.1 | 未提供角色，或描述仅重复任务 | 返回任务记忆，不编造职责，不强制形成差异 |
| R12、8.2 | 执行角色请求曾有风险的操作；预算不足 | 保留已知关键风险和条件，结构化标明覆盖不足 |
| R9、8.3 | 判断依赖旧版本，随后出现反例；检查超出预算 | 相关结论待复核，未完成检查不当作有效；返回聚合复核项 |
| R13、8.4 | 同条件事实冲突，或不同范围的建议差异 | 保留来源与条件；无法分类时待核实 |
| R15、8.5 | 建议反复转述；注入“建议→已验证”分类错误 | 不累计验证次数；发现证据缺失或分类矛盾则降级并可回原文纠正 |
| R11、R16、8.6 | 同角色跨产品接任，或职责变化但交接未确认 | 保留职责版本、责任、依据与待确认状态 |
| R17 | 新 Agent 接任测试职责；旧经验在新协议下失败 | 检索适用经验，保留新反例，旧经验不继续作为当前有效建议 |
| R18 | 同名会话、同一会话多任务、解除后迟到事件；重启后查询绑定 | TaskRegistry 保留明确映射；歧义拒绝，不误写其他任务 |
| R18 | 一批现有 JiuwenSwarm MemoryUnit 无 task_id/职责，语义索引不可用 | 关联清单中的记录经 get 进入共同背景和交接；未关联历史不宣称完整覆盖 |
| R19 | 写入超时、索引延迟、并发绑定修订、事件重试及响应丢失 | 按明确引用核验；同修订仅一个控制变更成功，冲突拒绝，重试返回既有结果 |
| R7、R20 | 伪造职责或作者、撤销读取权、隔离异常来源 | 拒绝身份替换和越权，原文及派生输出都不能绕过限制 |
| R6 | 关闭任务、归档来源、清理被引用记录 | 不自动删除活跃依赖；必要清理后明确缺证，不恢复成已验证 |

### 10.6 数据来源和标注

先自建并经授权记录第 4 节的三方轨迹：前任离线无交接接续、同职责换 Agent、环境变化、权限撤销和并发记录。由两名标注者独立标注关键证据、任务状态、经验适用条件及必须交接的信息，记录分歧和复核过程；先做小规模试标，报告每条轨迹耗时与总人工成本，再决定样本规模。

公开多 Agent benchmark 可用于补充证据检索与职责经验实验，但需检查许可、能否重放、是否有真实工具结果及是否允许跨任务记忆。改造成接续任务时记录改造点，不能用它替代真实产品接入测试。训练/历史轨迹、参数调试集和最终评测集分开，避免同一经验实例及其答案穿越划分。

## 11. 最小可展示版本与实施顺序

首版包含一个接入前置门槛和两个连续里程碑，完成第二个里程碑才称为“角色记忆首版”，不能只交付共享证据底座。

0. **G0 接入前置门槛**：按 13.11 的产品矩阵，记录实际客户端版本、工具注册及调用方式、认证成功/拒绝样例、绑定上下文来源、一次记录的持久回执和一次结构化视图读取。agent-memory 维护适配包及能力清单，用户/部署方提供凭据和测试上下文。三方各自通过后才进入三方闭环验收；MCP 支持的官方说明不等于本项目已联调。无法注册工具或校验身份时标为阻塞并明确需产品方提供的能力，不以“后续验证”结项。
1. **接续闭环**：用户创建项目任务并绑定产品上下文；WorkBuddy 保存部分记录后离线，Hermes 无交接单恢复背景并写入结果，JiuwenSwarm 再读取。验证授权、明确引用、未采集历史缺口、撤权和重试；OpenClaw 按相同契约独立完成接入验收，不以其他产品通过代替。
2. **关系扩展闭环**：同一起点分别以诊断、测试、执行职责查询，返回不同的有依据路径，同时保留关键反证和共同约束。新增、修订和撤回一条关系后复查结果；另验一条未与新任务连边的历史经验能作为独立候选被发现，保留无路径标识。对照纯向量、职责标签重排、无职责图展开，测量关系路径正确率、证据召回、越权、延迟及预算截断。



首版新建一个组织内的项目共享空间用于新协作记录和任务控制；不把某个产品已有私有空间直接改为共享，不改写旧记忆 Scope。旧记忆通过背景关联及真实来源授权参与接续，具体拓扑见 13.6。新产品未能导出历史时可从新事件开始，完整历史导入能力单列；真实三方在线接续仍是交付门槛，契约替身只能用于提前验证内核。

完成闭环后，再独立扩展 R3 的全库自动关系发现、R8 通用评测接口、R13 自动分歧分类和 R16 职责变更重判；自动巩固和推送仅在实测成本与需求支持时引入。

### 12.1 责任边界

| 事项 | 责任方 | 本特性的责任 |
| --- | --- | --- |
| 产品身份与接入认证 | agent-memory 适配维护者、身份系统及部署方 | 提供接入包和 G0 验收；可信连接与业务字段分离 |
| 全局任务与本地上下文映射 | agent-memory TaskRegistry；用户或受托脚本发起 | 持久化注册、绑定、查询、解除及背景引用，执行治理和修订检查 |

| 工作区、文件、工具及执行环境 | 三方运行时 | 交接中提供资产引用和前置条件，显示未满足条件 |
| 原始记录真实性、重新试验和最终裁决 | 来源、执行工具及相应责任人 | 保存证据状态，支持纠正及复核闭环 |
| 复核任务的分配和通知 | 当前参与者与任务负责人 | 通过显式 view/review 工具处理；适配指引要求推进前调用，未调用不得声明阶段已核验；首版不推送 |
| 存量导出的授权与可获得性 | 数据所有者、三方产品 | 提供选择性导入及核对方案，未知来源和权限不自动共享 |

### 12.2 已知实现缺口和待验证项

- **图存储已有可用实现**：`GraphStore` 接口原有两个后端——`InMemoryGraphStore`（注册名 `memory`，纯内存，测试广泛使用）和 `NanoGraphRAGGraphStore`（注册名 `nano_graphrag`，基于 nano-graphrag 的 NetworkXStorage，持久化到 GraphML）。`GraphRecaller` 有关键词/实体种子 + BFS 邻域展开骨架。首版开发/测试用内存后端，角色图持久部署使用具名 KV 图投影；现有 `nano_graphrag` 是无向单边图，未满足本特性的有向多关系和 incident_edges 契约，不能直接作为角色图后端。职责视图已补类型/方向过滤、策略展开、逐跳授权检查和路径返回。
- **关系类型已有基础**：`LLMAssociator` 内部定义了 `RelationType` 枚举（caused_by / refers_to / corefers / follows_from / similar_to / contradicts），与本方案的六种证据关系不完全等价，需显式映射。`Relation.relation` 和 `Edge.relation` 均为自由字符串，不强绑定枚举——现已提供跨层共享的可扩展关系类型注册表，见 13.3。
- **冲突检测有基础，消解链条断开**：`LLMAssociator` 的 Phase 3 可发现 contradicts 关系并写入图索引，Evolver 的 CONSOLIDATE 模式有去重/版本替代框架（ADD/UPDATE/SUPERSEDE/NOOP），但 ASSOCIATE 发现矛盾后没有自动触发消解动作，CONSOLIDATE 也不利用 contradicts 边——角色事件和关系登记已接入 13.5a 的冲突处理；旧 ASSOCIATE 路径未自动转换为证据关系真源。
- 当前 provider 已使用 `/v1/<verb>` 请求格式，HTTP 支持可选 Bearer，进程内客户端要求注入可信 security_provider；这些现有能力可复用，但仍需验证生产认证配置及新增职责查询契约，不能把现有连接可用等同于本特性已接通。
- 仓内 JiuwenSwarm 有 provider 实现；WorkBuddy、Hermes、OpenClaw 使用新增的统一远程 MCP 桥，尚无各产品原生历史导出器。13.11 已选择工具接入路线并区分官方已提供能力、本仓待开发能力与需产品配合项，具体版本联调是 G0 阻塞项。
- TaskRegistry、职责关系扩展、结构化角色视图及可信连接来源门禁已落地；全量经验状态演进仍需扩展，契约见 S10。现有内核 `get` 可以按 Scope/ID 读取旧 MemoryUnit；接入需提供明确引用读取，不能把 Markdown 文件读取等同于该能力。
- 现有 `MemoryUnit` 无 memory tree 字段；[memory tree 文档](../common/F08-memory-tree.md)描述目标设计。角色接续不能依赖其已实现。
- `hybrid` 会把 `RETRIEVAL_ONLY` 传给子 builder：forward 跳过本体，全文/向量可建投影；但 `unified` 委托的 CompositeDomainStore 对该模式为空操作。仅返回成功不能证明索引补建，须在选定后端验证。`rebuild()` 不能据名字推断可用；补索引不是旧记忆按引用进入交接的前提。
- 真实轨迹、标注成本、经验独立收益和可接受的交接延迟尚无基线，按第 10 节取得结果。

## 13. 设计方案与关键决策

本节说明拟采用的组织方式、运行流程和取舍。[S10](../../specs/S10-cross-agent-continuity.md) 集中承载接入、任务登记、关系及职责查询契约和视图 schema；公开入口已按该规约落地，实装边界及未完成验收见第 14 节。

### 13.1 数据组织：共享记录、任务判断、职责经验

首版复用 MemoryUnit 及既有存储，不另建“每个角色一个库”。将下列对象作为记忆内容的不同用途，而不是增加 Scope 维度或为所有对象新增 MemoryTier：

| 对象 | 记录什么 | 更新方式 |
| --- | --- | --- |
| 来源记录 | 原始消息、工具结果、人工反馈及来源定位 | 原文保留；纠正以新记录关联旧记录 |
| 任务判断 | 结论/建议、依据、条件、作者职责背景及验证状态 | 新判断保留旧版本；分歧并存，不由时间戳自动裁决 |
| 职责经验 | 可复用策略、步骤、停止条件、验证办法、适用职责与条件、来源 | 明确归集，复验或反例推动修订；程序性经验可使用既有 PROCEDURAL 分类 |
| 交接记录 | 目标、进度、未决责任、风险及上述记录的确定引用 | 可选背景快照，生成后不原地覆盖；不要求生成或接受后才接续 |

**业务归集与权限归属分离**：职责标识、任务标识用于组织信息，真实归属仍是 `MemoryUnit.scope`。职责经验可服务多个任务，因此不能以某次任务的会话标识作为唯一检索入口。经验按职责逻辑归集，物理上仍受项目或团队空间治理。

**载体选择**：复用 `segments` 保存可追溯的内容或结构投影；参与内核过滤与行为判定的职责、任务、记录用途及证据状态，拟以少量受校验的系统 metadata 记录。由核心解释的字段不塞进 `user_metadata`；用户业务标记保留在后者。现有 metadata 只允许标量和字符串列表，复杂交接内容及带类型的证据引用采用受 schema 校验的内容记录，不放任意嵌套字典。机器消费从校验后的记录生成，不从摘要重新抽取状态。最终键名、schema 版本及编解码规则在 S07 固化。

**引用要准确**：沿用 `source_ref` 定位来源、`provenance` 表示派生血缘、`supersedes` 表示版本替换，但三者不能替代“支持/反驳/适用条件”等关系。首版在内容记录中保存明确给出的依赖及所用版本；引用必须携带足以解析的 Scope、unit ID 及所依赖内容的摘要，不能假定 ID 全局唯一或同 ID 永远未变。默认修订采用新版本；引用遇到既有 OVERWRITE 导致内容摘要变化时重新核验，不能继续沿用旧验证状态。首版复用 GraphStore 能力构建可重建的关系投影；具体后端需验证类型、方向、路径与授权契约，不预设必须部署独立图数据库。

**继承不能靠 metadata 复制**：现有派生规则对多源 metadata 取相等交集，不能据此完整保存多个作者职责、支持关系或经验范围。本方案由构建过程显式组装上述信息并回指原记录；聚合后不再把作者、分类置信度或验证状态当作可无条件继承的字段。

#### TaskRegistry：由 agent-memory 维护映射

首版新增控制层 TaskRegistry，用户或受托脚本显式注册全局任务、绑定产品上下文、查询和解除绑定。映射不等待产品主动建立，也不保存在某个 Adapter 的进程内变量中。记录通过具名持久管理端口保存，重启后可查，规范见 S10。

一个全局任务可以关联 WorkBuddy 的任务、Hermes 的一个或多个 session、JiuwenSwarm session。它们表示“这个上下文参与 T”，不表示粒度和生命周期完全相同。一会话多任务时使用不同 binding_id，并逐事件显式选择；未能唯一解析时拒绝写入。无法从产品取得原生 ID 时，由接入桥生成持久上下文别名，标明 `adapter` 来源，经用户确认绑定；不冒称已经取得产品原生任务 ID。

只有任务负责人或明确受托者可以创建/解除绑定；可读参与者可查询获授权的绑定。解除采用软撤销，历史关联保留，迟到事件不得被自动改绑到别的任务。绑定不授予源记忆读取权限。已有记忆通过 Registry 的任务背景清单关联其原 Scope、ID 和内容摘要，不要求给每条旧记忆原地补 task_id。

Registry 保存任务绑定、背景引用和修订，不保存推进权或强制移交状态。首版单写服务实例按任务串行更新映射并持久化，禁止把现有 KV 的 get/update 当作跨实例 CAS；具体恢复规则见 13.4 和 S10。

### 13.2 写入与职责经验形成

记录流程为：认证与归属校验 → 保留来源 → 校验/分类 → 构建记忆及索引 → 返回实际持久化结果。适配器只转换格式和传递已知上下文，不替内核推断权限、验证状态或重做业务编排。

认证后的写入者可以在有写权限的空间提交自己的观察或判断；受托导入他人历史时，区分“本次导入者”和“原记录声称的作者”，不能把后者变成已认证身份。修改或撤回他人记录仍由既有权限决定，不因为承担了相同职责就获得修改权。

首版经验积累走**显式归集**：参与者提交一条有价值的策略，选择来源及适用职责，系统保存为经验候选。可以用现有抽取/抽象算子辅助生成候选，但没有来源或验证结果时仍是候选；无需每条都人工批准，也不能由模型自行宣称验证完成。

经验的语义状态与 MemoryUnit 生命周期分开：

| 触发 | 经验状态及动作 |
| --- | --- |
| 从经历中提出经验 | 候选，标明尚未验证的条件；允许作为建议检索 |
| 收到可定位的执行/测试结果或明确的责任方确认 | 记录“在给定条件下获得支持”；确认来源和验证范围可见，不升级为通用真理 |
| 出现相关反例、依赖版本变化或条件不匹配 | 待复核；旧适用范围保留，但不能直接作为当前已验证操作 |
| 复核产生修订经验 | 形成新版本并关联新旧依据；旧版本保留追溯 |
| 明确否定或不再维护 | 停止作为当前建议，按保留策略归档或遗忘 |

例如，支付幂等经验在旧协议下有支持，新任务改用另一幂等键后不能继续显示“已验证”；新的测试反馈首先影响该条件下的适用性，不应把所有支付经验一并推翻。

### 13.3 查询：从记忆起点按职责展开关系

**主线不是“通用路＋职责标签路”双路向量检索。** 向量、全文和实体索引用于定位起点；职责决定后续沿什么关系、什么方向展开。同一查询文本在相同范围内可以使用同一查询向量，差别发生在图遍历阶段。正文和图投影共同存储，不按职责复制记忆。

1. **限定范围并取共同背景**：认证授权后读取任务的明确引用；任务查询必须保留目标、约束、风险及未决事项，不能让相似度 top-k 淘汰必要背景。
2. **确定起点**：提供完整记忆引用时直接点读；否则通过现有向量/全文/实体召回得到少量起点。实体命中需解析到记忆，不假定 entity ID 等于 MemoryUnit ID。
3. **按职责展开**：服务端将运行时 duty 映射为已装配策略，规定关系类型、入/出方向及预算。诊断优先原因和证据；测试优先验证方法和结果；执行优先方案与前置条件。无职责使用通用策略，未知职责报错，不静默猜测。
4. **核验并回读**：每一步先校验边及目标可读性、关系来源、版本和有效状态，再继续扩展；无权节点不能当隐藏桥梁到达其他节点。循环去重，限制跳数、总节点/边数和耗时；超限报告缺口。对选中结论的直接反证和必要条件执行共同检查，不能被职责策略跳过。
跨任务经验没有与起点连边时，允许按任务目标或 query 在授权经验中做一次有界语义候选发现，并检查适用条件。仅有 anchor 时使用其已授权内容，不读取隐藏邻居生成查询。独立候选标注“语义相关、无关系路径”，不得拼成图路径；可从该经验自身再展开。该分支与图共用节点/耗时预算，职责标签只辅助候选排序，不取代图主线。仅 task_id 且无可用目标内容时返回 missing_input，不猜测任务。

5. **组织结果**：按任务相关性与路径用途组织事实、判断、经验、未决、风险和缺口，同时返回起点、边及证据路径。路径相通不等于逻辑成立，支持关系不自动传递，不能将待核实关系升级为事实。

职责策略是服务端可配置的数据，不是给每条边贴角色标签。多个职责可以沿同一条边；关系相同但预算不足时不能承诺完整召回。正文、经验和索引复用，职责只影响遍历策略和呈现，不影响访问权。

首版不持久化跨主体共享的角色视图缓存。图索引滞后、缺失或不可用时可返回起点及明确背景的 partial 视图，明确未完成关系扩展；不得把无边、未建图和通道失败混为一谈。生成时间不是三方历史同步水位。

#### 轻量关系模型与现有 entity 能力

关系类型及语义应在构建对应图索引前定义；具体哪两个记忆相连，可在摄入时显式指定或抽取为候选，后续增量增加、修订或撤回。普通向量索引可以先建，不能将“建过向量索引”视为“已建立所有关系”。

现有 EntitySchemaCatalog 定义实体类型和属性，EntitySchemaExtractor 将接受的属性生成 MemoryUnit，实体身份解析和关系投影属于后续职责；不能把抽取器直接当图构建器。实体反向索引表达“同一实体相关的记忆”，不自动表达支持、因果或验证。GraphStore 已有节点/边和邻域接口；GraphRecaller 已有关键词/实体种子与邻居展开骨架，职责视图在此基础上实现显式记忆起点、类型/方向策略、路径返回和授权后的逐跳展开。现有 Associator 的相似、矛盾等关系可提供候选，但既有枚举、方向与本草案的证据边不完全等价，需显式映射和校验，不能直接复用同名边的含义。实体定位与职责遍历保持分层，实体共现仍不自动成为证据关系。

采用轻量 ontology 思想：预定义节点类别、关系含义、端点约束及关系状态，不引入通用本体推理平台、角色继承或全行业概念库。事实关系与职责策略分开版本化；不得把共现或语义相似自动标成因果。程序性经验也可成为节点，须确认现有实体索引准入规则及图映射能覆盖它，不能默认所有 tier 都会进入实体反向索引。

**关系类型注册表**：关系类型为可扩展枚举，内置六种通过代码注册，用户可通过配置文件（`config/relation_types.yaml`）新增。每种关系定义如下属性：

| 属性 | 说明 |
| --- | --- |
| name | 关系标识（如 `supports`），全局唯一 |
| display_name | 展示名（如"支持"） |
| direction | `forward`（A→B）/ `backward`（B→A）/ `both`（双向等价） |
| symmetric | 是否对称（contradicts 是，supports 不是） |
| transitive | 是否传递（requires 是，supports 不是）；首版有界展开，不做无限传递闭包 |
| valid_source_kinds | 允许的源节点内容类型（如 observation / result / experience） |
| valid_target_kinds | 允许的目标节点内容类型 |
| description | 给 LLM 推断和人工审阅看的自然语言说明 |

首版内置六种关系：

| 关系 | 方向 | 对称 | 传递 | 语义 |
| --- | --- | --- | --- | --- |
| supports | forward | 否 | 否 | A 为 B 提供事实或实验依据 |
| contradicts | both | 是 | 否 | A 与 B 在相同条件下不兼容 |
| possible_cause_of | forward | 否 | 否 | A 被认为可能导致 B 的发生 |
| verification_method_for | forward | 否 | 否 | A 描述了验证 B 是否成立的方法或步骤 |
| verifies | forward | 否 | 否 | A 的执行结果为 B 的成立提供了验证 |
| requires | forward | 否 | 是 | A 的成立或执行需要 B 作为前置条件 |

加载顺序：内置六种硬编码注册 → 配置文件覆盖 display_name/description 或新增自定义类型 → 启动时校验端点约束合法性。运行时不可动态增删类型。现有 `LLMAssociator` 的 `RelationType`（caused_by / refers_to / corefers / follows_from / similar_to / contradicts）与上述六种不完全等价，首版需在构建链中做显式映射：similar_to 不入证据图，corefers 映射到实体共指索引，caused_by 映射到 possible_cause_of，contradicts 保留，其余按语义对齐或标为待映射。

**关系状态**：每条关系有独立可信状态——`candidate`（LLM 或用户提议，待核实）/ `confirmed`（有明确依据）/ `needs_review`（端点变化，需复核）/ `revoked`（已撤回）。LLM 推断置信度低时状态设为 candidate；用户显式提交仍需明确确认状态和可定位依据；不能仅凭调用者提交即确认。

**LLM 推断关系类型**：复用 LLMAssociator 架构，扩展 prompt 为"给定两条记忆和已注册关系类型清单（含 description），判断关系类型、方向和置信度"。用户通过配置新增的关系类型自动进入 LLM 的候选清单，不需要改代码。模型推断均先为 candidate；high 不代替验证。端点校验通过且有明确依据的授权复核才能 confirmed。

**职责遍历策略配置**：策略是服务端可配置的数据（`config/duty_policies.yaml`），不是每个职责一个插件。每条策略定义展开的关系类型优先级、方向和预算：

```yaml
# 示例：诊断策略
diagnosis:
  display_name: "诊断"
  traversal:
    - edge_type: possible_cause_of   # 优先因果
      direction: both
      priority: 1
      max_depth: 3
    - edge_type: supports             # 找支持证据
      direction: backward
      priority: 2
      max_depth: 2
    - edge_type: contradicts          # 必须看反证
      direction: both
      priority: 1
      max_depth: 2
  budget:
    max_nodes: 50
    max_edges: 100
    timeout_ms: 2000
```

内置 diagnosis / testing / execution / general 四种策略；用户可通过配置新增。调用方传 `duty=diagnosis`，服务端查表走对应策略，未指定用 general，未知 duty 返回错误。contradicts 在所有策略中默认包含，不可被职责配置跳过。准确 schema 见 S10。

关系真源保存为可追溯记录，经构建链投影到图；先提交真源，再更新图投影。涉及本次新记忆时先 record 取得真实引用，再登记关系；首版不支持客户端临时端点 ID。索引失败返回 partial 和可重试引用，按关系 ID/版本幂等补建，不重抽全部历史。查询逐边回查真源与端点；删除/撤回先使真源状态生效，滞后索引不得复活旧边。端点被 OVERWRITE 或替换后，摘要不匹配使相关边待复核。

### 13.4 接续与并发：恢复背景，不转移任务所有权

用户或受托脚本将新产品上下文绑定到已有任务，新 Agent 即可查询已保存的背景和关系。前任可离线，无需生成交接单；后任不需要 accept 才能读取或写入获授权的观察。可选交接快照仅作为明确引用的补充材料，首版不实现 prepare/accept/cancel、lease 或强制单推进方。

TaskRegistry 的串行修订只保护任务映射与背景清单，不锁外部执行。变更带 expected_revision 和稳定 request_id；首版通过同一服务的单写管理入口持久化控制记录及回执，同修订竞争返回 conflict。绑定撤销后拒绝新事件，不自动改绑；服务重启仍能查询映射。关闭任务不删除历史，新写入不得隐式重开任务。

多个获授权 Agent 可以贡献观察。事件键包含组织、落点、可信连接与绑定；同键同内容重试不重复计证据，同键异内容冲突。不同来源的矛盾结果并存，显式标出，不按时间戳或摘要合并成确定进度。**记忆系统只管已保存信息的组织、呈现和一致性，不管任务执行协调**——谁该执行、任务是否完成、多个 Agent 的工作如何分配，由用户或执行系统负责。多方对同一步骤提出矛盾进度判断时，按 §8.4 和 §13.5a 的冲突消解流程处理：factual 冲突尝试自动消解，advisory 差异各自保留，无法自动消解时 ESCALATE 给用户。记忆系统不承诺执行 exactly-once。

成功记录后按引用写后可读；向量、实体、图索引不承诺同时更新。正文持久化结果与索引状态分开返回，unknown 先核对再重试。未提交的产品历史明确为缺口，不能凭最后一条消息宣称任务完成。绑定不授予来源权限，恢复背景时重新核验，不存在一次确认后永久可用的保证。

### 13.5 变化与复核：读时有界检查，推进前处理

首版不在每次版本变更后同步扫描并改写全库判断图，而采用**记录纠正/变化＋查询候选的依赖检查**：

- 纠正、反例和验证结果引用被影响的记录或明确的环境条件；收到变化后持久化，历史版本不丢失。受影响引用建立可精确过滤的系统投影，检查时从真源读取对应纠正记录与治理状态，不依赖语义 top-k 或尚未更新的向量索引；无法完成精确读取时将依赖状态记为未知。
- 视图生成和交接核验检查当前选中判断的依赖链；采用访问去重和节点数、深度、耗时上限，环或超界都产生未完成检查状态。
- 被检查路径上任一依据待复核、失效或无法取得，依赖它的结论不能继续作为当前已验证结论。尚未访问的全库节点不必立即写入标记；读取时必须执行同一规则。
- 对明确给出的条件变化只影响匹配记录；不能因为“版本升级”四个字把所有经验都判为错误。关系识别不到时显示条件未知，不伪装成已确认无影响。

按**同一变化＋同一任务/经验**聚合复核项，展示影响当前接续的必需依据、仅影响候选建议的事项、尚未完成的检查三档。分档来自依赖用途与检查结果，不依赖模型臆测重要性。多处引用同一失效来源只生成一个主要复核项，展开后可看到受影响结论。

闭环为：变化入库 → 当前参与者显式获取视图 → 用户/当前参与者分配复核或报告阻塞 → 责任人通过 review 写回证据/裁决 → 下次视图重新核验。首版以工具方式驱动，JiuwenSwarm 可额外复用前置钩子读取；没有调用记录的阶段不能宣称已完成核验。正在运行且不再查询的 Agent 不具备实时通知保证。确认已读与完成复核分开，缺少新证据不能自动恢复”已验证”。主动订阅和推送不是首版依赖。

### 13.5a 冲突消解：从检测到行动的闭环

现有 LLMAssociator 能发现 contradicts 关系并写入图索引，Evolver CONSOLIDATE 模式有去重/版本替代框架（ADD/UPDATE/SUPERSEDE/NOOP），但两者之间存在断链——矛盾发现后没有自动消解流程。首版补齐检测→分类→消解→呈现的完整链条。

**冲突分类**：检测到 contradicts 边时，同时判断冲突类型：

| 冲突类型 | 含义 | 示例 |
| --- | --- | --- |
| factual | 同条件下相互不兼容的事实陈述 | 同一时间、同一系统：”内存 16G” vs “内存 32G” |
| temporal | 同一事实在不同时间的变化 | “用户住在北京”（2025）→”用户住在上海”（2026） |
| advisory | 不同职责或视角下的建议差异 | “可以继续试验” vs “尚不足以全面执行” |

advisory 类型永远不自动合并，只保留各自条件和依据。factual 和 temporal 进入自动消解。

**冲突消解器接口**：走标准 Producer 注册，可插拔：

```python
class ConflictResolution(str, Enum):
    PREFER_A = “prefer_a”        # 采用 A，B 标为 refuted
    PREFER_B = “prefer_b”        # 采用 B，A 标为 refuted
    BOTH_VALID = “both_valid”    # 条件不同，各自成立
    ESCALATE = “escalate”        # 提交人工/负责人裁决
    DEFER = “defer”              # 暂不消解，保留双方

class ConflictResolver(ConstructionOperator):
    def resolve(memory_a, memory_b, edge, context) -> ConflictResolution
```

**内置三种消解策略**：

| 策略 | 逻辑 | 适用场景 |
| --- | --- | --- |
| RecencyResolver | 同来源的后续观察优先；不同来源不自动裁决 → ESCALATE | 同一 Agent 自我纠正 |
| VerificationResolver | 有验证结果的优先于无验证的（supported_in_conditions > candidate > unverified）；同级别 → DEFER | 有测试结果的事实冲突 |
| LLMResolver | 用 LLM 分析条件差异，判断是真冲突还是条件不同 → BOTH_VALID 或 ESCALATE | 复杂场景的辅助判断；结果默认 candidate 状态，不自动生效 |

策略链由配置选择（如先 VerificationResolver → RecencyResolver → LLMResolver），首个返回非 DEFER 的结果生效。

**触发时机**：

1. **写入时**：新记忆经 Associator 发现 contradicts 边后，构建链自动触发消解策略链，结果随写入结果一并返回
2. **查询时**：view 生成过程中遇到 contradicts 边，按消解状态呈现——已消解的显示胜出方和依据，未消解的进入 risks 区或 gap（`unresolved_conflict`）
3. **review 时**：人工通过 review 原语提交裁决，优先级高于所有自动策略

**消解结果的记录**：

- PREFER_A/B → 保留反证边和两份原记忆，在当前条件下的视图标记失败方 refuted；保存消解依据引用，依赖失效后恢复待复核，不全局撤销原记忆
- BOTH_VALID → 保留 contradicts 边，补充条件差异说明，两条记忆各自 active
- ESCALATE → 进入 view 的 gap（`conflict_escalated`，blocking=true），等待 review 原语裁决
- DEFER → 进入 view 的 risks 区，不阻塞但显式标注

**关键约束**：自动消解只处理 factual 和 temporal 冲突；advisory 差异永远不自动合并。LLMResolver 的结果默认为 candidate 状态，不自动生效。人工裁决（review 原语）始终优先于自动策略。消解记录保留完整依据和变更历史，旧记忆不物理删除。写入时检测到多于两方的循环冲突时，不逐对消解，整组 ESCALATE。

### 13.6 共享治理：身份、用途和来源可信度分离

首版**新建项目共享空间 P**，归属同一组织 O，用于新协作记录、共享经验及任务登记的管理边界；不把现有 JiuwenSwarm 私有空间直接改成共享。三方分别认证并获得 P 内所需权限，共享写入使用经空间策略允许的项目落点，提交者保留在可信来源及审计中，不靠伪装同一 Agent 身份共享。

现有 provider 的映射是 `scope_id→org`、显式 `space→space`、`user_id→user`、`agent_id→agent`、`session_id→session`；scope_id 不是项目 space。旧单元继续保留原始五维 Scope，新模式的项目写入落点与历史 bound_scope 分开配置，不能清空旧 user/agent/session 或修改原 org 来“打通”。

旧记忆进入任务背景有两条明确路径：

- **授权引用**：在 TaskRegistry 保存原 Scope/ID/摘要，接任者另有该来源的读取权后按原 Scope 点读。同空间成员权也不保证能读所有细粒度资源，须以实际判权为准；不同空间的引用逐来源授权。P 的读取权和任务绑定都不替代这些权限。
- **显式发布**：不开放原私有范围时，由有发布权限者选择允许共享的内容，在 P 创建新的共享记录，保留来源出处与发布依据。按 13.6 的发布规则决定允许的内容，不能用自动摘要绕过权限。

首版来源限同组织；遗留数据属于另一 org 时不改字段冒充同组织，须独立批准的导入/发布流程，不计作直接跨组织共享。引用因撤权不可读时，view/可选背景快照 显示安全缺口或阻塞，不能继续展示旧私有摘要。核验以控制真源的必需引用集合为准：对调用者隐藏无权引用的身份，不等于从必需集合删除它；不可先过滤来源，再把剩余结果报告为完整或 ready。

| 行为 | 要求 |
| --- | --- |
| 读共享任务与经验 | 当前调用身份有权读取；角色名称不提供权限 |
| 写入或修正判断 | 有目标空间及对应资源的操作权，记录真实提交者；作者职责仅作业务背景 |
| 发布私有经验到共享空间 | 显式授权发布，校验可公开内容与来源；不能把私有原文自动摘要成公开事实 |
| 撤销共享 | 后续读取立即重新判权；先前已交付给外部产品的内容无法由记忆服务保证远程擦除 |
| 隔离异常来源 | 有治理权限者指定来源范围与原因，后续查询和经验引用停止把该来源用于可执行建议，并可审计 |

来源认证回答“谁提交”，不回答“内容是否真”。工具输出、导入文本和历史建议均按数据处理，不能提升为系统指令；自动投毒识别不作为首版前提，但对明确识别的异常来源必须能采取治理动作。

来源隔离采用**先阻断后整理**：保存受治理的来源状态，读侧检查命中记录及其依赖，先阻止继续使用，再异步标记或整理关联记忆。不把“删除了源记录但派生摘要仍可读”视为完成。该门禁要覆盖普通 get/search、角色视图和交接等所有能返回相应内容的入口，不能只在角色视图中做过滤。

跨权限范围的持久化派生内容尤其容易泄露。首版不自动把多空间素材合成为更广可见的经验：持久化派生只在可验证的共同可见边界内进行，否则拒绝发布或由有权责任方显式重新发布允许共享的内容。跨空间组合视图只对当前调用者生成，并逐项校验来源。派生读取时来源权限失效或无法验证，保守停止返回依赖该来源的内容；不以空引用替代授权检查。

上述来源门禁和派生可见性检查属于本特性的必要新增控制，不能假定现有授权接口已自动完成。首版不实现自动信任打分，也不把来源降权当作已知污染后的唯一处置。

### 13.7 与既有记忆机制及生命周期的关系

| 既有机制 | 复用方式 | 不混淆的边界 |
| --- | --- | --- |
| Scope / Space（[F03](../common/F03-scope-space-isolation.md)） | 继续承担数据归属、隔离与共享治理 | 职责、任务不是新权限轴；跨产品任务 ID 不能取代空间授权 |
| middle-term（[F06](../control/F06-middle-term-memory.md)） | 缓冲原始对话，供后续抽取 | 交接依赖已持久化来源/结果，不等待后台抽取完成；抽取后归档原文不能让必需引用失效 |
| memory tree（[F08](../common/F08-memory-tree.md)） | 后续可用于任务历史的结构化浏览 | 目标中的包含树不等于证据支持图，也不表示角色继承；首版不依赖它 |
| temporal（[F07](../common/F07-temporal-t-message.md)） | 区分事件、消息、摄入和有效时间 | 时间新不代表可信，消息时间不等于验证时间；环境适用性另行判断 |
| dreaming（[F04](../F04-dreaming.md)） | 需要后台巩固时复用现有演进调度及持续授权 | dreaming 是调度方式，不能自动把候选经验变为已验证经验 |

任务关闭后，交接和任务判断转为历史，按保留策略归档；仍被活动任务或经验引用的证据不能由本特性的自动清理提前移除。被推翻的假设退出当前建议但保留原因。长期未使用的经验可降为低优先级或归档，不能仅凭引用次数推断真假。

首版采用已有生命周期机制加引用检查，不新增独立遗忘引擎。管理方主动删除或强制遗忘优先于引用保留；引用随后显示证据缺失，派生内容受 13.6 的读取门禁约束。归档并非授权隔离，不能用 ARCHIVED 代替撤权。

自动压缩和巩固后续复用 Evolver/Abstractor，保持来源、条件、反例和验证范围；低频合并不能把多个局部成功变成全面成功。按任务关闭后的记录量、每条经验的版本和引用量、源记录保留量测量增长，再决定后台策略。首版增长控制至少包括不按角色复制、限制单次展开、关闭任务归档及显式保留策略。

### 13.8 存量接入与迁移

**需要存量连续性方案，不默认需要全量迁移。** 先盘点数据版本、归属和来源能力，再选择路径：

| 存量类型 | 处理 | 必须核对 |
| --- | --- | --- |
| 现有兼容 MemoryUnit，无职责/任务关联 | 原样点读；选择后在 Registry 背景清单增补关联，不改原记录，不重抽历史 | 进入 view 共同背景和可选快照的精确引用；职责/证据状态未知不能补造 |
| 本体兼容，仅新增过滤或引用索引 | 在所选后端支持的路径上增量补建投影，保留旧索引回退路径 | 结果数量、过滤、授权和点读一致性；失败可重试 |
| `_v<4` 的旧 MemoryUnit | 按现有 metadata 拆分规则离线迁移，不运行时猜测系统/用户字段归属 | 备份、版本识别、字段映射、抽样回读；本方案不因此另设新主版本 |
| 三方自有对话/执行历史 | 经授权选择性导入，保留源标识；无法导出时从新任务积累并声明缺口 | 导出范围、作者可信程度、任务映射、时间语义、目标权限 |
| 三方专用运行状态、工具凭据 | 不作为记忆迁移；只保留允许共享的资产引用和前置条件 | 由执行系统另行恢复，不能以“导入成功”宣称可执行 |

**兼容读取不是只有语义搜索**：TaskRegistry 背景清单或交接显式引用的旧记录，由 view 的共同背景步骤按 Scope/ID 读取，再与检索结果去重。新增关联是记录 ID 的旁路登记，不必改原 MemoryUnit 的 task_id，也不依赖索引增量补建。没有关联、没有交接引用的旧记录仍只能作为候选发现；系统不宣称已完整覆盖全部旧历史。

代码层面，`hybrid` 的 RETRIEVAL_ONLY 可跳过正排并调用全文/向量子 builder，存在“不重抽而补索引”的实现路径；`unified + CompositeDomainStore` 的同模式则不产生检索投影。必须看选定配置的实际可检索结果，不能只检查返回成功。补建不可用时降级为“已登记引用可进入共同背景和交接；未登记历史的自动发现受限”，不影响旧记忆按明确引用参与接续。

**旧记忆的关系补建**：旧正文与既有向量/全文索引保留。先选取获授权的任务或实体范围，按版本化关系模型试抽候选；复用已解析的实体身份，无法确定端点时保留待解析项，不凭同名合并。显式提供且有依据的关系可登记，模型提议默认待核实；记录源摘要、抽取/模型版本、批次及关系 ID，再增量投影图索引。无关系的旧记忆仍能作为起点和任务背景，返回“关系尚未覆盖”，不能报告无相关证据。关系补建不等于 RETRIEVAL_ONLY 的全文/向量补建。构建链维护最小覆盖清单（来源集合摘要、关系模型版本、批次、处理结果和投影水位）；新增/变更来源或投影失败后相关范围标 partial/unknown，详见 S10。

每批记录成功、跳过、待解析、冲突和失败项，核对端点、方向、证据、权限及原文摘要。重复批次不新增独立证据；撤回该批关系及投影，不删除原记忆或覆盖后续修订。用真实存量验证新增边可达、撤回后不可用、图滞后时真源门禁和无职责标签的回退读取。

首版兼容验收固定使用一批**实际经 JiuwenSwarm provider 写入、且无任务/职责标签的存量 MemoryUnit**：

1. 记录原配置、Scope、ID、内容摘要、tier 和来源。`sync_turn(infer=true)` 会保存未建索引的原始来源并生成派生记忆；`/messages/` 来源不等于可 get 的 MemoryUnit，本轮测试明确以实际派生单元为对象，原文导出另验。
2. 用既有 search/list 或已知 ID 找出授权样本；当前 显式 search 不限定 tier，prefetch 则筛选 semantic/core/procedural，样本不能只通过这个入口选择，也不能假定它覆盖 procedural/episodic。
3. 用户将样本引用绑定到全局任务，旧正文、Scope 和职责字段保持不变。新产品读取 view，应在共同背景中得到这些记录，职责及验证未知状态保留。
4. 前任离线且不生成交接；暂停语义索引更新或令召回无命中，新产品仍能经 get 读取已登记背景。重启服务后关联仍在。
5. 撤销一条源授权，确认不因 P 的成员权继续泄露；重放关联操作不增加证据计数；校验原记录摘要未因登记发生变化。

验证结果同时记录样本数、关联数、可读数、权限拒绝数及真实后端；未完成该批验证，不宣称存量接续通过。新写伪造样本只计契约测试，不替代实际存量样本。

迁移流程为盘点与映射 → 备份及试运行 → 小批量导入/补建 → 原文、数量、来源和权限核对 → 切换读取 → 保留回退窗口。导入记录批次和来源键，重复执行不得重复增加独立证据计数；失败清单区分成功、跳过、冲突和未完成项。回滚只撤销该批新增/变更并恢复必要映射，不能删除导入后其他参与者新增的记忆。

首版不要求统一迁移三个产品的所有历史；必须验证至少一批真实可获得历史的导入，以及 agent-memory 现有无职责记忆的兼容读取。完全无法导入的产品明确列为能力限制，不能填造历史状态。

### 13.9 分层与可插拔设计（S09）

只增加职责记忆所需的组合能力，优先复用现有算子和门面。拟议职责分工如下，非当前实现清单：

| 层 | 责任 | 明确禁止 |
| --- | --- | --- |
| 三方 Adapter / Entry | 产品事件转换、认证接入、查询已登记绑定、视图呈现与结果回写 | 直连底层存储；在核心添加 WorkBuddy/Hermes 等分支 |
| API | 校验公共输入、认证授权、审计，向控制层传递受控调用上下文 | 用职责字段授予权限；承载经验算法或交接业务编排 |
| Control | TaskRegistry 持久映射、写入结果核对、复核闭环与来源治理 | 绕过统一门面或创建第二套身份/存储状态 |
| Construction | 复用实体抽取、身份解析与关系构建扩展点，校验经验及关系来源；经 IndexBuilder 落盘与建索引 | 直接写裸 KV、让抽取置信度等同于验证状态 |
| Retrieval | 复用 Retriever 的召回和排序；组合共同背景、记忆起点、按职责的关系展开及证据回读 | 把单一角色排序算子当完整 Retriever；越过系统过滤 |
| Common / Storage | 公共记录类型与编解码；统一数据面读写和能力表达 | 后端专有字段承担授权；用图索引作为唯一事实来源 |

可替换边界选在真正不同的算法职责：候选经验生成优先使用现有 Extractor/Abstractor 扩展点；角色视图的内容组织拟作为接收**已授权、已核验候选**的子能力，由完整查询流程编排。只替换组织策略不应要求重写授权、交接或来源核验。关系扩展是检索子能力，需经统一存储门面声明类型/方向/路径能力；不在 provider 直接操作 GraphStore。职责策略表是运行时选用的数据，不是每个职责一个插件。纯格式转换、ID 映射和状态校验不为可插拔而各造一套插件。

新增子能力按标准 Producer 注册、发现和配置选型；实现不反向导入调用层。完整查询入口必须履行授权后读取、必需引用核验、候选检索、视图组织和错误呈现的整段责任；缺少必需子能力装配失败。基线组织策略也走同一注册/装配路径，不给内置实现留特殊分支。

有状态的 StoreManager/DomainStore、TaskRegistry 管理端口、IndexBuilder、检索和调度依赖按具名引用共享，读写与去重不能落到不同数据源。算法插件不私自创建连接、缓存库或后台线程；组合组件聚合必需依赖的 health，关闭由装配根负责。任务、职责和预算是运行时输入，组件种类及组合关系是装配配置，不能用一次请求暗换插件拓扑。

声明支持交接核验或来源门禁，就必须支持其正常、拒绝、部分失败和恢复路径；未声明能力明确不支持。必需引用失败不降级成完整视图；可选语义召回失败可返回基于明确交接的部分视图并报告错误。授权失败不切后端重试，插件缺失不当作空记忆。

### 13.10 最小交互原语和契约落点

下列是调用方所需的业务交互，不是新增方法目录或最终接口签名：

| 原语 | 调用方提供 | 系统返回/保存 | 落地约束 |
| --- | --- | --- | --- |
| record | 观察/判断/经验、来源、任务和职责背景、条件及已有证据 | 已保存引用、证据状态、部分失败或冲突 | 复用写入通道；校验真实身份，明确真源与索引结果 |
| view | 查询词或明确记忆起点、可选任务/职责、预算 | S10 的 role-view/1 结构，示意见下 | 共同背景包含 Registry 登记的旧引用；不改变现有 search 返回契约 |

### 13.11 三方 Adapter 接入方案与前置验收

**统一决策：以 record/view/review 和任务绑定工具接入，不要求主动交接，不扩展 Rail 协议。** 用户可明确要求 Agent 调用，也可通过同一受鉴权入口的脚本操作；未调用或未采集的信息不得假定已保存。任务/绑定维护由 agent-memory 提供，不要求三方增加全局 task_id。规范化事件、历史交换文件及回写结果的契约骨架见 [S10](../../specs/S10-cross-agent-continuity.md#adapter-接入契约)。

#### 产品能力与接入路线

以下分开记录仓内实现证据和官方文档支持的产品能力，官方资料核对日期为 2026-10-27。它们不替代选定版本的 G0 实测；也不把“未证实”写成产品一定没有该功能。

| 产品 | 已有证据 | 首版选择及本仓待做 | 需三方配合或未证实的部分 |
| --- | --- | --- | --- |
| JiuwenSwarm | 仓内 provider 有 prefetch/sync_turn/on_session_end，以及 get_tool_schemas/handle_tool_call | 保留 Rail 日常读写；改造 provider 的客户端及回执处理，通过已有工具注册入口新增绑定、view、review 工具，共用服务端接续能力 | 在目标 JiuwenSwarm 版本验证工具注册、调用和结果展示；不把扩展 Rail 协议作为首版前提 |
| WorkBuddy | 官方连接器文档支持 MCP/CLI＋Skill；MCP 有用户提供 Token 的方式 | 选择 MCP＋接入指引显式调用 record/view/review，服务端登记连接与上下文别名；本仓需新增接入配置和符合 S10 的工具适配 | 本地任务 ID 的自动传递、逐轮钩子和完整历史导出格式未证实。先用用户确认的持久上下文别名和显式结果提交；需要无感全量捕获时再要求产品接口配合 |
| Hermes | 官方文档支持 MCP 的 stdio/HTTP 配置与 headers；会话文档提供指定 session 的 JSONL 导出 | 选择 MCP 显式工具；用户/脚本绑定实际 session，导出文件转换成 S10 事件流；本仓需新增接入配置和导入转换 | MCP 请求是否自动携带本次 session、自动逐轮回写在目标版本实测；未取得时由显式绑定补足，不借 WorkBuddy 的会话粒度假设 |
| OpenClaw | 仓内为占位，未完成产品能力验证 | 拟用工具/插件桥转发同一服务契约，新增注册描述、连接配置及事件转换 | 目标版本的工具注册、凭据、上下文和导出能力均为 G0 必须解决项，不假定 MCP 或 Rail 可用 |

产品能力依据：[WorkBuddy 连接器](https://open.workbuddy.cn/docs/connector)、[Hermes MCP](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp)、[Hermes Sessions](https://hermes-agent.nousresearch.com/docs/user-guide/sessions)。WorkBuddy 的导出能力不以 CodeBuddy IDE 或其他同品牌产品的历史导出文档代证。Hermes 的原生 JSONL 是每会话一条记录，适配器拆分消息/工具事件后保留原文件定位。

共同认证路径选择每连接独立配置的 Bearer/API 凭据，由 agent-memory 校验并映射主体；不共享三方业务账号、不把 product 字段当凭据。远程 MCP 走受保护连接，本地桥接从受控配置取得凭据。本仓 MCP 已有凭据提取和认证调用接缝，但默认 required 模式未装配生产认证器时会拒绝业务；补齐认证装配是 G0 必做项，不能用 dev 测试身份通过共享管控验收。

无钩子的产品采用显式工具模式意味着**只保证已提交事件的接续**，不保证完整对话自动捕获。接入指引需明确“恢复任务时绑定并 view、结果形成后 record、缺证时补查、复核后 review”；这是工具使用流程，不是已经存在的自动 Rail。用户手工片段可导入但标记覆盖不足，不能冒称完整历史。

#### Agent 如何发现并调用能力

复用一个 JiuwenSwarm AgentMemoryMemoryProvider，不另建角色专用 provider。get_tool_schemas 暴露职责关系查询参数与说明，system_prompt_block 说明“恢复任务先查背景、缺证时展开、结果形成后记录”，handle_tool_call 经客户端转发内核查询。固定职责从配置补默认 duty，显式值优先；适配器不能自行更改图策略或授权。现有 search 的兼容调用继续保留；新 view 逻辑输入以 S10 为准，最终工具命名在实装时确定。

WB/Hermes 的 MCP 工具描述提供同一参数和结构化结果，Skill 只补充使用时机，不代替工具。仅服务端增加功能不会让 Agent 自动发现；验收须确认模型实际看到了 schema 并发出携带 duty 或 anchor 的调用。相同 query＋不同 duty，以及同一 anchor＋不同 duty 均需演示路径差异。

OpenClaw 首版拟采用产品工具/插件桥接统一远程入口，职责与路径契约同 S10；仓内尚无实现。本轮不假定它具有 JiuwenSwarm Provider 或可直接加载相同 MCP 配置。选定版本必须完成工具注册接口、认证传递、上下文 ID、调用结果和历史导出调查；无法提供受鉴权工具入口则明确阻塞该产品接入，不影响其他产品独立验收，也不能宣称 OpenClaw 已支持。接入包至少交付注册描述、连接配置、显式绑定和 record/view/review 转换；有钩子再增加自动采集。

#### JiuwenSwarm provider 的具体差距

以仓内 [agent_memory_provider.py](../../../jiuwen_memory_adapter/jiuwenswarm/agent_memory_provider.py) 为准，不能简单描述为已有完整 add/search/get 接续能力：

| 现有路径 | 可复用部分 | 必须改造的边界 |
| --- | --- | --- |
| sync_turn | 每轮传 `infer=true`，保存原始来源并同步抽取；日常事件采集 | 当前返回 None，异常只记日志；不能用于交接成功判定。接续模式要取得持久回执及全部相关引用，失败显式返回，不等 session end 补救 |
| prefetch | 执行前召回并注入上下文 | 目前仅将 content 拼成 Markdown，失败返回空串；接续模式先取得结构化 view，再渲染展示。保留引用、风险和 blocking gaps，不能丢弃后继续报告 ready |
| on_session_end | 可触发额外 EXTRACT | 不是关系查询或 review 的触发点，也不是“所有原文已入库”的回执；不将会话结束自动等同于交接 |
| 客户端 add/search/list/evolve | 可复用连接、异步调用和公开 API 桥接 | 既有 add/search/prefetch 保持原用途；新增 continuity_call 转发四个工具，role_record 返回完整引用，role_view 可按 anchor 精确读。迁移脚本经统一远程客户端调用公开 get；不把既有 add 返回值当可靠接续回执 |
| get_tool_schemas / handle_tool_call | 已有主动工具注册及分发 | 首版在此增加接续工具，服务端承担业务语义；不需新 Rail hook。JSON 字符串仅为宿主传输包装，内容仍须符合结构化契约 |
| bound_scope / HTTP 客户端 | 旧隔离坐标与连接配置 | 保留历史坐标；接续模式连统一远程服务，补项目落点、可信绑定及新 HTTP 契约。SDK 兼容模式不启用独立 Registry，不在 provider 复制治理算法 |

当前 get_tool_schemas 注册 `agent_memory_search`、`agent_memory_conclude`、`agent_memory_read_md_file`、`agent_memory_edit_md_file`；profile/procedural 的处理代码保留但未向模型注册。现有 search 不包含职责遍历参数，不能视为已具备关系扩展。改造采用**provider 内薄适配＋服务端共享能力**：保留其宿主生命周期和兼容模式，不在外层再包一套独立的记忆状态机，也不把关系查询机械映射成普通 add/search。

## 14. 拒绝的方案与建议取舍

| 方案/建议 | 决策及原因 |
| --- | --- |
| 只改查询措辞、职责标签加权或双路向量召回 | 不作为主方案。不能表达沿因果假设、证据、验证和条件路径展开；可作评测基线 |
| 首版引入重型 ontology 平台 | 不采用。先定义有限关系、端点与方向约束，复用 entity/graph 基础，不做通用逻辑推理 |
| 只保留共享证据底座，把职责经验全部后移 | 不采用。显式经验积累、继承和修正属于角色记忆首版；自动挖掘和全量巩固可后移 |
| 每个角色复制历史或新增角色 Scope | 不采用。职责多对多且可变化，复制放大更新成本，新增权限轴混淆职责与授权 |
| 先建设角色继承、人类专属角色体系 | 不采用。首版平面职责＋承担关系足够，人类与 Agent 都是参与者 |
| 只用 prompt 生成摘要作为交接 | 不采用。没有确定引用、证据状态和结构化缺口，无法可靠核验和自动评测 |
| 首版全局强一致、自动分支合并或全图同步传播 | 不采用。仅 TaskRegistry 映射变更串行检查；关系投影可重建，正文与图不承诺跨库原子快照 |
| 失效后只放一个无人消费的标记 | 不采用。推进前获取视图并处理复核项是接入流程要求；通用可靠推送暂不建设 |
| 已知异常来源只降权 | 不足以满足安全边界。首版支持显式隔离并检查派生依赖；自动检测和信任评分另行评估 |
| 为减少 P0 条数把权限、新结果回写后移 | 不采用。先按完整闭环切范围，再延后关系发现、自动分歧分类等独立增强 |
| 要求示例证明“没有角色必定做不好” | 不采用。补充具有职责历史增量的例子，但以公平消融测量收益，不预设角色一定有效 |
| 所有存量统一迁移、重抽与重索引 | 不采用。背景引用登记与索引补建分开；已知 Scope/ID 的旧记忆无需 task_id 即可被交接引用 |
| 等待三方扩展 Rail 才支持交接 | 不采用。首版统一选择显式工具；JiuwenSwarm 复用现有工具注册，WorkBuddy/Hermes 用 MCP |
| 把主动交接、单推进方或 accept 作为接续前提 | 不采用。前任可能离线；首版只管理记忆关联与修订，不接管外部执行所有权 |
| 三方独立 SDK 共享 KV 即视为 Registry 单写 | 不采用。进程内串行不提供跨进程互斥；接续控制集中到同一服务入口，远端失败不能静默本地接管 |
| 裁剪无权引用后对剩余背景宣布 ready | 不采用。隐藏引用身份与核验必需集合分开，缺少必需来源必须阻塞 |
| 一次查询等于证据永久有效或跨库原子快照 | 不采用。每次读取仍复查授权、端点摘要及关系状态 |


## 14. 实装结果与剩余验收（2026-10-29）

已实现任务控制记录、可靠事件回执、职责关系注册表及策略、结构化视图、关系真源与可修复图投影。复用 MemoryUnit、既有写入链、普通检索及权限系统；不要求前任在线或 handoff/accept。职责差异发生在有界图展开，而非仅改查询词。

构建侧新增可选 evidence_llm Associator，经公开 Associator 契约注入同一关系目录；角色事件写入后发现候选，再进入关系登记与冲突处理。旧 LLMAssociator 的共现/相似边不直接进入证据图，旧 ASSOCIATE 路径不被静默改造成确认事实。自动链使用验证优先、同来源显式时间纠正策略，可配置 LLM 辅助；依据不全时不选择胜者。人工裁决保存新修订并优先于自动结果。关系类型及状态以 S10 为准。

首次独立复查修正了两处错误：自动裁决不能丢失其验证关系依赖，角色图不能复用未分区的边 ID。验证关系变更后，已有裁决必须降级；图投影加入独立前缀，避免覆盖普通图边。原文和历史关系不物理删除。

接入交付包括 JiuwenSwarm provider 工具扩展，以及 WorkBuddy/Hermes/OpenClaw 可复用的远程 MCP stdio 桥。桥接只访问统一服务。历史支持 JSONL 预检/选择性导入、按原 Scope/ID 关联旧记忆、按批次补建与修订保护的撤回。迁移不是全库重新抽取，未知确认状态须按引用核对。

实现边界：无全量覆盖清单时关系覆盖始终 unknown；没有环境核验时 continuation_ready=false；任务映射管理首版仅创建负责人；source 隔离通过可信连接配置禁用，在普通读取及职责读取时重新检查；不实现任务执行所有权、自动推送或工作区迁移。自动发现只扫描已授权同项目的有界任务背景，不承诺全库关系发现。

仍未完成的验收是 G0 各真实产品版本、生产身份配置与真实调用轨迹，以及一批真实 JiuwenSwarm 存量和真实历史导出。仓内 API 三主体测试、MCP 编组测试和构造样本不替代这些验收，不据此宣称“三方已上线”。配置及操作见 [角色记忆示例](../../../examples/role_memory/README.md)。

### 14.2 回执恢复与条件支持语义复核

事件的背景更新和最终回执不是跨记录事务，但在 partial 保存可靠引用后可按同一事件恢复；补充崩溃点重启测试，确认既不重写正文也不重复背景。保留单调修订语义，不引入全库事务。可选关联失败记录脱敏错误类别，区分预期领域错误与异常程序错误；事件成功与关联完成分别表达。

视图补齐 supported_in_conditions，只对带证据和非空条件的已确认 supports 的判断端生效；不把确认验证方法、因果假设或验证关系等同于支持结论。按关系固有方向标注，反证待复核或明确反驳优先，撤回后重算。不因图遍历完成便声称历史/环境覆盖完整。

MCP 已将同步 API 放到工作线程，不存在所述直接嵌套循环；保留此调用约束。两处关系修改判权改用已读快照，去掉重复异步权限上下文读取。回执淘汰仍按 revision，图种子检索改为显式循环，行为不变。
