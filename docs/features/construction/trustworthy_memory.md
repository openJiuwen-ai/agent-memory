# 可信记忆（Trustworthy Memory）：有据 · 有时 · 有度

> 日期：2026-10-29
> 状态：方向提案（待立项）
> 方案设计：[F10 可信记忆](F10-trustworthy-memory.md)；下文目标语义不代表当前接口已实现。
> 英文表述：**Trustworthy Memory: Grounded · Timely · Calibrated**

---

## 1. 一句话定位

记忆系统在行业里大多比的是"**记得多**"，可信记忆要做的是"**记得对**"。

它要回答的核心问题只有一个：

> **对于这个提问者、这个时间点、这个场景，召回的每一条记忆该不该信、信到什么程度、应该怎么用。**

"对"拆成三个支柱：

| 支柱 | 含义 | 回答的问题 |
|---|---|---|
| **有据**（Grounded） | 每条记忆都能追溯来源，带签名，可审计 | 这条记忆从哪来？是谁说的？有没有被篡改？ |
| **有时**（Timely） | 知道它什么时候成立、什么时候过时 | 在问题所指的时间点，它还成立吗？ |
| **有度**（Calibrated） | 区分事实和推断，带置信度，拿不准就说拿不准 | 它是确定的事实，还是可能被推翻的推断？ |

此外还有两项贯穿三个支柱的能力：

- **可信度感知的召回呈现**：把三个支柱的信息交给回答模型，让它知道每条记忆该怎么用。
- **级联纠错**：源记忆被撤销或被认定为投毒时，由它衍生出的记忆跟着降级或失效。

## 2. 为什么做

### 2.1 用户与业务痛点

| # | 痛点 | 典型场景 | 现象 | 对应支柱 |
|---|---|---|---|---|
| 1 | **过时记忆** | 用户去年说住在北京，上个月说搬到了深圳 | 问"我住哪"时新旧两条一起被召回，回答模型只能猜 | 有时 |
| 2 | **"最新的"不等于"对的"** | 问"我去年在哪工作" | 只会"新的覆盖旧的"，于是返回了现在的公司 | 有时 |
| 3 | **推断被当成事实** | 系统从几次点菜推断"用户喜欢川菜" | 回答模型说"你说过你喜欢川菜"，听起来像用户亲口说的 | 有度 |
| 4 | **来源不可信 / 记忆投毒** | 网页、工具输出、第三方文档、其他 agent 写入的内容 | 和用户本人说的话同等权重，攻击者可以通过普通交互注入虚假记忆（MINJA，arXiv:2503.03704） | 有据 |
| 5 | **无法解释、无法定点纠错** | 用户问"你为什么觉得我……"，或者说"那条是错的" | 拿不出依据；删掉源记忆后，由它衍生出的摘要和技能仍然在生效 | 有据 + 级联纠错 |
| 6 | **多租户 / 多 agent 共享** | 群体记忆、跨 Space 召回 | 别人写入的记忆该信几分，没有判断依据 | 有据 + 有度 |

这些问题有一个共同点：**召回到了，但用错了**。只扩大召回、把召回做准解决不了它们，必须给每条记忆补上"能不能信、怎么用"的信息。

### 2.2 行业空白

- **冲突与陈旧**：各家记忆系统大多采用"追加"或"替换"两种策略，新旧矛盾的记忆经常共存。专门考察冲突处理和陈旧检测的新基准上，整体表现普遍偏低（具体基准与数字立项前核实）。
- **时间维度落不到检索上**：有的系统在存储层做了双时态知识图谱，但被指出检索阶段实际没用上时间。
- **记忆安全没有生产级方案**：投毒攻击已有公开研究，带溯源签名的防御还停留在论文阶段，开源记忆系统里几乎没有落地。
- **可解释性**：用户能否理解、编辑、审计 agent 的记忆，结构化记忆系统里还没有好的答案。

可信记忆正好落在这几块空白的交汇处。目前还没有开源系统把"时间 + 来源 + 置信度 + 签名审计"作为一个整体做完整。

### 2.3 评测与竞争

- **LoCoMo 和 LongMemEval 头部分数已接近天花板**，单纯刷分很难形成差异化。可信记忆的价值集中在这两个基准中**最难、也最难刷**的几类题上：

| 基准 | 题型 | 可信记忆的作用 |
|---|---|---|
| LongMemEval | knowledge-update | 新旧记忆区分清楚，旧的标记失效，不再和新的一起交给回答模型 |
| LongMemEval | temporal-reasoning | 按问题所指时间点取当时有效的记忆 |
| LongMemEval | abstention | 用置信度判断该不该拒答 |
| LongMemEval | single-session-preference | 推断出的偏好以信念形式存在，带置信度 |
| LoCoMo | adversarial | 推断和事实分开，减少"自信地答错" |
| LoCoMo | open-domain / 推理类 | 推断结论预先归纳，召回时附带依据 |

- **新基准是首发阵地**：冲突处理和陈旧检测类基准还没被刷满，有机会拿到首发成绩。
- **安全攻防可以直接展示**：投毒前后的攻击成功率对比，是很直观的演示材料。

### 2.4 为什么由我们来做

可信记忆不需要另建一套系统，我们已经有大部分零件，差的是把它们连起来：

| 零件 | 现有能力 | 位置 |
|---|---|---|
| 双时态字段 | `Temporal` 有 `t_event` / `t_ingest` / `t_valid` / `t_invalid` / `t_message` 五个时间字段 | `jiuwen_memory/common/type_def/memory.py` |
| 版本更替 | SUPERSEDE 时旧版标记 `SUPERSEDED`，并写入 `t_invalid` | `storage/domain_store_impl/composite_domain_store.py`、`control/engine_impl/cloud_engine.py` |
| 有效期过滤 | 检索谓词按 `t_invalid > t` 过滤，支持 `as_of` 回溯 | `retrieval/retriever_impl/predicate_builder.py` |
| 演进血缘 | `provenance`（多→一合成来源）、`supersedes`（版本链）、`source_ref` | `common/type_def/memory.py` |
| 签名能力 | 链式 HMAC 审计、KeyProvider 管理的 MAC 密钥 | `common/security/audit_integrity/` |
| 抽取支持评分 | Extractor/Abstractor 有 LLM 自评分与文本 evidence；不是校准概率 | `construction/extractor_impl/llm_extractor.py`、`construction/abstractor_impl/llm_abstractor.py` |
| 多租户 | Scope 五维隔离、Space、群体记忆 | `control/collective/` 等 |
| 后台演进 | Dreaming 定时 evolve，每轮重新鉴权 | `api/memory_api_impl/dreaming.py` |

竞品通常只具备其中一两项（例如只有时序图谱，或只有置信度），我们是少数能**同时具备全部零件**的系统。

## 3. 要做什么

### 3.1 有据（Grounded）：来源分级 + 证据链 + 记忆级签名

**来源分级**：每条记忆标明来源类别，并映射到可信等级：

| 来源类别 | 示例 | 默认可信等级 |
|---|---|---|
| `user_stated` | 用户本人明确陈述 | 高 |
| `user_observed` | 从用户行为观察到（选择、点击、操作） | 中高 |
| `agent_inferred` | agent 归纳推断 | 由证据决定（见"有度"） |
| `tool_output` | 工具或 API 返回 | 中 |
| `document_import` | 导入的文档、网页 | 中低，可按来源白名单调整 |
| `peer_agent` | 其他 agent 写入 | 由该 agent 的权限和历史可信度决定 |

可信等级是**策略可配置**的，不写死在代码里。企业场景可以按组织、Space、agent 单独设定。

**证据链**：

- 衍生记忆（摘要、推断、技能）通过 `evidence_ids` 指向它所依据的原始记忆。
- 与现有 `provenance` 的分工：
  - `provenance` 记录"由谁合成而来"（构建血缘）；
  - `evidence_ids` 记录"凭什么相信它"（认知依据）。
  - 两者可能重合，但语义不同。例如一条推断可能由 A 合成，但同时被 B、C 佐证。
- 召回时可以展开证据链，回答"你为什么这么认为"。

**记忆级签名**：

- 把现有的 HMAC 能力从审计事件下沉到每一条记忆。
- 对规范化后的"内容 + 关键元数据（来源、时间、scope）"计算签名，密钥统一经 KeyProvider 获取。
- 召回时校验签名。签名失效或缺失的记忆，按策略降权、隔离或过滤。
- 与审计链联动：每次写入、取代、撤销都留下可验证的审计记录。

**级联纠错**：

- 源记忆被撤销、被判定为投毒、或被证伪时，沿 `evidence_ids` 和 `provenance` 反向找到所有衍生记忆。
- 根据衍生记忆对该证据的依赖程度，降低置信度、标记待复核，或直接失效。

### 3.2 有时（Timely）：双时态语义贯通全链路

**语义统一**：明确两条时间轴的含义，并贯彻到写入、演进、检索和呈现的每一步：

| 时间轴 | 字段 | 含义 |
|---|---|---|
| 世界时间（目标） | 独立世界有效区间，见 F10 | 这件事**在现实中**从何时起成立、何时起不再成立；不直接重解释已有 `t_valid` / `t_invalid` |
| 系统时间 | `t_ingest` 及拟议修订历史 | 系统**何时得知**、何时改变认知；现有版本链不足以恢复所有原位修改前的状态 |

**取代时的失效时间**：

- 现状：不同路径存在差异；`CloudEngine.update` 可传入 `patch.t_valid`，缺省才取当前时间，文档块编辑等路径使用当前时间。现有 `t_valid` 的语义是系统认为成立的时间，不能直接视为已实现世界有效时间。
- 目标：优先使用新事实的世界生效时间（例如"上个月搬到深圳"→ 上个月）。抽取阶段要尽量解析出变化发生的时间，解析不出时再退回写入时刻，并标注精度。

**按问题所指时间召回**：

- 查询解析识别问题的时间意图："现在""去年""搬家之前"。
- 现在时 → 只取当前有效的记忆。
- 过去时 → 用 `as_of` 取该时间点有效的记忆。
- 演变类（"我换过几次工作"）→ 取整条版本链，按时间排序。

**时间线呈现**：同一主体同一属性的多个版本，以时间线形式交给回答模型，而不是平铺成几条互不相干的记忆。

**与现有能力的关系**：Schema 时序支路已经实现 latest / snapshot / history / range 四种查询模式（默认关闭）。本项工作是把同样的语义推广到主链路的普通记忆。

### 3.3 有度（Calibrated）：认知状态 + 置信度 + 两种更新模式

**认知状态**（epistemic status），每条记忆必填：

| 状态 | 含义 | 更新模式 |
|---|---|---|
| `stated` | 当事人明确陈述 | 确定性取代 |
| `observed` | 观察到的行为或事件 | 确定性取代 |
| `inferred` | 推断出的结论（即**信念记忆**） | 渐进修正 |
| `imported` | 外部导入 | 确定性取代，可信等级由来源决定 |

**置信度**（`confidence` ∈ [0, 1]）来源分两类：

- 事实类（`stated` / `observed` / `imported`）：主要由**来源可信等级**决定。
- 推断类（`inferred`）：由**证据聚合**决定。支持证据越多越高，出现反驳证据就降低，长时间没有新证据时缓慢衰减。

**两种更新模式**：

- **确定性取代**：事实变了，旧版直接失效（写入 `t_invalid`，标记 `SUPERSEDED`）。复用现有 SUPERSEDE 链路。
- **渐进修正**（信念修正）：
  - 新证据**支持** → 提高置信度，追加 `evidence_ids`；
  - 新证据**反驳** → 降低置信度；
  - 置信度跌破阈值 → 信念失效，必要时生成反向信念；
  - 用户**明确否认** → 直接推翻（相当于 `stated` 级证据）。

**置信度校准**：

- 置信度要和实际正确率对得上（标称 0.8 的记忆，大约 80% 是对的）。
- 用评测集或线上反馈做校准，并用 ECE 等指标衡量。
- 没有校准的置信度对回答模型没有意义。

**拿不准就说拿不准**：召回结果整体置信度过低，或者存在未消解的冲突时，引导回答模型保守作答或拒答，不编造答案。

### 3.4 冲突检测与消解

- **写入时**：新记忆与同一主体、同一属性的既有记忆比对，识别"更新""补充""矛盾"三种关系。
  - 更新 → 确定性取代；
  - 补充 → 并存；
  - 矛盾且无法判定先后 → 两条都保留，标记冲突，降低置信度。
- **Dreaming 时**：后台批量扫描未消解的冲突，结合来源等级、时间、证据数量尝试消解；无法消解的保留冲突标记，等新证据出现。
- **召回时**：未消解的冲突以"存在矛盾记录"的形式明确交给回答模型，不让它在不知情的情况下二选一。

### 3.5 可信度感知的召回呈现

这是三个支柱最终产生效果的地方，对跑分的影响可能也最直接：很多知识更新题和时间推理题失分，是因为新旧记忆被一起交给了回答模型，而回答模型不知道该信哪条。

- **排序**：可信度（来源等级 × 置信度 × 签名状态 × 时效）作为重排信号之一，与相关性一起参与排序。
- **分组**：同一主体同一属性的记忆归为一组，按时间线排列。
- **标签化**：每条召回记忆附带简洁标签，例如：

  ```
  [用户陈述 | 2026-09 起有效 | 取代"住北京"(2024-03 ~ 2026-09)] 用户住在深圳
  [推断 | 置信度 0.7 | 依据 3 条点餐记录] 用户可能喜欢川菜
  [冲突 | 两条记录矛盾，尚未消解] 用户的生日：3 月 5 日 / 5 月 3 日
  ```

- **回答约定**：在答案生成的提示中明确标签的用法，例如：优先使用当前有效的陈述；推断类用保守措辞；冲突类说明不确定性。这样回答模型才能给出"截至 9 月你住在深圳，此前在北京"这样的答案。
- **渐进式披露**：与现有 L0/L1/L2 分层披露结合。默认只给简洁标签，需要时再展开证据链。

### 3.6 数据模型草案

在 `MemoryUnit` 上新增或明确以下信息（作为一等字段还是放进 `system_metadata`，待定，见第 9 节）：

| 字段 | 类型 | 支柱 | 说明 |
|---|---|---|---|
| `source_kind` | 枚举 | 有据 | 来源类别（见 3.1） |
| `trust_level` | 数值 / 枚举 | 有据 | 来源可信等级，由策略计算 |
| `evidence_ids` | `list[str]` | 有据 / 有度 | 认知依据 |
| `signature` | `str` | 有据 | 记忆级 HMAC 签名 |
| `key_ref` | `str` | 有据 | 签名密钥引用 |
| 世界有效区间 | 拟新增 | 有时 | 与既有 `temporal.t_valid` / `t_invalid` 兼容语义分开，详见 F10 |
| `temporal_precision` | 枚举 | 有时 | 时间精度：日 / 月 / 年 / 未知 |
| `epistemic` | 枚举 | 有度 | `stated` / `observed` / `inferred` / `imported` |
| `confidence` | `float` | 有度 | 置信度 [0, 1] |
| `conflict_with` | `list[str]` | 有度 | 未消解冲突的对端记忆 |

已有字段 `provenance`、`supersedes`、`source_ref`、`lifecycle` 保持原语义，与新字段配合使用。

## 4. 范围

### 4.1 覆盖范围

- **记忆类型**：全部记忆，包括事实、推断、经验和技能、文档记忆。可信度是所有记忆共有的属性，不是新的记忆类别。
- **生命周期**：写入 → 演进（取代、修正、冲突消解、衰减）→ 召回 → 呈现 → 纠错，全链路覆盖。
- **场景**：
  - 个人助手：住址、工作、偏好等属性会变化的信息；
  - 企业与多 agent：来源复杂，有共享，对安全和审计有要求；
  - 长期运行的 agent：记忆不断累积，过时和矛盾会越来越多。

### 4.2 收益集中的场景

可信记忆的价值集中在**有变化、有矛盾、有多个来源、有推断**的场景。属性稳定、只有单一来源的简单事实召回（例如"我女儿叫什么"）收益有限。评测和宣传应聚焦前一类场景。

## 5. 区别与联系

### 5.1 与信念记忆

**区别**：

- **信念记忆是一类记忆**：agent 推断出的结论，带置信度，会随新证据修正。它回答"我认为用户或世界是什么样"。
- **可信记忆是一套适用于所有记忆的机制**：判断每条记忆此刻能不能信、怎么用。

| 维度 | 信念记忆 | 可信记忆 |
|---|---|---|
| 作用对象 | 只针对推断出的结论 | 全部记忆 |
| 核心问题 | 我推断出了什么，有多确定 | 这条记忆还成立吗？从哪来？有多确定？有没有被篡改？ |
| 关键机制 | 证据归纳、置信度、信念修正 | 双时态、来源分级、置信度、证据链、签名审计、召回标签化 |
| 典型例子 | "用户可能喜欢川菜"（置信度 0.7，依据 3 次点菜记录） | "用户住深圳"：用户亲口说的，2026-09 起有效，取代了北京那条，签名有效 |
| 防的错误 | 推断不准、推断不更新 | 过时、时间错位、推断被当事实、投毒、无法追溯 |

**联系**：

1. **信念记忆是可信记忆的一部分**：`epistemic = inferred` 的记忆就是信念记忆，对应"有度"支柱的核心。
2. **信念修正依赖另外两个支柱**：新证据能不能推翻旧信念，要看时间（是不是更晚）和来源（是不是更可信）。没有时间和来源，信念修正就退化成"谁新谁覆盖"。
3. **置信度统一**：事实的可信度来自来源等级，信念的置信度来自证据聚合，两者在召回时归到同一个可信度打分里。
4. **两种更新方式互补**：事实走确定性取代，信念走渐进修正。
5. **推断要回到事实**：信念通过 `evidence_ids` 指向依据的事实。事实被撤销或证伪时，信念跟着降级，即级联纠错。

**实现上不新增"信念"tier**，用认知状态字段区分即可。这样复用现有的 SUPERSEDE、双时态和血缘，不会出现两套并行的机制。

### 5.2 与现有 SUPERSEDE / 双时态 / 血缘

可信记忆是这三项能力的**语义深化和链路贯通**，不是替代：

| 现有能力 | 现状 | 可信记忆在其上补什么 |
|---|---|---|
| SUPERSEDE | 新版取代旧版，旧版标记失效 | 区分更新、补充、矛盾；引入渐进修正；失效时间改用世界时间 |
| 双时态 | 字段齐全，检索按 `t_invalid` 过滤；完整的时序查询只在 Schema 支路，默认关闭 | 世界时间与系统时间语义统一；主链路支持按问题时间意图召回；时间线呈现 |
| 血缘 | `provenance` / `supersedes` 记录构建关系 | 增加认知依据 `evidence_ids`；支持反向级联纠错 |

### 5.3 与安全治理（认证、加密、审计）

- 现有安全能力保护的是**访问和存储**：谁能读写，落盘是否加密，操作是否可审计。
- 可信记忆把安全延伸到**内容本身**：这条记忆的来源是否可信，内容是否被篡改，召回时是否应该使用。
- 记忆级签名复用现有 KeyProvider 和 HMAC 能力，审计链记录记忆的写入、取代、撤销全过程。两者结合可验证系统保护后的内容完整性与操作记录；HMAC 本身不能证明原始作者身份或内容真实。

### 5.4 与 Dreaming

- Dreaming 是可信记忆的**后台执行者**：冲突消解、置信度衰减、级联纠错、信念归纳，都适合在后台批量进行。
- 可信记忆反过来给 Dreaming 提供**约束**：整理产生的新记忆（摘要、推断）必须带认知状态、置信度和证据链，不能凭空制造"事实"。
- 进一步可以在 Dreaming 中加入整理后自检：整理完自动出题验证，整理后答不对、整理前答得对时，回滚这次整理。

### 5.5 与经验记忆

- 当前分支没有经验 Curator/Wilson 实现；不能把其他分支的能力作为可信记忆的现有复用基础。
- 可信记忆为各类记忆统一评估语义和呈现方式；当前抽取自评分只保留为诊断，不作为校准概率。
- 经验和技能同样适用"有据"：每条技能可以追溯到它归纳自哪些轨迹；轨迹被判定有误时，技能跟着降级。

### 5.6 与多租户 / 群体记忆

- Scope 和 Space 解决的是**能不能看到**。
- 可信记忆解决的是**看到之后信几分**：跨 Space、跨 agent 召回的记忆，按写入方的来源类别和可信等级参与排序和呈现。

## 6. 现状与缺口

| 支柱 | 已有 | 缺口 |
|---|---|---|
| 有据 | `source_ref`、`provenance`、`supersedes`；审计事件的链式 HMAC | 没有来源类别和可信等级；没有认知依据链；签名没有落到每条记忆；检索不使用来源信息；没有级联纠错 |
| 有时 | 五个时间字段；取代时写入 `t_invalid`；检索按有效期过滤；`as_of`；Schema 时序（默认关闭） | 失效时间默认取写入时刻，世界时间与系统时间语义需要统一；主链路没有按问题时间意图召回；没有时间线呈现 |
| 有度 | Extractor/Abstractor 的 LLM 自评分与文本 evidence（尚未校准、未验证片段） | `MemoryUnit` 没有认知状态和置信度；没有统一的渐进修正与置信度校准；已有 ConflictResolver 和冲突图语义，尚需贯通可信主链路 |
| 召回呈现 | L0/L1/L2 分层披露 | 召回结果直接拼进提示，没有可信度标签、分组和回答约定 |

## 7. 验证方案

### 7.1 前置：建立分项基线

- 在 LongMemEval-S（500 题）和 LoCoMo 全量上跑出分项成绩，同时记录 tokens/query 和延迟。judge 模型固定并公开。
- 仓库目前还没有提交过端到端分项成绩，这一步是衡量后续收益的前提。

### 7.2 失分归因

抽查 knowledge-update、temporal-reasoning 两类题的召回结果，统计失分中有多少属于以下情况：

- 新旧记忆同时被召回，回答模型选错；
- 应取过去某个时间点的值，实际取了最新值；
- 推断被当成事实作答。

这一步可以在动手前量化可信记忆能拿回多少分。

### 7.3 评测指标

| 支柱 | 指标 | 评测来源 |
|---|---|---|
| 有时 | knowledge-update / temporal 准确率；陈旧率（召回结果中已失效记忆的占比） | LongMemEval、LoCoMo、陈旧检测类基准 |
| 有度 | abstention 准确率；置信度校准误差（ECE）；冲突识别准确率 | LongMemEval、冲突处理类基准 |
| 有据 | 投毒攻击成功率（启用前后对比）；证据链可追溯率；级联纠错覆盖率 | 自建攻防集（参考 MINJA） |
| 整体 | 分项准确率不下降的前提下的 tokens/query 与延迟 | 全部基准 |

## 8. 推进节奏

| 阶段 | 内容 | 交付物 |
|---|---|---|
| 第 0 步 | 分项基线 + 失分归因 | 基线报告；收益预估 |
| 第 1 步：有时 | 双时态语义统一；取代时使用世界时间；主链路按时间意图召回；时间线呈现 | knowledge-update / temporal 分项提升 |
| 第 2 步：召回呈现 | 可信度标签、分组、回答约定 | 端到端分项提升；"为什么这么认为"可展示 |
| 第 3 步：有度 | 认知状态、置信度、渐进修正、冲突标记与消解、校准 | abstention / 冲突类指标；信念记忆能力 |
| 第 4 步：有据 | 来源分级、证据链、记忆级签名、级联纠错 | 投毒攻防对比演示；可审计的记忆来源 |
| 持续 | 与 Dreaming 结合：后台冲突消解、衰减、整理后自检 | 后台演进可验证 |

第 1、2 步直接对准跑分最难的几类题，见效最快，先做。第 3、4 步形成完整的差异化能力和宣传亮点。

## 9. 对外表达

**名称**：可信记忆（Trustworthy Memory）

**口号**：可信记忆：有据、有时、有度
（Trustworthy Memory: Grounded · Timely · Calibrated）

**主张**：不止记得多，更要记得对。

**宣传结构与技术结构一一对应**：

| 宣传点 | 技术支撑 | 可展示材料 |
|---|---|---|
| 有据：每条记忆都能追溯，不怕投毒 | 来源分级、证据链、记忆级签名、审计链 | 投毒攻防对比；"为什么这么认为"演示 |
| 有时：知道什么过时了 | 双时态、按时间意图召回、时间线 | knowledge-update / temporal 分项成绩；"截至 X 月……此前……"示例 |
| 有度：拿不准就说拿不准 | 认知状态、置信度、信念修正、校准 | abstention 成绩；置信度校准曲线 |

**对外引用竞品数字的原则**：只引用能点开原始来源核实的数字，并注明 judge 模型与评测配置。

## 10. 待决问题

1. 新增字段作为 `MemoryUnit` 一等字段，还是放进 `system_metadata`。前者语义清晰、可索引，后者对现有接口影响小。
2. 来源可信等级的默认策略，以及企业场景下按组织、Space、agent 覆盖的配置方式。
3. 记忆级签名覆盖哪些字段。签名范围过大，正常的元数据更新会导致签名失效；过小则起不到防篡改的作用。
4. 置信度阈值、衰减速率、渐进修正幅度的初始取值与校准方法。
5. 召回标签的格式与回答约定，需要在评测上做对照实验后确定。
6. 涉及的公开接口变化（返回结果携带可信度信息、证据链展开、撤销与级联），需要同步修订的 specs 范围。
