## 背景

业务系统通常已经有自己的日志收集方式，比如统一写入日志平台、按文件大小切分日志、
清理过期文件。把 SDK 嵌入业务系统后，希望 SDK 的运行日志也能交给这套系统处理。

之前 SDK 主要负责把日志打印到终端或写入文件，没有提供接入业务日志处理器的公开参数。
这次增加接管入口，同时保留原来的日志内容和脱敏规则，并允许在配置文件中调整输出样式。

本次只处理 SDK 运行日志。审计记录，以及 CLI、HTTP、MCP 各自的入口日志，保持原来的行为。

## 决策

下面说的“配置”，指创建 SDK 时通过 `assemble(config=...)` 或
`assemble_runtime(config=...)` 传入的配置。可以直接传 Python 字典，也可以用
`Config.from_yaml("文件路径")` 读取业务自己的 YAML 文件后传入。SDK 没有固定的日志配置
文件，也不会自动查找文件；下文的 `sdk_logging.yml` 只是示例文件名。

### 业务怎样接收日志

创建 SDK 时，通过 `assemble()` 或 `assemble_runtime()` 的 `log_handler` 参数传入业务的
日志处理器。这个参数必须用参数名传递，原有调用方式不用改。

日志处理器使用 Python 标准库的 `logging.Handler`。它负责接收日志，再决定写文件、
发往日志平台，或交给业务现有的日志框架。SDK 交给它的是 `LogRecord`，也就是包含正文、
级别、模块名、源码位置等信息的日志记录；交付前仍按现有规则脱敏，没有关闭脱敏的开关。

处理器由业务创建和关闭。SDK 不会因为某个实例关闭，就关闭这个处理器，因为其他 SDK
实例或业务代码可能还在使用它。

### 日志输出到哪里

这份配置中的 `globals.log_output` 决定输出方式：

| 配置值 | 输出到哪里 |
|---|---|
| `builtin` | SDK 自己打印到终端；配置了 `log_file` 时，还会追加写入该文件 |
| `business` | 只交给业务传入的处理器，不创建 SDK 自己的终端或文件输出 |
| `both` | 同时交给业务处理器，并使用 SDK 自己的终端和可选文件输出 |

首次初始化时，如果没有配置 `log_output`，一律默认选 `builtin`，即使传入了业务处理器也
不会调用它。要让业务处理器接收日志，需要明确选择 `business` 或 `both`；选择这两种模式
却没有提供处理器，初始化会报错。

这里的“只交给业务”只约束 SDK 新建的输出。如果业务此前手工给 SDK 日志器添加过处理器，
SDK 会保留它们。因此，不要把同一个处理器既手工添加到 SDK 日志器，又通过 `log_handler`
传入，否则同一条日志会收到两次。

### 日志样式由谁决定

SDK 自己的输出使用 `config` 中的 `globals.log_format` 和 `globals.log_datefmt`。
业务处理器如果已经设置了格式化器（`Formatter`），就保留业务的格式；如果没有，SDK 会
为它设置同样的格式。
业务处理器原有的级别限制和过滤条件也继续生效。

SDK 管理的两路输出都会先检查 `globals.log_level`，业务处理器再执行自己的级别和过滤条件。
即使应用把某个 SDK 子日志器设成更低级别，也不能绕过这个统一门槛。例如 SDK 配置为
`ERROR`，业务处理器未限制级别，子日志器产生的 INFO 日志也不会交给业务；SDK 配置为
`INFO`、业务处理器设为 `ERROR` 时，SDK 内置输出接收 INFO 及以上，业务只接收 ERROR 及以上。

例如，在 `log_format` 中加入 `%(pathname)s:%(lineno)d`，就能显示源码文件路径和行号；
加入 `%(funcName)s`，就能显示函数名。这些信息本来就在日志记录中，不需要修改打印语句。

双路输出时，每个输出拿到一份单独的日志记录，避免业务处理器修改正文或字典、列表后，
SDK 文件里也跟着变化。自定义业务对象和异常信息仍可能被两份记录共同引用；具体复制范围见
[S02 日志接管说明](../../specs/S02-memory-api.md#sdk-运行日志接管)。

### YAML 中分别筛选两路正文

业务可能只想上传值得关注的日志，同时在 SDK 本地保留更完整的信息。因此新增
`globals.log_filters.business` 和 `globals.log_filters.builtin`，两路各自可配置
`include`（只保留匹配项）和 `exclude`（排除匹配项），不配置时不过滤。

```yaml
globals:
  log_output: both
  log_level: INFO
  log_filters:
    business:
      include: '超时|连接失败'
      exclude: '健康检查'
    # 不配置 builtin：SDK 内置输出保持 INFO 及以上，不按正文过滤。
```

本例中，“查询超时”同时进入业务和内置输出；“初始化完成”只进内置输出；
“健康检查连接失败”也只进内置输出，因为业务的排除规则优先。
业务处理器已有的级别和 Filter 仍然生效，正则不能让低于级别门槛的记录重新输出。

匹配使用 Python 标准正则，正文任意位置匹配成功即可。匹配的内容是脱敏后、填入参数的
正文，避免依据未脱敏数据筛选，也避免改变格式后筛选结果跟着变化。不匹配另附的异常
堆栈，不修改日志内容。两路依据业务处理前准备的正文判断，不受业务修改记录影响。

规则在初始化时编译，不在每条日志处理时重复编译。配置写错就报错，不能静默丢日志。
规则和其他日志设置一样，在进程内固定；后续省略的规则逐项继承，显式不同的规则报冲突。
完整字段、`null` 和错误处理约定见 [S08](../../specs/S08-config.md#两路独立的正文正则过滤)。

### 同一个进程里的 SDK 实例共用配置

同一个 Python 进程可能创建多个 SDK 实例，但它们共用一套日志设置。首次日志初始化成功后，
设置就固定下来，避免后创建的实例改变前面实例的日志输出。

- 后续实例没有传日志配置或处理器时，继续使用已有设置。
- 再次传入相同配置、同一个处理器对象时，可以正常创建实例，不会重复安装处理器。
- 换成不同配置或另一个处理器对象时，会报配置冲突；即使两个处理器写的是同一个文件，
  也属于不同对象。
- 关闭某个 SDK 实例不会清除这套日志设置。

“首次初始化成功”指日志设置已经完成。如果接下来的模型加载或存储初始化失败，日志设置
仍然保留，方便继续记录错误；之后再次创建 SDK 时，也需要沿用这套设置。

日志初始化失败时会尝试恢复业务处理器原有的 Formatter；如果恢复也失败，会报告安全故障
提示，并继续抛出最初的初始化异常，避免后面的恢复错误掩盖真正原因。故障提示通过独立的标准 StreamHandler 直接输出到 stderr，不挂到 SDK、业务或根日志器。
它自己的写入错误也被接住，失败时返回状态并停止报告，不打断业务，也不递归调用日志系统。

### 覆盖哪些现有日志

SDK 中有两种获取日志器的写法：封装的 `get_logger()` 生成 `agent_memory.*` 名称，直接使用
`logging.getLogger(__name__)` 则生成 `jiuwen_memory.*` 名称。两种都是 SDK 运行日志。
本次同时接收它们，保留原名称和源码位置，不修改业务进程的全局日志配置或第三方库的日志。

### 安装路由时不打乱正在输出的日志

SDK 分发器仍放在原有命名空间处理器之前，先为 SDK 各输出准备独立记录。
安装和失败回滚时，在 Python logging 的模块锁内构造并发布新的处理器列表，
与其他线程通过标准接口增删处理器协调，不在正在使用的旧列表上删除或插入。
已经开始遍历旧列表的日志继续完成，避免原有处理器重复执行或跳过后续处理器。
这不会为初始化前的日志补发 SDK 输出，也不接管应用自行重设日志配置的行为。

### 业务处理器报错时怎么办

如果业务处理器向 SDK 抛出普通异常，SDK 会继续执行当前业务操作。双路模式下，SDK 自己的
输出也会继续。SDK 会绕过业务处理器，直接向标准错误输出（`stderr`，通常显示在终端）
写入一条故障提示，包含处理器类名、异常类型和文件、行号、函数位置，便于定位问题。
提示不包含原日志正文、异常消息或源码内容；即使写提示也失败，也不会因此中断业务操作。

脱敏步骤也可能因为自定义容器读取失败而抛异常。此时不再向 SDK 管理的输出分发该条记录，直接报告不含正文和
异常值的故障提示，后续正常日志继续处理。源日志器和分发器上的脱敏都受保护，不能只保护
分发器而让异常从前面的日志器 Filter 抛回业务。

SDK 分发器处理日志期间，同一线程再次产生的嵌套 SDK 日志会跳过整个 SDK 分发器，
既不交给业务处理器，也不进入 SDK 内置终端或文件输出，以避免递归。这只约束 SDK 管理的
输出；应用自己挂接的处理器和第三方日志不由这道保护控制。
处理器内部自行忽略的错误，SDK 无法感知；处理器是否成功写盘、上传以及怎样清理旧日志，
仍由业务负责。

## 拒绝的方案

- **直接修改整个进程的日志配置**：会影响业务自身和第三方库的日志，所以只接入 SDK 的
  日志器。
- **每个 SDK 实例使用不同的处理器**：现有日志器在进程内共用。要区分日志来自哪个实例，
  还需要新增实例标识和分发逻辑，会扩大本次改动。
- **运行中切换配置，或关闭实例时重置日志**：其他实例可能正在输出日志，这样做会影响它们。
  本次选择在进程启动时确定配置。
- **由 SDK 关闭业务处理器**：这个处理器可能还服务于其他业务代码，应由业务决定何时关闭。
- **两路共用一个正则开关**：业务减少上传量时，本地也可能丢失排查所需的日志，故分别配置。
- **匹配最终打印文本或修改日志正文**：格式变化会影响匹配，正文替换也超出已确认范围，
  所以只对脱敏正文做选择，继续使用标准 logging 的 Handler 和 Formatter。

## 配置文件和 SDK 装配示例

需要由业务开发者手动创建一个 YAML 文件，将下面的配置写进去。文件可以放在业务项目中，
名称和位置自行决定；本例使用 `sdk_logging.yml`。SDK 不会自动创建或保存这个配置文件。

后面的 Python 示例通过 `Config.from_yaml("sdk_logging.yml")` 读取它，再通过 `config`
参数传给 SDK。这里的相对路径以程序启动时的工作目录为准，也可以改成文件的绝对路径。

这份配置选择双路输出：SDK 追加写入自己的日志文件，业务处理器则写入另一个日志文件，
并按文件大小切分、清理旧文件。配置文件与这些运行时产生的日志文件是不同的文件。

```yaml
globals:
  log_level: INFO
  log_format: "%(asctime)s %(levelname)s %(name)s %(pathname)s:%(lineno)d %(funcName)s %(message)s"
  log_datefmt: "%Y-%m-%d %H:%M:%S"
  log_output: both
  log_file: ./var/log/agent-memory-sdk.log
```

```python
from logging.handlers import RotatingFileHandler
from pathlib import Path

from jiuwen_memory.api import assemble_runtime
from jiuwen_memory.config import Config

Path("./var/log").mkdir(parents=True, exist_ok=True)
business_handler = RotatingFileHandler(
    "./var/log/business-sdk.log", maxBytes=1_000_000, backupCount=5, encoding="utf-8"
)
# 本例没有给业务处理器设置 Formatter，所以业务输出和 SDK 内置输出
# 都使用 sdk_logging.yml 中的 log_format、log_datefmt，样式相同。
# 如需业务自己的样式，在创建 SDK 前调用 business_handler.setFormatter(...)；
# SDK 会保留业务样式，只有内置输出继续使用 YAML 中的样式。
try:
    runtime = assemble_runtime(
        config=Config.from_yaml("sdk_logging.yml"),
        log_handler=business_handler,
    )
    try:
        # 使用 runtime.api 执行业务操作，SDK 日志会同时写入两边。
        pass
    finally:
        runtime.close()
finally:
    business_handler.close()  # handler 归业务方管理
```

示例中的业务处理器把每个文件限制在约 1 MB，并最多保留 5 个备份文件。SDK 自己的文件只是
持续追加写入，不负责切分和清理。

如果只想交给业务处理器，把 `log_output` 改成 `business` 即可；此时 `log_file` 不生效，
可以删除。同一进程中，后续创建 SDK 实例时可以省略 `log_handler`，继续使用首次传入的对象。

## 验证

仓库交付日志专项测试，可以运行：

```sh
.venv/bin/python -m pytest tests/unit/api/test_sdk_logging.py
```

业务接入时，按上文的 YAML 和 Python 示例手动准备配置及处理器。完整演示脚本和配套
YAML 仅在本地保留，不随代码交付；以下是本次已经验证的接入场景，不依赖仓库中存在
额外示例文件。

| 场景 | 接入方式 | 预期结果 |
|---|---|---|
| 默认输出 | 不传 `config`，只传业务处理器 | 默认 `builtin`，业务处理器不接收日志 |
| 显式内置输出 | 配置 `log_output: builtin` | SDK 终端及可选内置文件输出 |
| 业务独占 | 配置 `log_output: business` 并传业务处理器 | 业务收到日志，SDK 不创建内置输出 |
| 双路、相同样式 | 配置 `both`，业务不设置 Formatter | 两路使用 SDK 配置的样式 |
| 双路、不同样式 | 配置 `both`，业务预先设置 Formatter | 业务保留自己的样式，内置输出使用 SDK 配置 |
| 两路正则不同 | 两路分别配置 include / exclude | 依据各自规则筛选，互不影响 |

专项测试覆盖正文参数填充与脱敏、两路规则独立、业务修改共享对象不改变内置筛选决定、
无规则时不提前拼接正文、匹配异常隔离，以及规则继承、冲突和非法配置无副作用。
另以真实 YAML、SDK 装配、分词组件和文件 Handler 验证双路输出、业务独占、处理器故障、
无效规则后重试和多实例复用；这些检查不替换 SDK 内部路由。

并发回归通过事件同步重现安装与日志输出的交错，验证两个 SDK 命名空间的原有处理器
不会重复处理同一条记录，初始化失败回滚也不会跳过正在遍历的后续处理器。
已有递归用例验证业务处理器只被调用一次、内置文件只有外层记录，保持嵌套记录跳过整个
SDK 分发器的约定。

## 已知遗留

- 接管从日志初始化完成后才生效。此前导入模块、注册插件时已经输出的日志，不会补发给
  业务处理器；本次没有调整启动顺序。
- 要更改日志格式、级别、输出方式、正则或业务处理器，需要重新启动进程。
- 正则同步执行，不提供单条匹配超时；复杂表达式可能拖慢产生日志的 SDK 调用。
- 处理器是同步执行的。如果它卡住，当前 SDK 调用也会等待。业务需要自行处理上传超时、
  异步收集、文件切分和旧日志清理等问题。
- CLI、HTTP、MCP 的入口日志，以及审计记录，仍由各自原有机制处理。
