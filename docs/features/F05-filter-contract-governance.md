# F05 — filters 契约治理：把公共过滤语言当产品治理

- 日期：2026-09-14
- 状态：设计定稿；团队执行版规范见 [F06-filter-governance-playbook.md](F06-filter-governance-playbook.md)
- 关联：`docs/features/F04-dreaming.md`（演进侧消费方）、`jiuwen_memory/common/type_def/filter.py`（契约本体）

## 0. 背景与动机

dreaming 复用检索的 filters（同一 `FilterExpr` 类型、同一套后端编译器）之后，出现了这样的担心：
「dreaming 复用 filters 会影响到检索的 filters」。

这句话的正确版本与错误版本必须分开：

- **错误版本**：dreaming 的过滤条件会串进检索查询、改变检索行为。——不成立。每次检索的
  FilterExpr 是请求期现场构造的独立实例，dreaming 的谓词在 resolver/装配期构造、存注册表，
  两边互不读取（实例隔离）。
- **正确版本**：两者**共享**的不是"句子"而是"语言 + 翻译官"——词汇表（`FilterOp` 算子、
  字段规则）与管道（`normalize`、四个后端编译器、内存求值器）。**共享层一旦演进，双消费方
  联动**。担心的是演进期联动成本，不是运行期串味。

因此治理对象是**共享层的演进方式**。反方案——dreaming 与检索各搞一套 filters——更糟：
词汇表分裂 = 每个后端编译器要翻两套语言 = 方言地狱。结论：**共用 + 治理**。

## 1. 三层模型

```
L3 消费层（各自造句，互不可见——实例隔离）
    检索：predicate_builder 造系统谓词 + 用户表达式
    演进：resolver 造候选谓词（dreaming 时间窗等）
        │ 两边只"说"这门语言，谁也不读谁的句子
        ▼
L2 编译层（四个翻译官：pg / ES / Milvus / Python 求值器）
    每个算子必须显式表态：会翻 or 明确报错
        │
        ▼
L1 契约层（FilterExpr：9 算子 + 13 内置字段 + 2 命名空间）
    小而稳的核心词汇表，变更走严格纪律
```

各层回答的问题：

| 层 | 回答 | 内容 |
|---|---|---|
| L3 | 会不会冲突 | 不会——消费方实例隔离，造句互不可见 |
| L2 | 能力谁保证 | 四编译器对每个算子显式表态，禁止静默不支持 |
| L1 | 怎么扩展 | 小核心词汇表，变更走演进纪律（见 §2） |

## 2. 演进纪律（L1 变更的三条军规）

共享层变更（加算子 / 改编译器 / 改字段语义）时刻，冲突风险才兑付。三条纪律防"抢方向盘"：

1. **纯增量原则**：只能加新算子/新字段白名单，**永不修改已有算子的语义**。
   例：`ne` 今天对缺字段判真，明天想改成报错——不行，那是破坏性变更，必须走新算子
   （如 `ne_strict`）。语义漂移是冲突的根源，纯增量从根上掐断。
2. **表态原则**：新算子进 L1 时，四个翻译官必须逐一显式实现或显式拒绝（现有正面案例：
   Milvus 编译器对 `eq`/`ne` 直接报错）。禁止"静默不支持"——查不出错才最危险。
   落成**契约测试**：一张 `算子 × 后端` 矩阵，每次加算子 CI 强制全表表态。
3. **连坐测试原则**：动 L1/L2 的 PR 必须同时跑检索 + 演进两边回归。
   制度基础：AGENTS.md 约束 #2（跨模块规约变动必须更新 specs）。

## 3. 四级决策树（"filters 能力不够"怎么办）

新需求（演进算法、检索功能都要）按顺序过四级，**能往下一级解决的绝不往上动**：

| 级 | 判断 | 解法 | 动共享层？ |
|---|---|---|---|
| **L0 词汇够** | 现有 9 算子 + 命名空间能组合出来 | 直接造句（`lifecycle IN [active]`、`t_message GTE cutoff` 均属此级） | 否 |
| **L1 该进核心** | 是通用谓词、检索也会用（如 `exists`） | 进 `FilterOp` 枚举 + 四后端实现 + 契约矩阵测试（检索受益） | 是，走 §2 纪律 |
| **L2 后置够** | 演进专属、且不需要下推（数据量小/点读路径） | resolver 内 Python 后置筛选（不进契约、不持久化） | 否 |
| **L3 打标够** | 演进专属、量大到必须索引级过滤 | 构建期**打标**（写 `user_metadata.*`）+ 命名空间过滤 | 否（开放命名空间现成） |

要点：

- **L3 的巧劲**：`user_metadata.*` / `system_metadata.*` 是天然开放的扩展面。算法想要新
  筛选维度，首选构建期打标（如 `dream_batch: "2026-09-14"`），读侧用现成 `eq`/`in` 查。
  **字段维度的扩展不需要动契约**——命名空间本来就是开放的。
- 真正需要动契约的只有**新算子**（新比较语义），走 L1 纪律。
- 灵魂原则：**"能下推的进契约，不能下推的走后置"**——与检索层现有结构同构（索引下推是
  性能优化，UnitReader 真源复核是正确性兜底），演进侧照抄：谓词源下推选料 + resolver
  后置收口。同一模式复用，架构一致性免费获得。

## 4. 已知风险审计（2026-09-14 逐文件验证）

对 9 算子 × 13 字段 × 四后端做过一次纯增量原则审计，结论：**无存量语义违规，但 6 项演进
风险**，1 项高危：

| # | 风险 | 位置/证据 | 严重度 |
|---|---|---|---|
| 1 | **裸名吞噬**：裸名不在 13 白名单 → 自动归入 `user_metadata.<name>`。将来往 `_BUILTIN_FIELDS` 加新字段（如 priority）时，所有存量 `{"priority": ...}` 一夜之间从"查用户标签"变"查新内置字段"——静默语义翻转 | `canonical_filter_field` | **高（治理级）** |
| 2 | Python 求值器 `1 == True` 判真；pg jsonb / ES term 判否。内存后端与 ES/pg 分歧——"测试过、线上挂"型 | `memory_filter._matches_clause` | 中 |
| 3 | `metadata.*` 命名空间移除先例——破坏性变更历史上发生过一次，证明风险真实 | `filter._check_field` 报错文案 | 中（先例） |
| 4 | `t_message` 无哨兵约定（t_event→0、t_invalid→哨兵有），真源 None 在窗口谓词下被各后端一致排外但静默 | `memory_filter._field_value` | 中（F04 遗留 #3） |
| 5 | ES 数值字段映射 double，>2^53 整数丢精度 vs Python 任意精度；normalize 未拒绝超大整数 | `T_INVALID_OPEN` 注释 | 低 |
| 6 | ES 标量守卫依赖写侧投影 array_marker——隐式跨层契约，只活在代码注释未进 specs | `_scalar_match` / `_array_marker` | 低-中 |

### 治理动作（按收益排序）

1. **冻结 `_BUILTIN_FIELDS`**：新标量字段一律进 `system_metadata.*` 命名空间（照样可筛、
   零语义翻转）——堵 #1，一条纪律的成本。
2. bool/number 分歧二选一：当 bug 修（严格比较，走跨模块纪律 + 全后端回归）或写进 specs
   已知分歧清单——#2。
3. ES array_marker 契约、哨兵"三处同改"清单归档进 specs（现在只有代码注释）——#4、#6。
4. `normalize` 顺手拒绝 >2^53 整数（低成本对齐）——#5。

## 5. 新演进算法接入操作（问答式）

新算法（如 `dream_3`）要选料时：

```
① 需要什么筛选条件？写在纸上
② 过 §3 四级决策树
   ├─ L0 → 造句即用，今天就能跑
   ├─ L1 → 提契约变更：spec 修订 + 枚举加词 + 四后端表态 + 矩阵测试（检索受益）
   ├─ L2 → resolver 后置钩子（Python，不进契约、不进注册表）
   └─ L3 → 构建期打标 + 命名空间查询（写侧打标，读侧零改动）
③ 任何一级都不需要新建"演进版 filters"——方言分裂是死路
```

## 6. 诚实边界（本方案刻意选择的成本）

- L2 后置钩子不下推：全量捞回再筛，数据量大时贵——它排在 L3 前只因实现零成本，量大该走 L3。
- L1 纯增量意味着词汇表只增不减：五年后可能 20 个算子 × 四后端实现面——刻意选择的成本，
  换"任何老查询永不坏"。
- 契约矩阵测试是持续负债：每次动 L1 全表跑——这份负债正是"影响检索"的保险单。
- 本文档是**治理动机与方案**；可执行规范（检查单、决策树路径、冻结令、优先级）在
  [F06-filter-governance-playbook.md](F06-filter-governance-playbook.md)。CI 强制项（表态
  矩阵测试）落地时机 = 第一次真实的 L1 变更提案。
