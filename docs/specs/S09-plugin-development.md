## 范围 / 边界

本规约定义新增或修改可插拔能力时必须遵守的通用规则，包括：

- 接口、实现、注册、发现和装配的职责边界；
- 顶层插件、组合插件和子能力插件的替换规则；
- 有状态依赖的共享、能力声明和生命周期；
- 安全、Scope、错误、可观测性和测试不变量；
- 插件演进时的兼容和文档同步要求。

本规约不记录具体实现类、target 列表、当前代码缺陷、某次重构步骤或后端选型。这些内容分别
归入模块 `AGENTS.md`、特性文档和问题清单。

## 核心概念

| 概念 | 定义 |
|---|---|
| 契约 | 上层可以依赖的抽象接口、输入输出、错误语义和不变量 |
| Producer | 某一类能力的注册、构建和依赖解析入口 |
| target | 插件实现注册到 Producer 时使用的稳定标识 |
| 具名实例 | 由配置声明并在同一次装配中按名称共享的实例 |
| 顶层插件 | 能够独立完成所属业务阶段完整责任的实现 |
| 子能力插件 | 只完成一个局部能力、必须由顶层或组合插件编排的实现 |
| 组合插件 | 通过注入多个子能力实现完整契约的顶层插件 |

## 不变量

### 1. 契约与实现分离

公共接口和 Producer 不得依赖具体实现模块。实现通过注册加入系统，调用方只依赖契约、能力
声明和配置引用，不直接 import 或判断具体实现类。

新增插件不得要求修改调用方的分支表。只有公共契约确实发生变化时，才允许协调修改上层。

### 2. 注册、发现和装配是不同阶段

注册只表示某个 target 可以被构建，不表示它已被加载、配置或实例化。系统必须明确完成：

```text
实现发现/加载 -> target 注册 -> 配置选型 -> 依赖解析 -> 实例构建 -> 健康校验
```

任何阶段失败都必须给出明确错误，不得静默换成其他实现。

### 3. 装配拓扑必须显式

组件选择、具名实例和依赖关系由装配配置决定。实现内部不得自行解析另一套平行配置、创建
未声明的有状态依赖，或依赖 import 顺序获得正确实例。

默认实现也必须经过与第三方实现相同的 Producer 和配置路径，不能使用只有内置实现才能进入的
特殊装配分支。

### 4. 有状态依赖必须共享

同一装配拓扑中表示同一数据源、索引、客户端或状态容器的依赖必须通过具名引用共享。缺少必需
的有状态依赖时应在装配阶段失败，不得匿名创建一个看似可用但数据不相通的新实例。

是否共享由配置和契约决定，不能依赖调用顺序或进程级隐式单例。

### 5. 顶层插件必须履行完整责任

被配置为某一业务阶段顶层入口的插件，必须独立履行该阶段契约。只能处理局部数据、单一索引或
单一步骤的实现必须声明为子能力，不能因为接口形状相似就作为顶层插件装配。

装配器应在启动阶段校验完整性；不能等到运行时才出现“调用成功但结果不可用”。

### 6. 能力声明必须真实且稳定

可选能力必须通过显式能力声明查询。声明支持某能力，就必须完整实现该能力的正常路径、错误
语义、健康检查和资源释放；未声明的能力应返回统一的不支持错误。

能力集合在实例生命周期内保持稳定。临时故障通过 health 和操作错误表达，不得通过动态增删
能力掩盖故障。

### 7. 组合插件的子能力必须可替换

组合插件可以提供默认子能力，但每个独立职责都应通过契约注入。替换一个子能力不应要求重新
实现整个组合插件，也不应要求修改核心装配代码。

组合插件只能编排子能力，不得绕过其公共契约访问实现私有状态。

### 8. 上层依赖统一门面

上层业务模块优先依赖领域级统一门面，不负责选择和组装底层后端。确实需要底层原语的组件，
只能通过统一门面暴露的标准能力端口访问，并先检查能力声明。

绕过统一门面直接解析底层 Producer 只能作为被规约明确列出的独立数据域；该例外仍需定义
所有权、安全、Scope、生命周期和恢复责任。

### 9. 核心代码不得识别具体插件类型

核心编排不得使用具体实现类型、模块路径或 target 名决定业务行为。不同实现的差异必须通过
多态接口、能力声明或装配期策略表达。

需要 `isinstance(ConcretePlugin)` 才能完成的绑定，说明公共契约或装配协议尚不完整。

### 10. 配置拓扑与运行时参数分离

插件种类、组合关系和实例数量属于装配拓扑，只能在装配或重建时改变。连接地址、凭据、模型
参数等允许晚绑定的值可以运行时刷新，但不得借晚绑定偷偷替换插件结构。

未知 target、无效引用、缺失必填依赖和不兼容能力组合必须 fail fast。

### 11. 安全与 Scope 不得因插件替换而退化

插件必须继承系统既有的授权、Scope 隔离和过滤边界：

- 调用身份与目标 Scope 分离；
- 持久化对象的真实 Scope 是后续操作的权威来源；
- 用户过滤条件只能与系统和授权过滤条件取 AND，不能扩大访问范围；
- 领域门面和其暴露的底层能力端口执行一致的安全约束；
- 不得把访问上下文隐藏在 metadata、extensions 或后端私有参数中绕过公共契约。

安全能力未配置时采用哪种默认行为由所属模块 spec 明确，插件不得自行改变。

### 12. 降级和部分失败必须显式

只有契约声明为可选或 best-effort 的能力才能降级。降级时必须返回结构化错误或产生可观测事件，
不得把“插件缺失”“通道不可用”和“查询确实无结果”都表示为空结果。

涉及真源和派生数据的操作必须定义提交顺序、幂等性、重试入口和恢复方式。部分成功不能被报告
为完整成功。

### 13. 健康检查和资源生命周期属于契约

插件的 health 必须反映其履约所需依赖的真实状态。组合插件负责聚合必需子能力的健康状态，
可选子能力的故障按降级协议报告。

持有连接池、线程、文件句柄或远程客户端的实现必须提供明确的关闭语义，并由装配根统一管理
生命周期，不能依赖解释器退出清理。

### 14. 兼容只能通过显式适配维护

公共接口、配置键、target 和持久化格式变化时，应提供适配器、迁移或明确的废弃周期。兼容层
只负责旧契约到新契约的转换，不得承载新的业务能力。

废弃路径应有测试和可观测提示；完成约定迁移后再删除，不能长期形成两套事实来源。

### 15. 文档与实现同步

公共接口、跨模块协议和不变量变化时更新对应 spec；新增实现、目录关系和本地约束更新模块
`AGENTS.md`；方案取舍和已知遗留写入 feature 文档；当前缺陷写入 issue 文档。

不得把具体修复步骤、文件迁移清单或某个实现的临时限制写成长期规约。

## 错误语义

| 场景 | 必须行为 |
|---|---|
| target 未注册或未加载 | 装配失败，指出 Producer 和 target |
| 具名依赖不存在 | 装配失败，指出引用位置和名称 |
| 顶层插件能力不完整 | 装配失败，不进入服务状态 |
| 请求使用未声明能力 | 返回统一的不支持错误 |
| 必需插件运行失败 | 操作失败，并保留可重试信息 |
| 可选插件运行失败 | 按契约返回部分结果和结构化错误 |
| 安全或 Scope 校验失败 | 拒绝操作，不得降级或换后端重试 |
| health 失败 | 报告真实依赖故障，不得返回伪健康 |

## 测试基线

每个新增插件或插件契约变更至少包含以下验证：

1. **契约测试**：同一套测试可运行于默认实现和新增实现，验证输入输出、错误和边界语义。
2. **装配测试**：仅通过标准配置选择 target、注入依赖并构建成功，不修改核心代码。
3. **替换测试**：替换单个插件后，未替换能力和上层业务契约保持不变。
4. **共享测试**：有状态依赖在所有消费方之间保持约定的对象身份和数据一致性。
5. **安全测试**：覆盖授权拒绝、跨 Scope 访问、过滤收窄和底层端口访问。
6. **故障测试**：覆盖必需能力失败、可选能力部分失败、重试和恢复。
7. **生命周期测试**：验证 health、关闭和重复装配不会泄漏资源或复用旧状态。
8. **默认配置回归**：未声明新插件时，默认行为和既有公开契约不变。

依赖外部服务的插件应同时提供无需外部服务的契约测试替身，以及真实后端集成测试。集成测试因
环境不可用而跳过时，不得宣称后端能力已完成验证。

## 开发检查清单

提交新增或修改插件前，逐项确认：

- 是否先定义或复用了稳定契约，而不是从具体 SDK 反推接口？
- 实现是否可以只通过注册和配置接入？
- 核心代码是否完全不知道具体实现类型？
- 顶层和子能力的责任是否明确，装配期能否校验？
- 有状态依赖是否使用具名引用共享？
- 能力声明、health、错误和关闭语义是否完整？
- 安全、Scope 和过滤边界是否与默认实现等价？
- 可选降级和部分失败是否可观测、可重试？
- 是否通过契约、装配、替换和故障测试？
- spec、模块 `AGENTS.md`、feature 和 issue 是否各自记录了正确内容？
