# 部署方式概览

最近一次修订日期：2026-09-05

本文用于帮助使用者先确定 agent-memory 的运行形态，再进入对应的详细安装步骤。当前项目的
部署方式可以归为两类：**容器化部署**与**SDK 部署**。

```text
agent-memory
├── 容器化部署
│   ├── 远程嵌入/精排模型 + Redis / Milvus / Elasticsearch
│   ├── 本地嵌入/精排模型 + Redis / Milvus / Elasticsearch
│   └── 远程嵌入/精排模型 + PostgreSQL / pgvector / Elasticsearch
└── SDK 部署（Python 进程运行内核）
    ├── 存储：进程内内存 / Docker 后端存储
    └── 调用：直接调用 MemoryAPI / 启动本地 HTTP 服务
```

## 1. 两类部署方式

### 1.1 容器化部署

容器化部署使用 Docker Compose 同时运行 agent-memory HTTP 服务和所需的存储后端。应用、
连接配置和后端依赖被组织在同一个 Compose profile 中，适合希望快速得到一套完整服务、减少
宿主机 Python 环境差异的场景。

当前仓库提供三套完整 Compose profile：

| Profile | 模型形态 | 真源与索引后端 | 对外形态 |
|---|---|---|---|
| `online` | LLM、嵌入、精排均调用远程服务 | Redis + Milvus + Elasticsearch | HTTP，默认端口 `8137` |
| `local` | 嵌入、精排在应用容器内加载本地 BGE；LLM 默认仍为远程 DashScope | Redis + Milvus + Elasticsearch | HTTP，默认端口 `8137` |
| `postgres` | LLM、嵌入、精排均调用远程服务 | PostgreSQL KV + pgvector + Elasticsearch | HTTP，默认端口 `8137` |

这里的“本地模型”仅指嵌入和精排模型本地运行，当前 `local` profile **没有内置本地 LLM**。
PostgreSQL 是存储选型，与模型形态是两个正交维度；仓库当前没有直接提供“本地嵌入/精排模型
+ PostgreSQL”的现成 profile。

详细步骤见[容器化部署](容器化部署.md)。

### 1.2 SDK 部署

SDK 部署是指由使用方的 Python 进程安装并装配 `jiuwen_memory`，可以直接调用
`MemoryAPI`，也可以在该进程上启动仓库提供的本地 HTTP 服务。

> 当前 `jiuwen_memory_entry/sdk` 还没有独立封装的 SDK 客户端或启动器。因此本文中的“SDK 部署”是对
> Python 包直接集成方式的统称，稳定入口是 `jiuwen_memory.api.assemble()` 返回的
> `MemoryAPI`。

这种方式有两个独立选择维度：

| 存储方式 | 直接调用 MemoryAPI | 本地 HTTP 服务 |
|---|---|---|
| 进程内内存 | 最小开发、测试、功能验证 | HTTP 协议联调、跨语言快速接入 |
| Docker 后端存储 | Python 应用内嵌记忆能力，并持久化数据 | 本地常驻服务、跨进程访问，并持久化数据 |

详细步骤见[SDK 部署](SDK部署.md)。

## 2. 如何选择

| 需求 | 建议方式 | 原因 |
|---|---|---|
| 最快验证 add/search | SDK + 内存 + 直接 MemoryAPI | 无外部服务，启动成本最低 |
| 联调 HTTP 请求格式 | SDK + 内存 + 本地 HTTP | 无外部存储，也能验证 HTTP 接口 |
| Python 应用内嵌且需要持久化 | SDK + Docker PostgreSQL/pgvector/ES + MemoryAPI | 不增加 HTTP 跳转，后端数据可持久化 |
| 本机提供跨进程 HTTP 服务且需要持久化 | SDK + Docker PostgreSQL/pgvector/ES + 本地 HTTP | 应用在宿主机，存储在容器中，便于开发调试 |
| 一条命令拉起完整服务 | 容器化部署 | 应用与后端依赖统一由 Compose 管理 |
| 嵌入和精排数据不能发送到远程模型服务 | 容器化 `local` profile | BGE 嵌入与精排在应用容器内运行 |
| 希望减少 Milvus、etcd、MinIO 组件数量 | 容器化 `postgres` profile | pgvector 替代 Milvus 及其依赖 |

## 3. 能力与边界

### 3.1 默认内存栈

不传配置调用 `assemble()` 时，系统使用内置离线配置：

- `CompositeStorage` 统一承载 Storage 接口；
- KV、Vector、Fulltext、Graph Store 均为进程内实现；
- 嵌入使用 hashing，实现不依赖外部模型；
- LLM 使用 echo，精排使用 overlap；
- 进程退出后，内存数据丢失。

它适合功能开发和测试，不应当被当作持久化部署。

### 3.2 HTTP 与 MemoryAPI 一一对齐

本地 HTTP 服务是 `MemoryAPI` 上的一层 JSON 适配，公开其全部 36 个方法。每个方法使用
`POST /v1/<method_name>`，请求字段名称、嵌套结构、必填项和默认值与同名 `MemoryAPI` 方法保持
一致；成功响应直接序列化原方法返回值，不增加另一层业务响应或任务语义。

HTTP 边界只做两类必要转换：

- `Scope`、`Context`、`MemoryPatch` 等 Python 对象使用同结构 JSON 对象表达，枚举和时间分别使用
  字符串值和 ISO 8601 字符串表达；
- `security` 不接受请求体传入，而是由认证边界根据认证 runtime 的认证结果构造后注入。
  dev 模式使用最小 `DevHttpSecurityRuntime`，不等于已装配完整生产安全运行时。

同步方法在请求线程内直接调用；异步方法由 HTTP 入口等待同名异步方法完成后返回原结果，不改造成
后台 job。选择 Python 直接调用通常是为了进程内低延迟、静态类型和 Python 对象，而不是为了弥补
HTTP 的常规接口缺口。不过，写入 `system_metadata.coords` 的归属判定扩展当前仍会被
HTTP/CLI 参数解析拒绝，需要直接调用 Python API；详见 [API F05 已知遗留](../../features/api/F05-http-memory-api-alignment.md#已知遗留)。

### 3.3 当前 HTTP 服务的安全边界

仓库提供的是基于 Python 标准库 `ThreadingHTTPServer` 的参考服务，不内置 TLS 或多进程管理。
业务请求必须先建立可信 `RequestSecurityContext`，请求体中的 `security`、`actor_*`、`identity`
等身份声明会被拒绝。默认 `required` 模式未装配生产 runtime 时，业务接口返回 503，不会降级信任
请求体身份。本地功能测试可显式启用 `dev` 模式，由服务端生成固定 `local/developer` ROOT 身份；
该模式忽略认证头但仍执行 MemoryAPI 授权。

标准启动入口 `HttpServer.serve()` 在创建 socket 前校验绑定地址，dev 模式默认只允许回环
地址（如 `127.0.0.1`、`::1`、`localhost`）。仅复用 `handler_cls()` 自建服务器不会执行
该校验，嵌入方必须自行保证绑定策略。Docker 容器内监听
`0.0.0.0` 还需显式设置 `JIUWEN_MEMORY_HTTP_ALLOW_DEV_AUTH_NON_LOOPBACK=true`；仓库 Compose
已设置该开关，并默认只把端口发布到宿主机 `127.0.0.1`。如需暴露到共享网络或生产环境，应恢复 `required`、提供生产级认证 runtime，并在
前置网关补充 TLS、访问控制和流量保护，使用适合生产的进程与可用性管理方案。

> **危险开关**：`JIUWEN_MEMORY_HTTP_ALLOW_DEV_AUTH_NON_LOOPBACK=true` 放开的是 dev
> 监听限制，不会增加凭据验证。任何能连接服务的人都会使用同一个测试身份，再接受 API
> 业务授权。必须限制端口发布、容器网络和代理转发的访问范围；启动 warning 不等于安全防护。

## 4. 不单独视为部署方案的接入方式

- **CLI**：提供全部 36 个 API 同名命令，参数名和 JSON 结构与 MemoryAPI 一致。
  本地直接调用 API，使用 `--server` 时原样发送 HTTP 请求；不保留旧参数和返回值转换。
  本地测试须显式 `--auth-mode dev`，远程认证由服务端决定。见 [CLI 说明](../../../jiuwen_memory_entry/cli/DESIGN.md)。
- **MCP**：可以通过 stdio 或 streamable HTTP 暴露工具，本质上是协议接入面；其底层仍需要选择
  内存或真实存储配置。
- **`jiuwen_memory_entry/sdk`**：当前只有包目录骨架，没有形成独立于 `jiuwen_memory.api` 的 SDK 产品层。
- **Kubernetes / Helm / systemd**：当前仓库没有提供对应的现成部署清单。
