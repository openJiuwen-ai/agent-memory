# 容器化部署

容器化部署使用 Docker Compose 同时运行 agent-memory HTTP 服务和后端存储。仓库已经提供
`online`、`local`、`postgres` 三套可直接配置和启动的 profile。

```text
调用方
  │ HTTP :8137
  ▼
agent-memory 应用容器
  ├── MemoryAPI / 构建 / 检索
  ├── 模型：远程调用，或容器内加载 BGE
  └── Storage 接口
       ├── Redis 或 PostgreSQL KV
       ├── Milvus 或 pgvector
       └── Elasticsearch
```

## 1. 前置条件

- Python 应用本身无需安装到宿主机，但需要 Docker 与 Docker Compose v2；
- Redis/Milvus/Elasticsearch profile 建议为 Docker 分配至少 `20 GB` 内存，完整栈常驻约
  `13–18 GB`；
- 能够拉取所需镜像；使用远程模型时，容器还需要访问相应模型端点；
- 默认 HTTP 端口 `8137`、Elasticsearch 端口 `9200`；Milvus profile 还暴露
  `19530/9091`，PostgreSQL profile 默认暴露 `5432`。

详细的原始 Compose 参数可对照 [deploy/docker/README.md](../../../deploy/docker/README.md)。

## 2. Profile 选型

| Profile | 应用内模型 | 外部模型 | 存储后端 | 适用场景 |
|---|---|---|---|---|
| `online` | 无 | LLM、嵌入、精排 | Redis + Milvus + ES | 已有远程模型服务，希望应用镜像更轻 |
| `local` | BGE 嵌入、BGE 精排 | LLM | Redis + Milvus + ES | 记忆内容不希望发送给远程嵌入/精排服务 |
| `postgres` | 无 | LLM、嵌入、精排 | PostgreSQL KV + pgvector + ES | 希望减少 Milvus、etcd、MinIO 组件 |

所有 profile 都通过 `POST /v1/<verb>` 暴露 HTTP 接口，并通过 `GET /healthz` 提供健康检查。

## 3. 在线模型模式

该模式的 LLM、嵌入和精排均由远程服务提供，真源使用 Redis，向量索引使用 Milvus，关键词
索引使用 Elasticsearch。

```bash
cd deploy/docker/online
cp .env.example .env
# 编辑 .env，至少配置 LLM_API_KEY、MODEL_API_TOKEN、
# EMBEDDER_BASE_URL、RERANKER_BASE_URL
docker compose config
docker compose up -d --build
```

模型 URL 有两条需要特别注意：

- `EMBEDDER_BASE_URL` 必须包含 `/v1`，OpenAI 客户端会在其后追加 `/embeddings`；
- `RERANKER_BASE_URL` 不要包含 `/rerank`，适配器会自行追加该路径。

默认 LLM target 为 DashScope。若改用通用 OpenAI-compatible 服务，需要同时调整
`config.yml` 中的 target、模型名、URL 和厂商专属参数，不能只替换 URL。

## 4. 本地模型模式

该模式在 agent-memory 应用容器内加载 `bge-m3` 与 `bge-reranker-v2-m3`，LLM 默认仍调用
DashScope。模型文件不会在容器启动时自动下载，应先在宿主机准备。

```bash
cd deploy/docker/local
./download-models.sh
cp .env.example .env
# 编辑 .env，至少配置 LLM_API_KEY
docker compose up -d --build
```

下载完成后，`deploy/docker/models/` 中应存在 `bge-m3/` 与
`bge-reranker-v2-m3/`。Compose 会把它们挂载到应用容器的 `/models-local`。

模型在应用第一次收到相关请求时才载入内存，因此首次 add/search 可能明显更慢。没有 GPU 时会
使用 CPU，功能仍可用，但批量写入和并发吞吐会受影响。

## 5. PostgreSQL 模式

该模式使用同一个 PostgreSQL 实例保存 KV 真源和三组 pgvector 向量表，并继续使用
Elasticsearch 保存全文索引。它不再启动 Redis、Milvus、etcd 和 MinIO。

```bash
cd deploy/docker/postgres
cp .env.example .env
# 编辑 .env：配置模型凭据与端点，并修改默认数据库密码
docker compose config
docker compose up -d --build
```

首次创建 PostgreSQL 数据卷时，[scripts/pg_schema.sql](../../../scripts/pg_schema.sql) 会自动：

- 安装 `vector` 扩展；
- 创建 `agent_memory_kv`；
- 创建 `agent_memory_vectors`、`agent_memory_vectors_l0`、
  `agent_memory_vectors_l1`；
- 创建 scope、metadata 和 HNSW 相关索引。

初始化脚本只会在空数据卷首次启动时执行。默认 DDL 使用 `public` schema、1024 维向量与
COSINE/HNSW。若修改 schema、表名或嵌入维度，需要在创建数据卷前同步修改 `.env`、
`config.yml` 和初始化 SQL；已有数据卷不会自动迁移。

## 6. 启动后验证

以下命令适用于三套 profile：

```bash
docker compose ps
docker compose logs -f agent-memory
```

另开终端执行：

```bash
curl http://localhost:8137/healthz

curl -X POST http://localhost:8137/v1/add \
  -H 'Content-Type: application/json' \
  -d '{"tenant_id":"demo","scope":"alice","content":"用户偏好用 Python 写代码"}'

curl -X POST http://localhost:8137/v1/search \
  -H 'Content-Type: application/json' \
  -d '{"tenant_id":"demo","scope":"alice","query":"用户喜欢用什么语言","k":5}'
```

健康检查返回 `status: ok` 只表示 HTTP 进程能够响应。完整可用性还应以一次真实 add/search
闭环为准，因为模型连接、向量维度或索引配置错误往往到业务调用时才暴露。

## 7. 配置加载规则

每个 profile 的 Compose 文件都会把本目录的 `config.yml` 挂载到容器内
`/config/config.yml`，应用启动命令再读取这个路径。因此真正决定所用配置的是 Compose 中的
挂载源。

```yaml
volumes:
  - ./config.yml:/config/config.yml:ro
```

HTTP 服务配置分为两层：

```yaml
profile: docker-profile-name

memory_api:
  globals: {}
  kv_store: {}
  vector_store: {}
  fulltext_store: {}
```

- `profile` 属于服务接入层，用于标识当前 profile；
- `memory_api` 内部才是交给 `build_kernel()` 的两级组件命名空间；
- 用户配置会合并覆盖内置默认装配，因此只需声明需要替换的实现；
- `${VAR}` 与 `${VAR:-default}` 由 HTTP 启动配置加载器递归展开；
- Docker Compose 会读取同目录 `.env`，配置文件本身无需保存密钥。

HTTP 启动器允许传入多个配置文件，但文件之间按顶层键浅合并。后一个文件一旦声明
`memory_api`，就会整体替换前一个文件的 `memory_api`，不会对其内部继续深合并。因此，同一
profile 的内核差异应尽量写在一份 `memory_api` 中。

## 8. 容器网络与宿主机地址

Compose 内部通过服务名连接后端：

- `redis:6379`
- `milvus:19530`
- `elasticsearch:9200`
- `postgres:5432`

这些名称只在 Compose 网络内可解析。如果改成“应用在宿主机运行、只用 Docker 启动存储”，
配置必须改用 `127.0.0.1` 和映射到宿主机的端口，不能直接复用上述容器 DNS 名称。具体操作见
[SDK 部署](SDK部署.md)。

## 9. 数据与生命周期

```bash
docker compose down
```

停止服务并保留具名数据卷。再次启动时，后端数据仍然存在。

```bash
docker compose down -v
```

停止服务并删除当前 profile 声明的数据卷。这会删除真源和索引数据，通常不可恢复，执行前应
确认已有备份。

## 10. 生产使用前需要补齐的能力

当前 HTTP 服务是参考实现，不内置 TLS、传输层身份认证、限流或多进程管理。Compose 中的
Elasticsearch 也默认关闭安全认证，默认数据库凭据仅适合开发环境。

对共享网络或生产环境部署，至少应补充：

- 在反向代理或 API 网关终止 TLS；
- 使用可信身份系统生成 actor，而不是信任请求体中的 actor 字段；
- 修改所有默认密码，按最小权限配置后端账户；
- 限制 PostgreSQL、Elasticsearch、Milvus 等后端端口的暴露范围；
- 为 PostgreSQL、Redis、Elasticsearch、Milvus 和模型端点配置 TLS；
- 增加限流、超时、重试、日志采集、监控、备份和恢复策略；
- 根据可用性目标补充进程编排与多副本方案。

## 11. 常见问题

### 健康检查正常，但检索为空

按顺序检查应用日志中的嵌入异常、模型端点连通性、向量维度是否一致，以及 Elasticsearch/Milvus
或 pgvector 中是否真正生成了索引数据。本地模型下载不完整时，也可能出现写入成功但索引构建
降级的情况。

### 中文关键词召回效果差

Elasticsearch 默认 analyzer 未必适合中文。可以选用内置 `cjk`，或使用安装了 IK 插件的
Elasticsearch 镜像并配置 `ik_max_word`。Analyzer 只在索引创建时生效，修改后需要重建旧索引。

### 修改配置后没有生效

若修改了 Compose 挂载或服务定义，应执行 `docker compose up -d` 重新创建相关容器，单纯
`restart` 不会应用 Compose 文件变化。随后用 `docker compose config` 和容器日志确认实际配置。
